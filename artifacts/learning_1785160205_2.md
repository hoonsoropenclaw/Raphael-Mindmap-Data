+## 2. 技術選型 — 為什麼這樣決定
+
+### 2.1 為什麼選 useReducer 而不是多個 useState？
+
+**選 useReducer 的理由**：
+- 狀態有 8 個互相關聯的欄位（cards / searchQuery / priorityFilter / editingId / dragState × 3），散在 useState 會變成「prop drilling + 隱式依賴」
+- Reducer pattern 讓所有變化都走 action，未來要加 undo/redo、redux-devtools、middleware（thunk / saga）都零成本擴展
+- Action type 是字串常量，比散落的 setter 更容易追蹤、grep、測試
+- TypeScript 化時 reducer signature 給完整的 type safety
+
+**唯一取捨**：Reducer 對新手較不直觀，需要多一個心智模型（action → reducer → state）。
+
+### 2.2 為什麼不引入 react-dnd / dnd-kit？
+
+- **減少依賴**：這個專案對外部 lib 零依賴，CDN 單檔就能跑
+- **原生 DnD API 已經夠用**：純粹「跨欄移動」場景，HTML5 `dragstart` / `dragover` / `drop` 三事件就夠
+- **教學價值**：寫原生比寫 lib 配置更能展示狀態流（start → over → end）
+- **bundle size**：省 ~30KB（dnd-kit minified）
+
+**取捨**：原生 DnD 在手機觸控支援差。如果未來要觸控，再換 react-dnd 或 @dnd-kit。
+
+### 2.3 為什麼不用 Tailwind / styled-components？
+
+- 純 CSS + CSS 變數最容易審閱、最容易調樣式
+- 對 demo 場景：讀 styles.css 比讀 utility class 組合直觀
+- **零 build step**：CSS 是單檔，CDN 模式直接 `<link>` 就好
+
+### 2.4 為什麼 CDN + Vite 雙模式？
+
+- **CDN**：1 秒看見效果，無需 `npm install`（適合 demo / 教學 / 快速 prototype）
+- **Vite**：正式專案導入時的路徑（import 元件 + HMR）
+- 兩個 entry（`index.html` / `App.jsx`）邏輯分離，不互相污染
