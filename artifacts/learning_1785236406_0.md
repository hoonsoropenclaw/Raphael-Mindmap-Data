    技術決策摘要
    1. DB：純 stdlib sqlite3，WAL 模式、BEGIN/COMMIT 顯式交易；測試用 per-app temp file 隔離（:memory: 對 per-request connection pool 不友善——曾踩坑、debug 後改寫）
    2. Schema：id INTEGER PK AUTOINCREMENT、title/description/completed/created_at/updated_at、created_at 加 index
    3. Rate limit：原本用 @limiter.limit() decorator，但會破壞 FastAPI 對函式簽名的解析（POST payload 被當 query）——slowapi 的已知行為；改寫為 ASGI middleware，直接呼叫 slowapi 的 __evaluate_limits 帶動態選擇的 limit（依 HTTP method 決定 60/m 或 20/m）。過程也踩到 hit() 不 raise、test() 不消費——這些都修了
    4. 測試：用 create_app(db_path=":memory:", disable_rate_limit=True) 跑 CRUD + 驗證、再 disable_rate_limit=False 單獨驗 rate limit（25 次 POST 必拿 429）
    5. 204 端點：用 response_class=Response + Response(status_code=204) 解掉 FastAPI 「204 must not have body」的 assert
    
    設計上的取捨（你可以決定是否要回頭改）
    - 用 tempfile.NamedTemporaryFile 取代 :memory: 是「乾淨但會留 .db 檔」的解；如果你想完全乾淨，可以加 teardown hook os.unlink
    - Rate-limit middleware 直接呼叫 slowapi 的 name-mangled private API（_Limiter__evaluate_limits、_key_func）；這是 trade-off——能動態選 limit 但綁 slowapi 內部實作。如果升級 slowapi 可能要重檢。較保守的解法是放棄動態、改在 endpoint 上 @limiter.limit("20/minute") 並讓那 3 個 endpoint 吃 request: Request（已經驗證會引發 422 bug，需要另外改 FastAPI 解析方式）
    - slowapi 的 _check_request_limit 想用但失敗，因為它不會動態套 limit、要靠 decorator 註冊
