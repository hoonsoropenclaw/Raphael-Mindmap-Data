+from fastapi.responses import JSONResponse
+from slowapi import Limiter, _rate_limit_exceeded_handler
+from slowapi.errors import RateLimitExceeded
+from slowapi.middleware import SlowAPIMiddleware
+from slowapi.util import get_remote_address

+
+from . import __version__

+### B2. Rate limit — 為什麼不直接用 slowapi 的 SlowAPIMiddleware
+**踩坑紀錄**：原本計畫用 `slowapi==0.1.9` 的 `SlowAPIMiddleware`（社群標準答案），但實測發現一個 upstream bug：
+
+- slowapi 0.1.9 的 `Limiter._check_request_limit` 第一行 `endpoint_url = request["path"] or ""`
+- starlette/fastapi 的 `Request` 是 object 不是 dict，`request["path"]` 會 raise `AttributeError`
+- `sync_check_limits` 內 `except Exception as e:` 把這個 `AttributeError` 視為「其他錯誤」走 fallback handler
+- 結果：使用者觸發 rate limit 時，server 回 **500** 而不是 429
+
+**修法選擇**（我評估了三條路）：
+1. ❌ monkey-patch `request["path"]`：第一次嘗試做了 shim，但其他位置又在用 `request.something["x"]` 之類寫法，得不償失
+2. ❌ 把 slowapi 降版：風險高（其他依賴鏈可能不匹配）
+3. ✅ **自製薄 middleware**（最終選的）：約 80 行程式碼、邏輯清楚、零外部依賴、保留 `X-RateLimit-*` headers
+
+實作見 `app/rate_limit.py` 的 `IPRateLimiter` + `app/main.py` 的 `RateLimitMiddleware`。策略是 in-memory **sliding window**（deque of timestamps per key），不用引進 redis 依賴。
+
+**未來要水平擴展**：把 `_hits` 換成 redis 後端（介面已隔離 `check()`），其他程式碼不動。
+
+### B3. Circular import 預防
