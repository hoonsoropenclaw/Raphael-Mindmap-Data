+# Senior Architect Review / Implementation Notes
+
+## Input feedback
+
+The global `~/.hermes/architect_feedback.md` was read before implementation. It described a different Linux monitoring project, so no project-specific design was available. The reusable principles were applied:
+
+- Do not pass secrets through CLI arguments. This API has no secret-bearing CLI arguments; operational configuration is supplied through environment variables (`TODO_DATABASE`, `TODO_RATE_LIMIT`, `TODO_RATE_WINDOW_SECONDS`).
+- Protect mutable state from concurrent updates. SQLite writes are guarded by a process-local lock and use transactions; the rate limiter uses its own lock.
+- Prefer explicit, verifiable state handling. The database schema is initialized deterministically and all SQL values are parameterized.
+
+## Architecture
+
+1. FastAPI provides the HTTP layer and OpenAPI documentation.
+2. Synchronous endpoint functions are paired with the standard-library `sqlite3` driver. This avoids mixing `async def` with blocking database calls.
+3. SQLite stores `todos` with integer primary keys, validation constraints, UTC ISO-8601 timestamps, and a completion flag.
+4. A middleware-based in-memory sliding-window rate limiter keys requests by client IP. `/health` is excluded so liveness checks remain available during throttling.
+5. Pydantic models validate create/update payloads and shape responses, preventing unbounded title or description input.
+6. SQL uses placeholders everywhere user input reaches the database.
+7. Application startup uses a FastAPI lifespan handler, and the `204` delete route explicitly disables response-model generation for current FastAPI compatibility.
+
+## Verification evidence
+
+- `python3 -m pytest -q` -> `6 passed`
+- `python3 -m compileall -q app.py test_app.py` -> exit code `0`
+- Live uvicorn smoke test -> health `200`, create `201`, list `200`, update `200`, delete `204`
+- Rate-limit behavior is covered by unit tests and returns `429` with `Retry-After`.
+
+## Known scope limits
+
+- The rate limiter is process-local; deploy behind multiple workers or replicas with Redis/database-backed limiting for global enforcement.
+- SQLite is appropriate for a simple single-instance API. Higher write concurrency should move to PostgreSQL.
+- There is no authentication because it was not requested; production multi-user deployment should add authentication and ownership checks.

    架構決策摘要
    
    - 使用同步 FastAPI endpoint + sqlite3
    - 避免在 async def 中混用同步資料庫操作
    - 使用 SQLite placeholder 防止 SQL injection
    - 使用 lock 保護同一 process 內的寫入與 rate limiter 狀態
    - 以環境變數提供資料庫與 rate limit 設定
    - 不將敏感資訊放在 CLI 參數中
    - 使用 UTC ISO-8601 timestamp
    - todos table 加入 completed IN (0, 1) constraint
    - 明確處理 404、422、429 與 204 狀態
    
    已知限制
    
    目前是簡單單機版本：
    
    1. Rate limiter 是 process-local  
       多 worker 或多副本部署時，需要改用 Redis 或集中式資料庫。
    
    2. SQLite 適合低至中等寫入量
