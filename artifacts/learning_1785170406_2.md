+# JOURNAL.md — fetch_trending.py 實作思路
+
+## 1. 目標
+
+寫一個自動化腳本，從 GitHub Trending 抓取 repositories，輸出成 markdown 表格。
+不需使用者互動，單一 CLI 工具直接跑就會產出檔案。
+
+## 2. 設計決策（為什麼這樣做）
+
+### 2.1 為什麼選 HTML 抓取而非 GitHub API
+
+- **GitHub 官方沒有 Trending API**。`/search/repositories` 可用 `created` + `stars` 排序近似，但
+  ranking 是「絕對星數總和」而非「時間區間內的星數增量」——這跟 GitHub Trending 的語意（今天/這週/
+  這個月誰漲最多）不同。要複製 Trending 的真實語意，**直接抓 `github.com/trending` HTML 是唯一乾淨解**。
+- 不需要 GitHub token（公開頁面），省去 onboarding。
+- HTML 結構穩定（GitHub 用 `article.Box-row` class 已多年），defensive parser 多寫 2 個 fallback 即可。
+
+### 2.2 為什麼選 `requests` + `BeautifulSoup` + `lxml`
+
+- 系統已裝（驗證：`beautifulsoup4 4.13.5`, `lxml 5.4.0`, `requests 2.34.2`），PEP 668 不必新建 venv。
+- 比起 `urllib`：cookies / redirects / encoding / JSON 都不用自己處理。
+- `lxml` 比 html.parser 快且容錯更好（GitHub HTML 有時不嚴謹）。
+
+### 2.3 為什麼帶 User-Agent header
+
+- 觀察：GitHub 對裸 `python-requests/x.x` UA 會回 403 或跳 captcha。
+- 解法：偽裝成 Chrome 124 desktop user-agent。已在實測驗證過（沒有 UA 會 403，加了之後 200 + 完整內容）。
+
+### 2.4 為什麼提供 CLI flags 而非環境變數 / config file
+
+- 一個 script 對應一個 invocation pattern，CLI 是 Unix 慣例（grep / jq / curl 都這樣）。
+- 用 `argparse` + `choices={'daily','weekly','monthly'}` 自動擋掉非法 since 值（驗證：`--since bogus` 立即
+  被拒、exit code 2）。
+- `--stdout` flag 是給「用 pipe 串接」用的（例：`python3 fetch_trending.py --stdout | head`）。
+
+### 2.5 為什麼 schema 是 `dataclass TrendingRepo`
+
+- 10 個欄位（rank/full_name/url/description/primary_language/language_color/stars_total/
+  stars_period/forks_total/contributors_count/built_by）剛好對應 trending 頁的視覺資訊。
+- `@dataclass + asdict()` 雙用：JSON 輸出直接 `asdict(r)`，markdown 輸出讀欄位名（IDE-friendly）。
+- `field(default_factory=list)` 避免 mutable default 陷阱。
+
+### 2.6 為什麼 parser 寫 3 層 fallback
+
+GitHub 公開 HTML 偶爾會改 class（這是公開服務的特性），我寫了：
+
+1. **主路徑**：`article.Box-row`（歷史最穩定的 class）
+2. **退路 1**：`[data-testid='repository-row']`（GitHub 2018 後開始用 data-testid）
+3. **退路 2**：用 `h2.h3` 找容器（class 全失效時的最終保險）
+
+每一層都做相同的事，所以只要任一層活著就能拿到資料，缺資料時 stderr 會印「沒抓到任何 repo」
+並提示「HTML 結構可能改了」。
+
+### 2.7 為什麼輸出檔名預設是 `trending_<since>[_<lang>].md`
+
+- 排程重複跑不會覆蓋昨天的（除非 since + lang 完全一樣），方便做 daily diff / archive。
+- 使用者也可以用 `--out` 完全覆寫。
+
+### 2.8 為什麼同時支援 `--json`
+
+- Markdown 給人看，JSON 給程式接（cron job、log aggregation、GitHub Actions artifact）。
+- 兩個 flag 獨立，可只輸出其一。
+
+### 2.9 為什麼做 defensive int parsing（`_parse_int`）
+
+- GitHub HTML 把大數字顯示成 `1.2k`、`15K`、`3.4m`（小於 1000 進位）
+- 也可能顯示 `1,234`（千分位逗號）
+- 三種格式都要正確 parse，不然 stars 欄位會亂掉
+- 容錯：parse 失敗回傳 0（不要 raise 中斷整個 run）
+
+### 2.10 為什麼 markdown 表格右對齊數字欄位
+
+- GitHub Flavored Markdown：`--:|`
+- 數字欄位右對齊視覺上更好掃（readability）
+- 文字欄位（Repository / Description / Language）左對齊
