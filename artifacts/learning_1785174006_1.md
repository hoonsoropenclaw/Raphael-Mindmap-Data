+"""In-process token-bucket rate limiter.
+
+Why token bucket?
+- Smooth bursts: short bursts of 20 requests go through, then steady-state
+  is bounded by refill rate (5 req/sec default → 0.2s avg response window).
+- O(1) memory per key: just two floats (tokens, last_refill_ts).
+- No external dependency (Redis etc.) needed for a single-instance app.
+
+Trade-offs:
+- In-memory state means per-instance limits. If you scale out to N workers,
+  each gets its own bucket. For this todo app (single FastAPI worker for
+  dev / small prod), that's acceptable. A future upgrade would push bucket
+  state into Redis with INCR + EXPIRE.
+- Keys are derived from a header (default: x-api-key) and fall back to
+  client IP. Both can be spoofed by the caller, so this is *defense in
+  depth* not authentication. For real auth add JWT/API-key validation
+  before this layer.
+"""
+
+from __future__ import annotations
+
+import math
+import threading
+import time
+from dataclasses import dataclass, field
+from typing import Optional
+
+from .config import Settings
+
+
+@dataclass
+class _Bucket:
+    tokens: float
+    last_refill: float
+
+    def copy(self) -> "_Bucket":
+        return _Bucket(self.tokens, self.last_refill)
+
+
+@dataclass
+class RateLimitDecision:
+    allowed: bool
+    remaining: float
+    retry_after_sec: float
+    capacity: int
+    refill_per_sec: float
+
+
+class RateLimiter:
+    def __init__(self, settings: Settings, *, clock=time.monotonic) -> None:
+        self._capacity = settings.rate_capacity
+        self._refill = settings.rate_refill_per_sec
+        self._clock = clock
+        self._buckets: dict[str, _Bucket] = {}
+        self._lock = threading.Lock()
+
+    # --- internal ---------------------------------------------------------
+
+    def _refill_bucket(self, bucket: _Bucket, now: float) -> None:
+        elapsed = now - bucket.last_refill
+        if elapsed <= 0:
+            return
+        bucket.tokens = min(
+            float(self._capacity),
+            bucket.tokens + elapsed * self._refill,
+        )
+        bucket.last_refill = now
+
+    def _get_or_create(self, key: str, now: float) -> _Bucket:
+        with self._lock:
+            b = self._buckets.get(key)
+            if b is None:
+                b = _Bucket(tokens=float(self._capacity), last_refill=now)
+                self._buckets[key] = b
+            else:
+                self._refill_bucket(b, now)
+            return b.copy()

## 設計取捨說明

### 1. 為什麼 single connection + lock，而不是 connection pool
SQLite 對 concurrent write 用 WAL mode 已經不差；多 connection 在 in-process 時只是徒增 lock 競爭。一條 connection + 一個 `threading.Lock` 序列化所有 read/write，模式簡單、行為可預測。

### 2. 為什麼 `isolation_level=None` (autocommit)
讓 `db._tx()` 自己管理 `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`，可以精準控制錯誤時 rollback。比 sqlite3 預設的「自動 begin」+「commit on success」透明。

### 3. 為什麼 `BEGIN IMMEDIATE` 而不是 `BEGIN`
`IMMEDIATE` 一開始就搶 RESERVED lock，避免 `BEGIN` + 第一個 write 才升級成 RESERVED 時的 race。

### 4. 為什麼 FakeClock 注入而不是 monkey-patch `time.monotonic`
`RateLimiter(clock=...)` 接受 callable injection；測試可以寫 `clock.advance(0.5)` 直接跳時間。沒有 `monkey-patch.setattr`，沒有副作用。

### 5. 為什麼 `/healthz` 不過 rate limit
Kubernetes liveness probe 預設每秒打，過 rate limit 會把 pod 標 unhealthy 然後無限重啟。`/healthz` 必須永遠 free。

### 6. 為什麼 PUT 重置 `completed=False`
HTTP 語意上 PUT 是「用新 representation 取代舊的」，沒帶 `completed` 欄位 → 重置。PATCH 才做 partial merge。

### 7. 為什麼 rate-limit key 先看 `x-api-key` header 再看 IP
header 是 application-level identifier（多 client 共用同一 IP 的 NAT 也分得開）；IP 退到 fallback。同時 header 可被 spoof，所以**這不是 auth**，僅是 rate-limit key — README §Security 已說明。

### 8. 為什麼 WAL sidecar 檔案（`-wal` / `-shm`）保持 0644
它們是 SQLite 內部頁面 cache，沒有 main db 解不出來；umask 077 + dedicated service account 才能完全收緊。`0o644` + main 0600 已經是大多數部署的可接受權限模型。

+## 設計取捨說明
+
+### 1. 為什麼 single connection + lock，而不是 connection pool
+SQLite 對 concurrent write 用 WAL mode 已經不差；多 connection 在 in-process 時只是徒增 lock 競爭。一條 connection + 一個 `threading.Lock` 序列化所有 read/write，模式簡單、行為可預測。
+
+### 2. 為什麼 `isolation_level=None` (autocommit)
+讓 `db._tx()` 自己管理 `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`，可以精準控制錯誤時 rollback。比 sqlite3 預設的「自動 begin」+「commit on success」透明。
+
+### 3. 為什麼 `BEGIN IMMEDIATE` 而不是 `BEGIN`
+`IMMEDIATE` 一開始就搶 RESERVED lock，避免 `BEGIN` + 第一個 write 才升級成 RESERVED 時的 race。
+
+### 4. 為什麼 FakeClock 注入而不是 monkey-patch `time.monotonic`
+`RateLimiter(clock=...)` 接受 callable injection；測試可以寫 `clock.advance(0.5)` 直接跳時間。沒有 `monkey-patch.setattr`，沒有副作用。
+
+### 5. 為什麼 `/healthz` 不過 rate limit
+Kubernetes liveness probe 預設每秒打，過 rate limit 會把 pod 標 unhealthy 然後無限重啟。`/healthz` 必須永遠 free。
+
+### 6. 為什麼 PUT 重置 `completed=False`
+HTTP 語意上 PUT 是「用新 representation 取代舊的」，沒帶 `completed` 欄位 → 重置。PATCH 才做 partial merge。
+
+### 7. 為什麼 rate-limit key 先看 `x-api-key` header 再看 IP
+header 是 application-level identifier（多 client 共用同一 IP 的 NAT 也分得開）；IP 退到 fallback。同時 header 可被 spoof，所以**這不是 auth**，僅是 rate-limit key — README §Security 已說明。
+
+### 8. 為什麼 WAL sidecar 檔案（`-wal` / `-shm`）保持 0644
+它們是 SQLite 內部頁面 cache，沒有 main db 解不出來；umask 077 + dedicated service account 才能完全收緊。`0o644` + main 0600 已經是大多數部署的可接受權限模型。
