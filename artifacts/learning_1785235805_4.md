    發現兩個真實的 bug,我得停下來修:
    
    Bug 1: FilterBar 的 useMemo 的 selector useKanbanSelector 裡 allTags 是每次 render 都回傳新陣列 — 因為 Array.from(set).sort() 每次都建新陣列,selector output reference 每次都變 → 觸發 "getSnapshot should be cached" 警告 → 然後進無限 loop。
    
    Bug 2: KanbanColumn 的 useFilteredTasks 也回傳新陣列,同樣問題。
    
    這是 useSyncExternalStore 經典陷阱 — selector 必須回傳 stable reference 否則無限重渲。我必須在 store 內做 memoization,或在 selector 層用 useMemo + stable input。
    
    最乾淨的修法是讓 selector 不在每次呼叫時回傳新 array — 我用兩個方案:
    
    方案 A:selector 裡 memo,用 useRef + useMemo 包裹
    方案 B:在 store 內部用 reselect 風格 memoization,對 derived 陣列用 shallow equality

+## 2. 架構決策 (Architecture Decisions)
+
+### 2.1 State shape — 為什麼拆 `tasks` (Map) + `order` (column → array)
+
+```js
+state = {
+  tasks: { [id]: Task },            // O(1) lookup, Task 是 immutable
+  order: { [columnId]: id[] },      // 每欄順序獨立維護
+  filters: { tags: [], priorities: [] },
+  ui: { modal, toast, draggingTaskId },
+  history: { past: [], future: [] }
+}
+```
+
+**理由**:
+- 跨欄移動 = `order` 結構 copy 兩欄、`splice` 兩次。tasks map 不動。
+- 改任務內容(標題、tags)只更新 tasks,不動 order。React 重新 render 只針對被改的卡片。
+- 排序是「顯式 array」而非 sorted insertion — 拖放插入任意位置簡單。
+- Map + array 雙結構看似冗餘,但避開了「需要 sort 或重排整個 array 才能 move 一個 item」的成本。
+
+### 2.2 Store 模式 — `useSyncExternalStore` 取代 Redux/Zustand
+
+選 React 18 內建的 `useSyncExternalStore`:
+- concurrent-mode 安全(store 切換不會撕裂 UI)
+- 不需要 Provider(任何地方都能用 hook 訂閱)
+- 與 React 18 batch + selective hydration 直接整合
+
+關鍵陷阱(下面 §3 fix 段落會詳述):selector 必須回傳 stable reference,否則 `getSnapshot should be cached` warning + 無限 re-render loop。

+### 2.3 Undo / Redo — bounded snapshot stack
+
+```js

+```
+
+每個 snapshot 只含 domain state(`tasks`, `order`, `filters`),不含 `ui`。ui 變化(open modal、set dragging)不污染 history。

+**Bounded = 50 筆**(HERMES-LITE trade-off:50 步 undo 對任務管理場景足夠,記憶體可控)。
