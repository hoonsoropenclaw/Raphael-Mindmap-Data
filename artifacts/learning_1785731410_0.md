+"""
+Async event bus — the core of the event-driven crawler architecture.
+
+Design notes
+------------
+The crawler is decomposed into three loosely-coupled actors communicating
+through an async event bus rather than direct function calls:
+
+  - EventBus            : pub/sub channel, asyncio.Queue per subscriber
+  - ScrapeJob producer  : publishes 'JOB_DISPATCHED' events with target URLs
+  - WorkerPool consumer : subscribes to 'JOB_DISPATCHED', publishes 'ITEM_FOUND'
+
+Why event-driven instead of `await asyncio.gather(...)`?
+
+  - Decouples scheduling from execution: a 'RATE_LIMITED' event from one
+    worker can throttle ALL workers without producer/consumer refactor.
+  - Back-pressure becomes natural: queue sizes cap in-flight jobs, memory
+    stays bounded regardless of crawl depth.
+  - Observability is free: every event passes through the bus, so a
+    WebSocket-style dashboard can subscribe to the same stream.
+
+Concurrency is bounded by `maxsize` of the job queue, NOT by raw asyncio
+gather — this is the single most important detail.  An unbounded gather
+will OOM the moment the target has 100k+ pages.
+"""

+
+import asyncio
+import enum
+import time
+import uuid
+from dataclasses import dataclass, field
+from typing import Any, Awaitable, Callable, Optional

+    RATE_LIMITED = "rate.limited"
+    PAGE_REQUEST = "page.request"
+    PAGE_RESPONSE = "page.response"

+async def hackernews_extractor(html: str, url: str, page: Page) -> list[dict[str, Any]]:
+    """Pulls `<a class="storylink">title</a>` entries from an HN-like page.

+    Returns one item per link with {title, href, source_url}.

+    """Subscribes to ALL events and keeps the last N in a list.  Useful for

+## 2. 架構設計
+
+```
+       Crawler.run(urls)
+              │
+              ▼
+    ┌─────────────────────┐
+    │     EventBus        │  ← 每個 subscriber 一個 asyncio.Queue (maxsize=1024)
+    │  pub/sub + 背壓      │
+    └─────────────────────┘
+       ▲          ▲
+       │          │
+       │     ┌────┴───────────────────────┐
+       │     │   WorkerPool              │
+       │     │   - N 個 async worker     │ ← asyncio.Semaphore 限流
+       │     │   - 每個 worker 1 個       │
+       │     │     BrowserContext        │   (隔離 cookie / storage)
+       │     │   - page.on('request',    │
+       │     │           'response',     │   ← 全部 page 生命週期事件
+       │     │           'console')      │      都 fan-out 到 bus
+       │     │     → publish PAGE_*      │
+       │     │   - extractor(html,url,   │
+       │     │     page) → items         │
+       │     └───────────────────────────┘
+       │
+    EventStore.__call__  ← 單一 observer 把所有事件 append 起來
+                              （測試 / debug / future WebSocket dashboard）
+```
+
+**為什麼 event-driven 而非 `asyncio.gather(...)`：**
+
+- **背壓自然**：每個 subscriber queue 是 bounded 的。慢 consumer 不會卡整條 pipeline；只會丟它自己的事件（其他 subscriber 仍收到）。
+- **解耦**：未來加 RATE_LIMITED consumer 可同時節流所有 worker，不用改 producer/consumer 介面。
+- **可觀測性免費**：每個 page 生命週期觀察（request / response / console / error）都是 stream event。「為什麼這個 URL 抓失敗？」→ 重放 event log 就行。
+- **併發兩處節流**：(1) bus queue（記憶體上限）、(2) worker semaphore（CPU/RAM 上限）。兩者缺一不可 — 任何單獨一個都會在大規模爬取時 OOM。
