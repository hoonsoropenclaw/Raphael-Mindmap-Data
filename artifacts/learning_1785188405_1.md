+## 2. 架構決策

+### 2.1 狀態模型：append-only segment log + dictionary tasks
+
+```ts
+TimerState {
+  active: ActiveRun | null                    // 目前 live run（null = 待開始）
+  segments: readonly TimerSegment[]           // append-only 每次 START 的記錄
+  tasks: readonly TaskEntry[]                 // 用戶建的任務
+  selectedTaskId: string | null               // 計時歸屬到哪個任務
+  mode: TimerMode                             // pomodoro / short-break / long-break
+  history: HistoryStacks<TaskEntry>           // task 操作 undo/redo
+}
+
+TimerSegment {
+  id, mode, startedAt, endedAt  // endedAt = null 表示進行中
+}
+```
+
+**為什麼用 append-only segment 而不是累計 ms？**
+
+- 暫停 → 繼續 → 暫停 過程中**毫秒不丟**（reducer 永遠關閉前一段、開新一段）
+- 未來要做「今天我專注幾分鐘」分析 = `segments.filter(s => s.endedAt !== null).reduce(...)`，零改動
+- reducer 邏輯只用 immutable append + close，永遠 O(1) 操作
+
+**為什麼 history 只追蹤 task 編輯、不追蹤 timer？**
+
+- 計時是 live clock，不是文件編輯——按一次 undo 不該把「正在倒數的時鐘」倒帶回 24:55
+- 這呼應 Kanban Board 的 L3 #2：「UI-state vs domain-state 的歷史邊界」
