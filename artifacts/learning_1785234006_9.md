+    matches the stdlib-first production tool pattern.

+## Design decisions
+
+### 1. Stdlib only — no `requests`, no `beautifulsoup4`
+
+`urllib.request` + `html.parser.HTMLParser` + `dataclasses` is enough for a
+single HTTP endpoint that returns ~150 KB of HTML with stable structural
+patterns. Pulling `requests` or `bs4` would add install cost and a third-party
+attack surface for zero benefit.
+
+This follows the **stdlib-first production tool pattern** documented in
+`trial-and-error/references/by-category/stdlib-production-tool-pattern.md`.
+
+### 2. No GitHub token
+
+GitHub does **not** expose a public REST endpoint for trending. GraphQL's
+trending is not available either. HTML scraping of `github.com/trending` is the
+only first-party path. GitHub's anonymous HTML endpoint is rate-limited to
+~60 reqs/hour/IP, which is fine for ad-hoc or daily cron use.
+
+If higher throughput is needed later: switch to a GitHub API workflow that
+sorts repositories by `created_at` or `updated_at` and manually filters for
+"trending" — but that's a different feature, not the same one.
+
+### 3. HTMLParser state machine (not regex)
+
+Each `<article class="Box-row">` is one repo card. The parser walks:
