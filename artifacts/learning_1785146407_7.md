+| 批次選取與操作   | Set<id> 狀態 + 7 種批次 actions           |

+## 3. 架構決策
+
+### 3.1 為什麼用 useReducer 而非 useState 散彈槍
+
+14 種 action、共用同一份 state schema（tasks/filter/selected/editing/lastDeleted）。如果拆 useState 會遇到：
+- 批次刪除要同時改 `tasks` + `selected`，分開 setState 會有 race
+- 拖曳 reorder 要 atomic 改 list 順序
+- 復原刪除要從 `lastDeleted` 撈回，跨欄位耦合
+
+`useReducer` 一個 dispatch 保證 atomicity，且 action type 字串化讓每個意圖可追溯。
+
+### 3.2 為什麼用 Context API 而非 Redux/Zustand
+
+兩個 context（Theme + Toast）各只裝單一職責，不會有 re-render 地獄。Redux 對這個規模是 overkill，多 30KB+ 程式碼換一個 DevTools —— 教學/展示情境不必。
+
+### 3.3 為什麼 inline edit 用 conditional render 而不是彈出 modal
+
+modal 會切斷使用者的 context（要對齊「編輯誰」），條件 render 原地變身為表單（CSS 設負 margin 讓卡片外觀不變）才是流暢體驗。
+
+### 3.4 為什麼 score 公式用線性加權而不是排序抽象
+
+`score = impact*10 - effort*2 + priorityWeight - (overdue ? 50 : 0) + statusBonus`
+
+- 影響度權重最高（影響使用者最深的才是重點）
+- 投入度是負權重（花越少時間越優先做）
+- 逾期是 50 的懲罰（強烈要求正視）
+- 完成/封存是負分（自動沉底、不佔視線）
+
+這條公式簡單、可調（PM 想改權重就改數字），不需引入 ML/排序演算法。
+
+### 3.5 為什麼用 CSS 自訂屬性做主題而非 className 切換
+
+```css
+[data-theme="light"] { --bg: #f6f7fb; ... }
+```
+
+- 30+ 個顏色 token 一次切換
+- 不用寫兩份樣式
+- transition: background var(--transition) 讓切換有平滑感
+
