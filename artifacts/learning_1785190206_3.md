+## 1. Why this design, not "another Todo list"
+
+The prompt asked for "a complete React UI component with complex state management". A naive Todo app is one `useState<Task[]>` away from "done" and demonstrates none of the moving parts that justify the request. I deliberately picked a **mission control console** because it forces the following to co-exist:
+
+1. **Multi-axis state machine** — 4 statuses × 4 priorities × N labels × free text query
+2. **Undo/redo with domain/view separation** — view (filter, sort, selection) must not pollute history
+3. **Versioned persistence** — localStorage round-trips, rejects unknown versions and malformed payloads
+4. **Inspector + Batch operations** — multiple panels reading and writing the same store coherently
+5. **Responsive industrial aesthetic** — must read as a control tower, not a Notion clone
+
+## 2. State architecture (the load-bearing decision)
+
+### 2.1 Shape: dictionary + sequence
+
+```ts
+DomainState {
+  tasks: Record<TaskId, Mission>   // O(1) lookup, immutable updates
+  order: TaskId[]                    // render order; new tasks prepend
+}
+ViewState   { filters, sort, selectedIds, inspectorTaskId, editorTaskId, theme }
+HistoryState { past: DomainState[]; present: MissionState; future: DomainState[] }
+```
+
+I split dictionary from sequence because the data model has two different update patterns:
+- "Toggle `critical`" touches one task → O(1) `tasks[id]` lookup, no order change
+- "Move to column 2 position 3" needs column lookup, splice in/out of order arrays
+
+Trying to keep both in one `Task[]` array forces every update to re-allocate the entire array, breaking `React.memo` and ratcheting up re-renders.
+
+### 2.2 Domain vs view split (L3 lesson inherited)
+
+`task/*` actions carry timestamps and mutate domain; `filter/*`, `sort/*`, `selection/*`, `inspector/*`, `editor/*`, `theme/*` mutate view only. The `historyReducer` is the single chokepoint: domain actions push to `past` and clear `future`; view actions return immediately with no history touch.
+
+This is the L3 lesson that the previous Kanban iteration codified. Confirming it works in practice: after a `task/batch-status` action, pressing Undo restores the prior statuses but **keeps** the current `query=aurora` filter and sort order, so the user is not teleported into a disorienting "where am I" state.
+
+### 2.3 `scrubView` — the boring function that prevents 6 categories of bugs
+
+Every reducer that mutates domain also has to think: "what view refs are now stale?" `selectedIds` may point to deleted tasks; `inspectorTaskId` may dangle; `editorTaskId === "new"` is always valid but an `editorTaskId === "missing-id"` is not. `scrubView` runs after every domain mutation and prunes dangling references.
+
+Without this, the Undo button becomes a footgun: pressing it would render a panel referencing a deleted mission. With it, the reducer is always self-consistent.
+
+### 2.4 Pure reducer → testability (the previous-iteration TODO closed)
+
