+# github-trending
+
+Scrape [GitHub Trending](https://github.com/trending) and emit a GitHub-flavored Markdown table.
+
+**No API key, no auth, no OAuth.** Just a desktop `User-Agent` and HTML parsing.
+
+## Why this exists
+
+GitHub does not expose `/trending` through its REST API. The Trending page is
+server-rendered HTML, so the cleanest path is to parse it. This library pins
+the structure that's been stable since 2014 (`<article class="Box-row">` +
+indexed `<h2>` headings + `<p class="col-9">` descriptions) and turns each
+card into a typed `Repo` object.
+
+## Install
+
+```bash
+pip install -e .
+```
+
+Or just drop the `github_trending/` folder into your project — it has no
+runtime dependencies.
+
+## CLI
+
+```bash
+# Today's trending (default)
+python -m github_trending
+
+# Python repos this week
+python -m github_trending --language python --since weekly
+
+# Save to a file
+python -m github_trending --output trending.md
+
+# JSON instead of markdown
+python -m github_trending --json --output trending.json
+
+# Top 10 only
+python -m github_trending --limit 10
+```
+
+Output looks like:
+
+```markdown

+# GitHub Trending Scraper — Implementation Notes
+
+## Task
+Write an automated script that scrapes GitHub Trending repositories and
+outputs them as a Markdown table.
+
+## TL;DR
+Built a zero-dependency Python package at `github_trending/` with a CLI,
+typed data model, and three test tiers. End-to-end works: scraping live
+GitHub, parsing 14-25 repos per page, rendering a valid GitHub-flavored
+Markdown table.
+
+```
+$ python -m github_trending --language python --since weekly --limit 10
+## GitHub Trending — weekly (python)
+
+| # | Repository | Description | Language | Stars | Stars in period |
+| --- | --- | --- | --- | --- | --- |
+| 1 | [ayghri/i-have-adhd](https://github.com/ayghri/i-have-adhd) | A skill for your coding agent… | Python | 11,186 | +6,991 this week |
+…
+```
+
+## Design decisions
+
+### 1. HTML scraping, not the REST API
+GitHub has no public REST endpoint for `/trending`. The Trending page is
+server-rendered HTML, so the cleanest path is to parse it. The HTML
+structure has been stable since 2014 — `<article class="Box-row">` per repo,
+with a heading `<h2>`, description `<p class="col-9">`, language
+`<span itemprop="programmingLanguage">`, and star/fork anchors. This is an
+unofficial contract but it's been stable for over a decade.
+
+### 2. Zero runtime dependencies
+`urllib.request`, `re`, `html`, `argparse`, `json` — all stdlib. The package
+is 814 LOC including tests and can be dropped into any project without
+`pip install`. Dev deps: only `pytest`.
+
+### 3. Three-tier testing
+- **Unit tests** (`test_scraper.py`): pure function coverage — URL building,
+  HTML cleaning, Markdown rendering, regex parsing, validation.
+- **Offline integration** (`test_offline.py`): runs the full pipeline
+  against a real HTML fixture in `tests/fixtures/trending_page.html`. No
+  network. This catches structural regressions even when GitHub isn't
+  reachable.
+- **Smoke tests** (`@pytest.mark.smoke`): actually GET github.com/trending
+  to confirm the live structure still matches our regex. Skippable with
+  `-m "not smoke"` so CI doesn't depend on outbound HTTP.
+
+### 4. Fail loud on structural change
+If GitHub ships a redesign and the page no longer contains any `Box-row`
+articles, `fetch_trending` raises `ParseError`. Silent empty results would
+be worse than a crash — the user would believe they're "getting nothing"
+when in reality the tool is broken.
+
+### 5. Defensive parsing
+A single malformed article shouldn't kill the whole page. The outer loop
+in `fetch_trending` catches `ParseError` per article and logs a warning,
+returning whatever it managed to harvest.
+
+### 6. Stable identifiers
+`Repo` carries `full_name`, `url`, and `period_stars_url` so downstream
+tooling (e.g. a Slack bot or weekly digest) can link straight to the repo
+without reconstructing URLs.
