+## 三、成品設計決策
+
+### 為何選「純 Python stdlib 監控腳本」這個最通用版本
+
+訊息中沒有指定:
+- 監控哪些指標 (CPU? Mem? Disk? 服務 port?)
+- 警告管道 (email? Slack? webhook? 寫檔?)
+- 部署方式 (cron? systemd timer? daemon?)
+- 語言/工具 (bash? Python? Go? Prometheus exporter?)
+
+**最通用版本 = 純 Python stdlib + 5 大基礎指標 + 環境變數可調閾值 + 結構化輸出**。
+理由:
+- 使用者拿到後**最容易延伸** (加 email / webhook / Prometheus 只改 main 即可)
+- 純 stdlib = 零安裝、cron 直接跑、不污染環境
+- 環境變數覆寫 = 不用改程式碼就能調閾值,適合丟進 production
+
+### 監控的 5 個指標
+
+1. **CPU 使用率** (`/proc/stat` 差值取樣, 0.5s 間隔)
+   - 不用 `top` / `ps` 因為會 fork 額外 process,且解析輸出脆弱
+2. **Load Average / nproc** (`/proc/loadavg`)
+   - 不只報 load 絕對值,還報 per-core 比率(因為 4 核主機 load=2 不算高,單核主機 load=2 已經過載)
+3. **Memory 使用率** (`/proc/meminfo` 的 MemAvailable,這才是 Linux 現代正確指標)
+4. **Disk 使用率** (`shutil.disk_usage`,可指定 path)
+5. **journalctl 錯誤數** (priority<=3,過去 10 分鐘)
+   - **有優雅降級**:journalctl 不存在時回 `skipped`,不影響 exit code
+
+### 為何選 exit code 三段 (0/1/2)
+
+- `0` = 全綠,cron 不發信
+- `1` = 有閾值超標,cron 自動寄信給 root (預設行為)
+- `2` = 整體收集失敗 (極少見,如 `/proc/stat` 都不見了),讓監控系統知道「腳本壞了」而非「系統壞了」
+
+### 為何 stderr 寫警告、stdout 寫 summary
+
+- cron / 監控 agent 通常抓 stdout (single line summary)
+- 警告細節走 stderr,人類或 syslog 收集
+- **第一次實作時我重複寫了 summary 到 stderr**(已修正),這種細節在 commit 前測試必抓到
