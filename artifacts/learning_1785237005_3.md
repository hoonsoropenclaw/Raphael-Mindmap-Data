    實作思路
    
    架構決策：
    1. Sync FastAPI over async — SQLite 是 sync-friendly DB，async + sqlite 在高併發下會 deadlock（參考 trial-and-error 教訓 38：FastAPI sync 已 production proven）。這選擇避免了 async/sync 混用的 3 類 pitfall。
    2. SQLAlchemy 2.0 ORM（declarative Base） — Mapped[T] + mapped_column() 是 SQLAlchemy 2.0 標準型別 hint 寫法，onupdate=_utcnow 自動處理 updated_at。
    3. slowapi + SlowAPIMiddleware — Limiter(default_limits=["60/minute"]) 預設全域限制，寫入端點額外 @limiter.limit(WRITE_LIMIT="30/minute") 雙層防護。Middleware 自動套 default_limits 到所有 endpoint。
    4. Pydantic v2 + model_dump(exclude_unset=True) — 支援 partial update（PATCH-style），客戶端只需送要改的欄位。
    5. Lifespan + tmp DB via env var — production 用 todo.db，測試自動切到 tempfile.NamedTemporaryFile，避免污染開發目錄。
    
    踩到的 4 個坑（依時間順序）：
    
    1. 坑 1：SQLAlchemy model 未註冊 → Base.metadata.tables = {} — 因 database.py 在 models.py 之前 import，ORM class 還沒執行。修法：app/init.py 顯式 from . import models 觸發註冊。
    2. 坑 2：SQLite :memory: 每 connection 獨立 DB — 原本 conftest 想用 in-memory engine + dependency override 換掉 get_db，但 override 設了但 request 仍然找不到表。根因調查未深，最後改用統一策略：所有 request 共用 main engine（tmp DB 檔案），每個 test 前 DELETE FROM todos 清資料。
    3. 坑 3：slowapi default_limits 不會自動套用到 endpoint — 一開始以為 Limiter 預設限制會自動 apply，實際上必須用 SlowAPIMiddleware 或每個 endpoint 加 decorator。修法：加 app.add_middleware(SlowAPIMiddleware) + 寫入端點保留 @limiter.limit(WRITE_LIMIT) 雙層限制。
    4. 坑 4：DELETE 204 不能用 JSONResponse(content=None) 回 null — FastAPI 看到回 null 就轉成 body null 字串。修法：改用 Response(status_code=204) 直接生成空 response。
