+## 實作思路

+### 1. 為什麼用 HTML 解析、不用 GitHub API
+
+GitHub **沒有公開 trending API**（這是常識、文件無此 endpoint）。可用替代方案：
+
+| 方案 | 優點 | 缺點 | 採納 |
+|------|------|------|------|
+| 官方 Search API + sort=stars | 結構化 JSON | 「trending」≠「all-time most stars」，方向不對 | ❌ |
+| 第三方 trending API（github-trending-api.herokuapp 等） | JSON 格式 | 第三方服務不穩、隨時可能下線 | ❌ |
+| 抓 `github.com/trending` HTML 自己 parse | 資料源即真相 | HTML 結構會變、需 regex 維護 | ✅ |
+| 用 Selenium/Playwright 跑 headless Chrome | 抗 JS 變動 | 重依賴、安裝成本高 | ❌（殺雞用牛刀） |

+採 HTML 解析的路徑，純 stdlib（`urllib + re + argparse`），無外部依賴。

+### 2. 解析策略：分塊 + 每塊 regex
+
+GitHub trending 頁面把每個 repo 包在 `<article class="Box-row">...</article>` 裡，所以：
+
+1. 先用 `ARTICLE_RE` 把 HTML 切成多個 article 區塊
+2. 每個 article 內部用專屬 regex 抓欄位 — 比 `html.parser.HTMLParser` 狀態機更簡潔、更可控
+3. 重要細節：欄位周圍常有 SVG icon 和巢狀 `<span>`，數字會混在 SVG path 的 `M8 .25a.75...` 裡 — `extract_number()` 先把整段 SVG 砍掉再抽數字。
+
+### 3. 區間字串的三態
+
+GitHub 對「區間內新增 stars」用三種文案，依 `?since=` 參數而定：
+
+- `daily` → `2,344 stars today`
+- `weekly` → `6,991 stars this week`
+- `monthly` → `13,743 stars this month`
+
+第一次實作只匹配 `stars today`，結果 weekly/monthly 的欄位全空。第二次 regex 改成 `(?:stars today|stars this week|stars this month)` 三選一即解。
+
+### 4. 非貪婪 regex 的陷阱（已踩過）
+
+原始 regex：`r'<span class="float-sm-right">(.*?)</span>'`
+
+問題：span 內部有 `<svg>...</svg>`，**SVG path data 內有 `M8 .25a.75.75 0 0 1 .216-.664` 這類含 `</svg>` 之前的小數點，但不會撞 `</span>` — 真正的麻煩是 SVG 內的 `<path ... d="..."/>` 跟 `</svg>` 邊界混在長字串裡**。第一次嘗試用 `.*?</span>` 在 SVG 內部遇到 `</svg>` 之後、下一個 `</span>` 才停 — 但其實 `</svg>` 後面就是 `</span>`，所以 non-greedy 反而會停在 SVG 內部任何 `</span>`。
+
+解法：用「`stars today` / `stars this week` / `stars this month`」這個文案錨點當終止條件 — 因為它在 SVG 結尾後才出現，永遠在最外層 span 的尾部。
