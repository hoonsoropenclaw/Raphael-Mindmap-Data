+         -H 'Content-Type: application/json' \
+         --data "$PAYLOAD" \
+         "$WEBHOOK_URL" \
+         >/dev/null || true
+fi
+
+# 3) syslog 留一條方便跟 journalctl / rsyslog 串接
+SEVERITY="$(printf '%s' "$PAYLOAD" | grep -oE '"severity": *"[^"]+"' | head -1 | cut -d'"' -f4)"
+SOURCE="$(printf '%s' "$PAYLOAD" | grep -oE '"source": *"[^"]+"' | head -1 | cut -d'"' -f4)"
+PRIO="user.warning"
+case "$SEVERITY" in
+    crit) PRIO="user.crit" ;;
+    warn) PRIO="user.warning" ;;
+    *)    PRIO="user.info" ;;
+esac

+if command -v logger >/dev/null 2>&1; then
+    logger -t monitor -p "$PRIO" "alert source=${SOURCE}"

+
+## 1. 任務與範圍
+
+任務：撰寫自動化腳本，定期掃 Linux 系統資源與日誌，超過閾值時發出警示。
+
+實作路徑：`/home/hoonsoropenclaw/.hermes/projects/learning_1785149406_2/`
+
+## 2. 設計決策（為什麼這樣做）
+
+### 2.1 為什麼分檔、不寫單一 monolithic 腳本
+- **monitor.py**：純監控邏輯（資源、日誌、閾值、SQLite）
+- **alert.sh**：純出口（落 log、可選 webhook、可選 syslog）
+- 理由：監控本身不該綁死通知方式。今天寫 JSON log，明天想接 Slack/PagerDuty/Email，只要改 alert.sh，monitor.py 完全不動。
+- 替代方案考慮過：「alert 都用 Python 寫」——但 sysadmin 慣例是 shell 腳本可手動 echo | ./alert.sh 測試，且不需要 Python 重啟就能改 alert 行為。
+
+### 2.2 為什麼用 SQLite 而不是純 log 檔
+- **查詢能力**：`SELECT source, COUNT(*) FROM alerts WHERE ts > ... GROUP BY source` 這類問題，純 log 只能 grep + awk
+- **去重（cooldown）**：需要以 source 為 key 記「最後送出時間」——log 檔做不到原子 upsert
+- **WAL 模式**：讀寫不互鎖，daemon 跑時可同時被外部查詢（python -c "import sqlite3; ..."）
+- 替代方案考慮過：直接用 JSON log + jq 處理——可行但每次查詢都 full scan，daemon 跑 30 天後 log 變 GB 等級會慢
+
+### 2.3 為什麼 cooldown 只擋 alert.sh、不擋 alerts 表
+- **如果連 alerts 表都擋**：人類查「過去 10 分鐘有幾次 CPU 過載」會得到「只有第一次」——失去監控意義
+- **如果只擋 alerts 表**：警示會狂炸（CPU 抖動 90%、5 秒後 89%、又 5 秒 91% — 會有幾十條 alert）
+- **正確做法**：表永遠記錄「事件」，alert.sh 用 cooldown 控制「通知」頻率。這是業界標準做法（PagerDuty / OpsGenie 也是這樣）
+
+### 2.4 為什麼 exit code 0/1/2 而不是只 0/非 0
+- `0` 一切正常
+- `1` 觸發警示
+- `2` 自檢失敗（依賴缺、psutil 壞掉等）
+- cron 看到 2 不會誤以為「系統有問題」誤報工程師，而是「監控腳本本身有問題」要修
+
+### 2.5 為什麼 daemon 模式用 `--watch N` 而非 fork 寫 daemonize
+- systemd / supervisord / launchd 都是更好的 daemon 工具，自己 fork 是重複造輪子且容易寫錯（檔案描述符洩漏、signal handling）
+- 提供 `monitor.service` systemd unit 直接 copy 用
+- 但 CLI 也支援 `--watch` 讓開發/測試方便（手動跑也能看輸出）
+
+### 2.6 為什麼 log 掃描用 regex 而不是 ELK / Loki
+- 任務是「自動化腳本」、不是「log 平台」
+- ELK / Loki 需要獨立服務、資源、維運成本
+- regex + journalctl 對 5 分鐘內的事件已經足夠（OOM、panic 這類事件頻率低，不需要全文檢索引擎）
+- 限制寫在 README：若日後量級變大，可把 `pattern: {}` 換成 Loki 查詢
+
+### 2.7 為什麼用 psutil 而不是讀 /proc 檔案
+- /proc 的格式跨版本會變（Ubuntu 24.04 vs 22.04 有些欄位不一樣）
+- psutil 已經處理跨平台 + 跨版本
+- 多數 Linux admin 環境 psutil 是標配
+
+## 3. 閾值選擇（為什麼 DEFAULT 這樣設）
+
+| 閾值 | 預設 | 為什麼 |
+|---|---|---|
+| CPU 85% | 持續 5 秒以上算「有問題」、單次 spike 不算。閾值要看 baseline |
+| MEM 90% | 留 10% 給 kernel cache，避免 swap 被打滿 |
+| Swap 50% | 一旦 swap 用超過 50% 通常代表 MEM 已經不夠；不能等到 90% |
+| Disk 90% | 超過會讓 systemd journal、logrotate 自己失敗 |
+| Load/CPU 1.5 | 經驗值（=每核心平均 1.5 個 runnable process） |
+| Net errors 100 | 累計值，預設偏寬鬆；可調低到 10 提早發現 |
+
+這些都可在 `config.yaml` 調。**沒有動態基準線**（baseline）是已知限制——若主機負載白天/晚上差異大，需要排程換 config 或接外部 baseline 服務。
+
+## 4. 警示嚴重度分級（為什麼這樣分）
+
+- `crit`：必須立即處理的硬故障（OOM、kernel panic、磁碟 >99%、CPU 超過 95%）
+- `warn`：需要關注但不一定立刻處理（auth fail 10 次、CPU 87%、load 偏高）
+- 為什麼不只用 crit/warn 二元：人類疲勞警報（alert fatigue）是 ops 大敵，太多 crit 等於沒 crit
+
