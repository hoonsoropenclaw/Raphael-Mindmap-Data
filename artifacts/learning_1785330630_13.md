+## 1. 概念邊界
+
+### 1.1 API 逆向工程「是什麼」
+
+合法用途：
+- 整合未公開 API 的第三方開發者（黑盒整合）
+- 安全研究人員對自家 API 做滲透測試
+- 企業併購時對被收購方 API 做資產盤點
+- 競品分析（公開 API 的功能性觀察）
+
+惡意用途：
+- 竊取商業邏輯或資料結構
+- 找出未公開端點（shadow API）進行未授權存取
+- 繞過認證、竊取 token、列舉使用者
+- 重打包商業 API 對外轉售
+
+### 1.2 本文立場
+
+只談**防禦**：如何讓你的 API 對逆向工程者「既難以分析、又能在被攻擊時快速偵測與回應」。不提供完整的逆向教學，也不提供任何可用於未授權系統的 exploit payload。
+
+### 1.3 核心原則（貫穿全文）
+
+| 原則 | 含義 |
+|------|------|
+| Defense in Depth | 沒有一道防線夠用，層層疊加 |
+| Least Privilege | 任何 token / session 只給剛好需要的權限 |
+| Assume Breach | 預設 API 已被逆向、token 已洩露，設計「即使如此也不致全毀」的架構 |
+| Observable | 任何異常存取都要能被偵測、紀錄、告警 |
+| Boring is Better | 用標準協定（OAuth 2.1、JWT、TLS 1.3），不要自幹 |
+
