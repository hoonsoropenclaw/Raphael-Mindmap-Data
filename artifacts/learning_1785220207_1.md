    是 SQLAlchemyError。這才是真正的 bug。修：用 check_same_thread=False + StaticPool 後，多個 session 共用同一個 SQLite 連接在 sync 模式下並發 db.commit() 還是會 race — 因為雖然是同一個連接，但多個 session 在同一個連接上同時 commit會交錯。
    
    正解：SQLite StaticPool + check_same_thread=False 仍然不能並發寫。要嘛：
    - 用檔案 + 多連接 + SQLite WAL mode + busy_timeout
    - 或在 endpoint 內部 serialize DB 操作（用 semaphore）
    - 或把 endpoint 改成 async def + 用 run_in_threadpool 跑 sync DB call
    
    Senior architect 提示：sync SQLAlchemy 跑在 async context 內，要 run_in_threadpool 才不會 block event loop。httpx ASGITransport 走 ASGI，但 FastAPI 對 sync def 路由是丟到 threadpool — 所以 def 路由理論上不會卡 event loop，但 100 並發 = 100 threadpool jobs。
    
    真正的 race：多個 thread 同時對同一個 SQLite in-memory connection做 commit。SQLite 連接不是 thread-safe（即使 check_same_thread=False 也只放行不同 thread 用同一連接，並發操作還是要序列化）。
    
    修正：endpoint 內的 DB 操作要 serialize。最簡單：endpoint 用 async with semaphore 包住 DB 操作；或 endpoint 改成真的 async 模式。
    
    更好的修法：create_app 接受 db_serial: asyncio.Semaphore，endpoint 內 await 它再執行 DB 操作。
    
    但這樣每個 endpoint 都要包 semaphore。乾脆在 _db_dep 直接做：但 _db_dep 是 generator 模式，跨 thread 就 close。
    
    最簡單：加一個 app-level asyncio.Semaphore，middleware 進入 endpoint 前 acquire。但這樣限流了所有 DB 操作，跟限流器重複。
    
    乾脆：endpoint 內每個 DB 操作都包 semaphore。把 semaphore 做成 app.state，依賴注入。
