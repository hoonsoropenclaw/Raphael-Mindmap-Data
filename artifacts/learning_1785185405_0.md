## 2. L3 教訓吸收（從 architect_feedback.md 跨專案複用）

1. **umask 防護不是 SQLite 專利，是所有 daemon-level 寫檔的常識**
   - 觸發點：architect feedback 提到 SQLite `-wal` / `-shm` 繼承 process umask 變 0644
   - 本專案實作：腳本 `__main__` 開頭直接 `os.umask(0o077)`，確保 `--log-file` 產出的 JSONL 永遠 0600（已 live 驗：`ls -la /tmp/monitor_test.log` = `-rw-------`）
   - 抽象原則：任何「會自己產檔」的 Python 腳本都應在 import 後立刻設 umask，不要依賴 systemd `UMask=` —— 因為腳本也會被 cron / nohup / ad-hoc 呼叫

2. **並發 I/O 監控的合理性（吸收「鎖競爭要驗證」）**
   - 觸發點：architect feedback 提到 SQLite WAL 在高併發下可能 race
   - 本專案實作：5 個讀取器都是 I/O bound（讀 `/proc`、讀 disk stats、呼叫 journalctl），thread pool 而非 process pool 就夠；CPU 監控刻意 sleep 1 秒取樣差分而非瞬間讀
   - 沒刻意做 async 是因為這是 batch tool 不是 long-running daemon，但保留了「未來接 asyncio.gather 壓測」的接口（dataclass + JSON 序列化可平行餵給 webhook）

3. **subprocess 必須 list 形式 + timeout（吸收 SQL injection → command injection）**
   - journalctl 用 `subprocess.run([..., "--since", since, "-p", "err", ...])`，不經 shell
   - timeout=10 秒（journalctl 在某些機器會 hang）
   - 「不可用」與「值為 0」分開表達：journalctl 不存在 / timeout → Metric.value = -1 + extra.note，觸發 ERROR alert；真的沒錯誤才 value = 0
