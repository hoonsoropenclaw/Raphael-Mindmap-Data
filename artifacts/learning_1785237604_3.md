+## 設計決策
+
+### 為什麼選 `python-telegram-bot`
+- PTB 22+ 預設 async，搭配 httpx async client，與我們 `aiohttp`/asyncio 生態一致。
+- 比 `python-telegram-bot` 早期版本或 `telethon` 更穩定、文件齊全。
+- 內建 `ApplicationBuilder` + `CommandHandler`/`MessageHandler`，不需自幹 router。
+
+### 為什麼預設 `wttr.in` 而非 OpenWeatherMap
+- **零摩擦啟動** — 拿完 token 就能跑，不用先去 OpenWeatherMap 申請 API key。
+- 對學習/原型階段剛好；production 高流量可換 OWM（`WEATHER_PROVIDER=openweathermap`）。
+
+### 為什麼 WeatherClient 是 Protocol 而非 ABC
+- 測試用 `FakeClient` duck-type 實作 — 不需繼承、import 順序簡化。
+- Production 端 `WttrClient`/`OpenWeatherMapClient` 都是 `WeatherClient` 的具體實作。
+- `build_client()` 是唯一的 factory，集中 provider 切換邏輯。
+
+### 為什麼 WeatherReport 是 dataclass（normalize payload）
+- wttr.in 與 OpenWeatherMap 回傳結構差異大（前者把溫度包成 list[dict]，後者是 m/s）。
+- 在 client 層 normalize 成 `WeatherReport` → `format_reply` 只吃正規化資料 → 換 provider 不必動 formatter。
+- 用 `frozen=True` 防止 formatter 意外 mutate。
+
+### 為什麼不用 `defaultdict` 處理 config（Senior Architect feedback）
+- 必要 env（`TELEGRAM_BOT_TOKEN`）缺值時 **立即 raise**，不默默用空字串。
+- 選填 env 在 dataclass field 給合理預設值，**顯式列出**——讀者一眼看完整設定。
+- 這呼應前次 feedback 「不要 lazy default、用 explicit 初始化」的精神。
+
+### 為什麼 `bot.run()` 用 `asyncio.Event` + signal handler
+- 不用「無限 `while True`」假 polling，事件驅動乾淨。
+- SIGINT（Ctrl+C）/SIGTERM 觸發 graceful shutdown：stop_polling → app.stop → app.shutdown → client.aclose。
+- 各階段 try/except 包起來：shutdown 期間一個失敗不影響其他清理動作（best-effort）。
