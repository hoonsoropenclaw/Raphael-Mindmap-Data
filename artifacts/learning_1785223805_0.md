+# feedback.md — Telegram 天氣 Bot 實作思路
+
+> 給下一輪接手者（Senior Architect / 自己下一輪迭代）看的「為什麼這樣寫」備忘錄。
+
+## 任務範圍
+寫一個 Telegram bot：使用者送文字 → bot 呼叫天氣 API → 回傳天氣給使用者。
+
+## 關鍵決策
+
+### 1. 天氣 API 選 Open-Meteo（不用 key）
+- **為什麼**：任務只說「呼叫天氣 API」，沒指定 provider，也沒給 API key。
+- Open-Meteo 完全免費、無需註冊、覆蓋全球、支援中文 geocoding、文件完整 → 零摩擦。
+- 預留 `.env` 欄位 `WEATHER_API_PROVIDER` + `OPENWEATHER_API_KEY`，未來要切換 provider 不必改 code。
+
+### 2. 模組切兩層：`bot.py`（Telegram 入口）vs `weather_api.py`（純資料層）
+- `weather_api.py` 是純函式 + dataclass，沒有 import `telegram`，可以獨立 unit test / mock。
+- `bot.py` 只負責：parse 訊息 → 呼叫 weather_api → 把結果丟回 Telegram。
+- **好處**：下次要加 Discord/Line 介面時 weather_api 直接 reuse；Telegram 套件升級也只動 bot.py。
+
+### 3. Mock 模式（沒 token 也能跑）
+- 環境沒 `TELEGRAM_BOT_TOKEN` 時自動走 `_run_mock_smoke_test()`：模擬幾個使用者訊息、把 bot 邏輯輸出印到 stdout。
+- **原因**：本機 CI、沒申請 bot 的開發者、無 token 的審閱者都能驗證邏輯。
+- **踩坑**：發現 `load_dotenv()` 不會清掉系統 env 既有值，所以 mock 跑要用 `env -i` 或 inline 隔離。
+
+### 4. 城市解析：別名表 + fallback 鏈
+**問題**：Open-Meteo 中文 geocoding 有兩岸歧義 + 簡繁差異：
+- `「高雄」` 簡中命中四川同名鎮，不是台灣高雄
+- `「臺北」` 完全查無結果（繁體字不在 Open-Meteo 簡中索引）
+- `「巴黎」` 直接命中法國 ✓
+
+**解法（4 層）**：
+1. **`_CITY_ALIASES` 表**（25+ 條常見中英對照）：`臺北→Taipei`、`高雄→Kaohsiung`、`首爾→Seoul`、`巴黎→Paris`...
+2. **簡→繁對照** `_TRAD_TO_SIMP`（處理臺/台、灣/湾 等）
+3. **fallback 鏈**：先 zh 簡體 → zh 原文 → en
+4. **空字串 / 只打關鍵字** → `WEATHER_DEFAULT_CITY`（預設 `Taipei`）
+
+### 5. 自然語言抽取 `_CITY_HINT_RE`
+使用者訊息可能是：
+- `/weather 台北` → regex 先剝掉指令前綴
+- `台北天氣` / `巴黎 天氣` / `東京weather` → regex 抓關鍵字後面的城市
+- `想知道` / `查`（無城市） → fallback 預設城市
+- 純 `Berlin` → 整段當城市名
+
+實測 9 個 case 全部正確路由。
+
+### 6. WMO Weather Code 中文化
+Open-Meteo 用 WMO 標準碼（0=晴、3=陰、95=雷暴…），內建 28 條對照表，沒命中就回 `未知天氣 (code=N)`。
+- **理由**：原 API 只回數字，直接給使用者看數字 UX 差。
+
+### 7. 錯誤一律 `WeatherAPIError`
+- 自訂例外帶 `url` + `status_code` 欄位
+- bot 層 catch 後回「⚠️ 查天氣失敗：xxx」訊息，**不讓例外炸到 Telegram**（避免使用者看到 Python traceback）
