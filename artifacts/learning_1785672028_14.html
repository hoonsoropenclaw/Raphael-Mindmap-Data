異步事件驅動架構在 RPA 自動化流程中的應用與優化

事件匯流排（Event Bus） · 工作者池（Worker Pool） · 重試退避（Retrier） · 死信佇列（DLQ） · 可觀測性（Observability）— 含即時互動示範

1 · 為什麼 RPA 需要從「同步腳本」升級成「異步事件驅動」

傳統 RPA（UiPath、Automation Anywhere、Playwright + Python）多半是線性同步腳本：開瀏覽器 → 登入 → 抓資料 → 寫入 Excel → 寄信 → 關閉瀏覽器。流程中只要任何一步失敗或慢，整個排程就被卡住，到了夜間批次時常常OOM、長時間等待、重複點擊同一頁面 200 次。

把腳本改寫成「事件驅動」（event-driven）後，每一個動作變成一條 Event 投遞到 EventBus，由多個 Worker 並行消費；中間結果透過事件傳遞而不是回傳值；失敗可以丟進 DLQ 讓人工介入。整個流程變成可觀測、可暫停、可重試、可水平擴展的系統。

瓶頸 1
同步阻塞
登入慢 → 整個 pipeline 等待；其他任務無法插隊。
瓶頸 2
競態 (Race)
多 agent 同時改同一個 Excel → 覆寫衝突。
瓶頸 3
失敗無重試
網站 503 一次就放棄，整批失敗。
瓶頸 4
事件丟失
process crash 後，沒做完的任務蒸發，沒有 audit log。

3 · 核心程式碼骨架（Python asyncio）

以下 code 整合 event_driven_application_development.md 與 workflow_simulation.md 兩個既有微技能，並補上 RPA 專屬的重試 / DLQ / idempotency。

# event_bus.py — 異步 publish/subscribe + 歷史快照 + 廣播
from collections import deque
from typing import AsyncGenerator
import asyncio, uuid, time

class BusEvent:
    def __init__(self, type: str, data: dict, idem_key: str | None = None):
        self.id = "evt_" + uuid.uuid4().hex[:8]
        self.type = type
        self.data = data
        self.idem_key = idem_key or self.id
        self.ts = time.time()

    def to_dict(self):
        return {"id": self.id, "type": self.type,
                "data": self.data, "idem_key": self.idem_key,
                "ts": self.ts}

class EventBus:
    def __init__(self, history_size=500):
        self._subscribers: list[asyncio.Queue] = []
        self._history = deque(maxlen=history_size)
        self._seen_idem: set[str] = set()   # idempotency

    async def subscribe(self) -> AsyncGenerator[BusEvent, None]:
        q: asyncio.Queue = asyncio.Queue()
        self._subscribers.append(q)
        try:
            while True:
                evt = await q.get()
                yield evt
        finally:
            self._subscribers.remove(q)     # 防 memory leak

    def publish(self, event: BusEvent):
        if event.idem_key in self._seen_idem:
            return False            # 重複事件略過
        self._seen_idem.add(event.idem_key)
        self._history.append(event)
        for q in self._subscribers:
            q.put_nowait(event)
        return True

    def history_snapshot(self, n: int = 20):
        return [e.to_dict() for e in list(self._history)[-n:]]
# rpa_pipeline.py — 工作者 + 重試退避 + DLQ
import asyncio, random, logging

async def worker(name, bus, dlq, handler, max_retry=3):
    "工作者：訂閱事件 → 跑 handler → 失敗就指數退避 → 最終丟 DLQ"
    async for evt in bus.subscribe():
        for attempt in range(1, max_retry + 1):
            try:
                await handler(evt.data)
                logging.info(f"[%s] ✓ %s 嘗試 %d 次成功", name, evt.type, attempt)
                break
            except Exception as e:
                if attempt == max_retry:
                    dlq.put_nowait((evt, repr(e)))
                    logging.error(f"[%s] ✕ %s 丟進 DLQ: %s", name, evt.type, e)
                else:
                    # 指數退避 + jitter，避免 thundering herd
                    wait = (2 ** attempt) + random.uniform(0, 0.5)
                    await asyncio.sleep(wait)

5 · RPA 場景的五大瓶頸與優化策略

5.1 同步等待 → 非阻塞 IO

把 requests.get()、time.sleep()、page.wait_for_selector() 包進 asyncio.to_thread()，或直接換成 aiohttp / playwright.async_api。這是事件驅動的前置條件：EventBus 上的 worker 必須是非阻塞的，否則整條 pipeline 還是會卡住。

5.2 競態衝突 → Idempotency-Key + 去重佇列

所有副作用事件（寄信、寫 DB、扣款）必須帶 idem_key。EventBus 在 publish 時就過濾重複；如果下游是資料庫，把 idem_key 設為 unique index。實務上「同一封信寄出 3 次」幾乎都靠這個修掉。

5.3 失敗無重試 → 指數退避 + Jitter

網站 503 是常態。指數退避（2s, 4s, 8s）+ jitter（±0.5s 隨機）可以避免「重試雪崩」。jitter 是關鍵——沒有它，所有 worker 會在同一毫秒一起重試，再次把網站打掛。

5.4 事件丟失 → DLQ + Idempotent 落地

最終失敗的事件不要丟給 /dev/null。背景跑一個 DLQ writer 把事件寫到 SQLite / Postgres，並透過 webhook 通知 Slack。人工介入後可以從 DLQ 重新 publish 到 EventBus 重跑。

5.5 缺乏觀測 → 結構化日誌 + 指標

每個事件都帶 id / ts / type / data，用 JSON formatter 輸出 → 直接灌進 Loki / ELK。再加四個核心指標：event_throughput、queue_depth、worker_utilization、dlq_size。沒有這四個指標，事件驅動系統就是黑盒子。

7 · 從原型到生產的部署選擇

規模建議方案RPA 典型情境
原型asyncio.EventBus + in-memory Queue個人自動化、每天 100 個事件
小隊Redis Streams + aioredis5 個 worker、跨機器、持久化
企業Kafka / RabbitMQ + DLX + Prometheus50+ worker、TB 級日誌、嚴格審計

不要一開始就上 Kafka。事件驅動的邏輯（pub/sub、retrier、DLQ、idempotency）和傳輸層（in-memory / Redis / Kafka）是正交的——先用 asyncio 寫完邏輯，再把 EventBus 換成 Redis Streams，最後才升 Kafka。邏輯都不變。

8 · 結論：三條不可妥協的設計原則

  1. 副作用必須帶 idempotency-key——沒有它，事件驅動 = 「更快的寄出 3 封重複信」。
  2. 失敗必須有 DLQ——沒有它，事件驅動 = 「更安靜的吞掉 bug」。
  3. 重試必須有 jitter——沒有它，退避 = 「集體重試雪崩」。

滿足這三條，RPA pipeline 就從「脆弱的腳本」進化成「可觀測、可恢復、可擴展」的事件驅動系統。
