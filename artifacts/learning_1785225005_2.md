+## 三、架構決策 (為什麼這樣設計)
+
+### 為什麼 systemd service + timer 而不是 daemon / cron?
+
+| 考量 | systemd timer | cron | long-running daemon |
+|---|---|---|---|
+| 失敗紀錄 | `journalctl -u` 內建 | mail spool 常被忽略 | 要自己寫 |
+| 啟動時序控制 | `OnBootSec=` 可延後開機 race | crond 開機就跑 | N/A |
+| 動態調度 | `OnUnitActiveSec` 自帶 jitter | crontab 編輯 + reload | N/A |
+| 資源隔離 | `ProtectSystem=`, `ReadWritePaths=` | 完全沒 | 自己搞 namespace |
+| 失敗處理 | `Persistent=true` 重啟補跑 | 失敗就消失 | 自己 try/except |
+
+**選 systemd timer**。N100 是現代 Ubuntu/Debian,systemd 是預設 init。
+`Type=oneshot` + `Restart=no` — sysmon 是週期性任務,不是 daemon。
+失敗時 systemd 會在 journal 留紀錄 + OnUnitActiveSec 60 秒後自動重跑 (Persistent)。
+
+### 為什麼是 one-shot 而不是 streaming?
+
+監控不該佔資源。one-shot 跑 < 0.5 秒 (CPU sample 200ms + awk/df/journal),
+每分鐘一次 → 0.8% CPU time 平均負載,可忽略。
+streaming daemon 反而要管 state 同步、log rotation、signal handling —
+複雜度高 10 倍但沒解決什麼真問題。
+
+### 為什麼 cooldown 在 script 而不是 systemd?
+
+systemd `OnFailure=` 只能 hook 「service exit nonzero」,**不能分辨是 cpu 還是 mem 觸發**,
+也無法對「同一個 metric」做 5 分鐘內只 alert 一次的 debounce。
+
+把 cooldown 邏輯寫在 script 內、用 `/var/lib/sysmon/alert_state` 存
+`<key>=<last_unix_ts>` 行,簡單且可調 (改 `ALERT_COOLDOWN_SEC` 即可)。
+
+### 為什麼不接 webhook / Telegram / Discord?
+
+預設「只能本機看」是 feature 不是 bug:
+- 不需要 token = 不會洩 token (USER.md / MEMORY 對 secrets 一再強調)
+- 對 N100 來說,先看到 journal 有 `[ALERT[CRIT]]` 就夠了
+- 擴充點清楚標記在 `alert()` 函式 + README,使用者想接時只需 5 行 curl
