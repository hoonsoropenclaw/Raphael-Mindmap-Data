核心設計決策：
1. 為什麼用 useReducer 而非多個 useState
   - 跨欄位的「表單資料」+「當前步驟」+「驗證錯誤」+「歷史紀錄」是同一個 transaction
   - 任何單一動作（改欄位、換步驟、undo）都該以一致的方式更新所有切片
   - 集中 action types 讓「該不該觸發副作用」一目了然

2. 為什麼 history/future 用 snapshot 而非 command pattern
   - snapshot 簡單直觀，且資料量小（< 5 KB）
   - command pattern 適合大型編輯器（Figma/VSCode），這個場景過度設計

3. 為什麼 debounce auto-save 而非每次 dispatch 都存
   - 每 keystroke 都寫 localStorage 浪費 IO
   - 400ms debounce 在「使用者停頓」瞬間存，使用者無感

4. 為什麼 theme 是 preferences 的子欄位
   - 主題是 user preference 而非環境狀態，屬於表單資料合理
   - 同時也是 wizard 的「示範」：偏好設定會即時生效

5. 為什麼 reducer 自己處理驗證
   - 在 NEXT_STEP / SUBMIT action 內驗證 = 規則集中
   - 個別欄位 onChange 時「只清錯」不重驗，避免使用者打到一半被打斷

6. 為什麼 setField 寫成 section+field 雙 key
   - 一個 action type 涵蓋 4 個 section × N 個欄位
   - 對齊 Redux Toolkit 的 createSlice 風格；type 數量爆炸的問題用 discriminated union 處理
