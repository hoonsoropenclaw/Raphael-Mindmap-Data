+Design notes
+------------

+  We keep a module-level ``aiosqlite.Connection`` and serialize writes with
+  the connection's built-in lock. SQLite handles thousands of writes per
+  second for this kind of workload — no need for an external broker.

+  the lock, which matters when our tests hammer the DB.

+"""Sliding-window rate limiter.
+
+Why sliding-window (not token-bucket or fixed-window)?
+-----------------------------------------------------
+* Fixed-window has a burst-at-boundary problem: a client can fire 2*N
+  requests across the window edge and slip through.
+* Token-bucket smooths over time but doesn't enforce hard ceilings
+  within a "second" — the test suite wants ``<= 3 per second``.
+* Sliding window over a 1-second grain, persisted to SQLite, gives a
+  strict ceiling and survives restarts. Same machinery trivially scales
+  to per-minute or per-hour grains via the helper.
+
+Concretely
+----------
+``check_and_record(identity, limit=N, window_seconds=1)`` does:
+
+1. Compute the *floor* of the current wall clock at the requested grain.
+   For 1-second grain that's ``now.replace(microsecond=0)``.
+2. Try to insert a row ``(identity, floor)`` into ``rate_limit_buckets``.
+3. If the row already existed, increment the in-memory hit count.
+4. The current second's count = (existing rows in this and the previous
+   grain-floors within ``window_seconds``). For the common 1s case we
+   only ever look at the current grain — the prior floor is past the
+   window boundary.
+
+Wait — for a true sliding window of width W over discrete grain G, the
+hit count sums the current floor + up to ``W/G - 1`` prior floors. We
+materialise each floor as a row so we can count later entries cheaply.
+"""

+

+from dataclasses import dataclass

+from . import db as _db

+    allowed: bool
+    remaining: int
+    retry_after_seconds: float

+    """ISO-8601 string of the *floor* of ``now`` at the given grain."""
+    if window_seconds >= 60 and window_seconds % 60 == 0:
+        minute_floor = now.replace(second=0, microsecond=0)
+        # advance by `window_seconds` minutes and key as that minute
+        # plus the number of minutes into the window so distinct windows
+        # don't collide.
+        minutes_into_window = (minute_floor.minute // (window_seconds // 60))
+        keyed = minute_floor.replace(minute=minutes_into_window * (window_seconds // 60))
+        return keyed.isoformat() + f"/{window_seconds}s"

+    return now.replace(microsecond=0).isoformat() + f"/{window_seconds}s"

+## 設計決策與取捨
+
+### 1. Rate limit 為何選「滑動視窗」
+- **固定視窗**有邊界突刺問題（boundary burst）：5 req/秒其實能塞 10 req。
+- **Token bucket** 不適合「嚴格 ceiling」語意（測試要的是 `≤ N per second`）。
+- **滑動視窗**用每筆 hit 為一個 row，COUNT(*) 範圍是「過去 W 秒」。
+  - 嚴格 N / W，沒有 boundary 突刺。
+  - 持久化在 SQLite，重啟後 bucket 仍延續。
+  - 用 `(identity, window_key)` 複合 index，O(log N) 每次查詢。
+  - **代價**：表會隨流量成長 → 加了 `prune()` 刪 1 小時以上 row。
+
+### 2. 並發安全用 asyncio.Lock
+aiosqlite 只序列化「一個 statement」，但兩個 coroutine 的 SELECT + INSERT 對可以交錯。
+→ 在 db 模組內建 module-level `asyncio.Lock`，覆蓋 SELECT 計數 + INSERT 這對 critical section。
+測試 `test_concurrent_writes_remain_safe` 用 10 個並行打、確保允許數 ≤ limit。
+
+### 3. Rate limit 與 DB 共用一個 SQLite
+- 部署簡單：不引外部 broker（Redis 之類）。
+- 缺點：limiter 吃一點 DB 頻寬；單實例夠用，叢集需抽到外部。文件已說明。
+
+### 4. Rate limit identity 用 client IP
+- 簡單、貼近真實部署。
+- 已知限制：經反向代理會誤判 → production 需解析 `X-Forwarded-For`（文件中標註）。
+
+### 5. 環境變數在每次請求重讀
+不用 `RATE_LIMIT` module 常數，用函式 `_rate_limit()` 每次 call 取 env：

+
+### 6. 限流覆蓋全部業務端點（含 `/health`）
