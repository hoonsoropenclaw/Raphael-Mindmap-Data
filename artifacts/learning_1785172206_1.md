+function loadInitial() {

+# Kanban React 元件 — 實作思路
+
+## 1. 為什麼選 Kanban(不選 Todo)
+
+題目要求「複雜狀態管理」,而 Todo(checkbox 列表)只需 `useState` 配陣列 filter,
+很快就觸天花板。Kanban 天生帶有:
+
+- **多維狀態**:欄位歸屬 + 欄內排序 + 拖拉暫態
+- **CRUD + 排序**:cards/columns 的不可變更新
+- **衍生資料**:篩選後分組、標籤字典
+- **跨元件通訊**:拖拉時 source → over → drop 的多角色協作
+
+這就逼出「狀態管理」真正的設計選擇——而不只是單純 setState。
+
+## 2. 狀態管理架構(為什麼這樣切)
+
+```
+                ┌────────────────────┐
+                │  kanbanReducer     │  純函數,所有 action → 新 state
+                │  (initialState)    │  易測試、可重放、可序列化
+                └─────────┬──────────┘
+                          │ state + dispatch
+                          ▼
+                ┌────────────────────┐
+                │  KanbanProvider    │  Context + 持久化 + 衍生資料
+                │  (localStorage)    │  useMemo 算 grouped/filtered
+                └─────────┬──────────┘
+                          │ value = {state, dispatch, grouped,
+                          │          filteredGrouped, dragApi, ...}
+                          ▼
+    ┌──────────┬──────────┬───────────┬──────────────┐
+    ▼          ▼          ▼           ▼              ▼
+  Header    FilterBar   Board     Modal(編輯)    AddCardForm
+```
+
+### 為什麼不用 Redux/Zustand?
+
+- Redux:太重,boilerplate 比專案本身大
+- Zustand:好,但對於這個規模(單頁、無路由、無 server sync),

+  }
+  // 3. 插入新位置(不可變 splice)
+  const result = [...without]
+  result.splice(targetIndex, 0, { ...card, columnId: toColumnId })
+  return result
