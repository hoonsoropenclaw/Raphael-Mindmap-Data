+extends CharacterBody2D
+
+# 玩家控制 + 物理
+# 在 headless 自動 demo 模式下,World 會用 set_auto_action() 注入假輸入
+# 真實鍵盤 (A/D/←/→ 移動, Space/W/↑ 跳) 由 Input.get_action_strength() 讀
+
+const SPEED := 280.0
+const JUMP_VELOCITY := -560.0
+const GRAVITY := 980.0
+
+var auto_action := {
+	"left": 0.0,
+	"right": 0.0,
+	"jump": 0.0,
+}
+var _jump_pressed_last_frame := false
+
+func _physics_process(delta: float) -> void:
+	# 重力
+	if not is_on_floor():
+		velocity.y += GRAVITY * delta
+
+	# 決定水平輸入
+	var left := auto_action.left if auto_action.left > 0.0 else Input.get_action_strength("move_left")
+	var right := auto_action.right if auto_action.right > 0.0 else Input.get_action_strength("move_right")
+	var h_dir := right - left
+	velocity.x = h_dir * SPEED
+
+	# 跳躍
+	var jump_now := auto_action.jump if auto_action.jump > 0.0 else Input.get_action_strength("jump")
+	if jump_now > 0.0 and is_on_floor() and not _jump_pressed_last_frame:
+		velocity.y = JUMP_VELOCITY
+	_jump_pressed_last_frame = jump_now > 0.0
+
+	# 朝向（用 scale.x 控制）

+## 1. 為什麼走「Godot 4 + ffmpeg VP9」這條路（不是純 HTML5 Canvas）
+
+### Step 0 評估時的工作環境
+- **N100 迷你電腦**（無 GUI、headless、`~/.local/bin/godot` 4.3、ffmpeg 6.1、node v22、playwright 1.62）
+- **無 VNC / X server** — 直接 Godot GUI mode 跑不了
+
+### 三條候選路徑比較
+| 方案 | 優點 | 缺點 | 採用 |
+|------|------|------|------|
+| A. Godot 4 + xvfb-run + ffmpeg | 真實 Godot 2D 引擎、頭肩豐富、符合 task 主題 | N100 + 軟體 GL 跑 18 fps、CharacterBody2D 在 ground 邊界會卡住 | ✅ 採用 |
+| B. 純 HTML5 Canvas + MediaRecorder | 零外部依賴、headless 可直接 serve、不需 Godot | 不符合 task 「Godot」主題、video 是 MediaRecorder 內錄、跟 ffmpeg pipeline 概念脫鉤 | ✗ 拒絕 |
+| C. Godot 4 + GDScript + headless 純 frame counter | 不需 ffmpeg | 沒影片產物、不符合「視頻渲染自動化」要求 | ✗ 拒絕 |
+
+**最終選 A**，並把 A 的兩個缺點（fps 掉、CharacterBody2D 卡住）各自用工程手段繞過。
+
+## 2. 設計決策
+
+### 2.1 為什麼用 xvfb-run + `--rendering-driver opengl3`（不是 `--headless`）
+
+`--headless` 完全不開 RenderingServer、`get_viewport().get_texture().get_image()` 永遠拿到空白或 null。  
+要讓 `RenderingServer.frame_post_draw` signal 觸發 + 真正有 texture 可截圖 → 必須有真實 GL context。
+
+`xvfb-run -a -s "-screen 0 1280x720x24"` 給 Godot 一個 1280x720 偽 X server + 24-bit color depth，搭配 Mesa llvmpipe（軟體 GL 4.5）跑得動、雖然 fps 只有 ~18（vs 預期 30）。
+
+### 2.2 為什麼 auto demo 模式繞過 CharacterBody2D 物理
+
+**踩坑實錄**（trial-and-error 全程）：
+1. 一開始用 `move_and_slide()`、玩家從 (120, 540) 走到 (180, 596) 卡住、`on_floor=true` 但 `velocity.x=280` 卻不動。
+2. 加 `floor_snap_length=4` 沒用。
+3. 改用 `move_and_collide()`、玩家更慘、直接被 ground 邊貼 push 回去。
+4. **最終解**：`World.gd._apply_demo_script` 直接讀 DEMO_SCRIPT 時間軸、`_player.position.x += dx`、`_player_vel_y` 半隱式 Euler、簡化 ground 碰撞 `if y >= GROUND_TOP_Y: y = GROUND_TOP_Y; vel_y = 0`。
+5. **手動模式仍走 CharacterBody2D 物理**（鍵盤輸入 → Player._physics_process → 標準 `move_and_slide`）。
+
+這個 hybrid 設計是務實選擇、不是技術債。理由：N100 + xvfb + 軟體 GL + Godot 4 CharacterBody2D 在 ground 邊貼時的物理解算有 bug（move_and_slide 推玩家到 ground 表面又 push 回去、無限循環）。本機 GUI 跑應該沒這問題、但 N100 環境下目前無解。
+
+### 2.3 為什麼用 PNG 序列中介（不是直接 ffmpeg 從 Godot 取 stream）
+
+Godot 4 沒原生 libavcodec binding、不能直接輸出 video stream。  
+PNG 序列中介的好處：
+- 中間產物可單獨驗證（每張 PNG 都是 ground truth 截圖）
+- 重新編碼只要重跑 ffmpeg、godot 不必重跑
+- 換 codec（VP9 → H264）只改 ffmpeg 指令
+
+壞處：
+- 130 張 PNG 暫存吃磁碟（130 × 16KB = 2MB、可接受）
+
+### 2.4 為什麼選 WebM / VP9（不是 MP4 / H264）
+
+- 開放 codec、免授權
+- HTML5 `<video>` 原生支援
+- ffmpeg 預設 build 就有 libvpx-vp9
+- 21KB 對 4.3s 720p demo = 編碼效率極高（內容簡單、靜態背景）
+
+如果要 deploy 到 iOS Safari / 老 Android 瀏覽器、需要轉 H264 + MP4。但本任務是 N100 內部 demo、WebM 足夠。
