+## 2. 本輪 2 個新功能的設計取捨
+
+### 2.1 Prometheus `/metrics` endpoint
+
+**選擇 ThreadingHTTPServer + daemon thread**：
+- `http.server` 是標準庫，唯一新 import
+- `daemon=True` 確保主程式退出時 thread 不會卡住
+- `ThreadingHTTPServer` 處理並發 scrape（Prometheus 偶爾會同時拉多個 target）
+
+**為什麼綁 127.0.0.1 而不是 0.0.0.0**：
+- alert 的內容含 key/severity/host，可能透露 hostname 與資源拓樸
+- 對外暴露需要認證（basic auth / mTLS），超出本監控腳本職責
+- 解法：放 nginx reverse proxy 在前面做 auth（README §Security note 註明）
+
+**為什麼 /metrics 跟 daemon run_forever 同一 process**：
+- 共享同一個 `State` 物件，cooldown map 自然反映在 metric
+- 不需要 IPC、socket、shared memory
+- 唯一成本：HTTP handler 在 main thread 之外跑，要 lock（已加 `threading.Lock`）
+
+**為什麼 13 個 metrics 而不是只暴露 5 個資源指標**：
+- `linux_monitor_up` — 給 Prometheus 偵測 daemon 是否還活著
+- `linux_monitor_last_scrape_timestamp_seconds` — 給 alerting rule 算 staleness
+- `linux_monitor_disk_percent{mount=...}` — 一定要 label 化，否則每個 mount 就要開一條 metric（違反 Prometheus 最佳實踐）
+- `linux_monitor_cooldown_seconds{key=...}` — SRE 想要追蹤「過去 1 小時有幾個 key 觸發 alert」就能直接從這拉
+
+### 2.2 ntfy.sh notifier
+
+**選擇 plain-text POST 到 `https://ntfy.sh/<topic>`**：

+- 私有 server 也能用（`MONITOR_NTFY_BASE_URL` 改指 private）
