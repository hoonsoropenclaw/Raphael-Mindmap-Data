+# Telegram Weather Bot
+
+A small Python 3 Telegram bot that receives a city name, queries the public wttr.in weather API, and replies with current conditions.
+
+## Features
+
+- Telegram `getUpdates` long-polling; no public domain or webhook certificate required.
+- Plain text city queries, `/detail <city>`, `/start`, and `/help`.
+- Python standard library only: no `requests`, `python-telegram-bot`, or package install.
+- Three defensive layers: optional user allowlist, per-user cooldown, and Unicode sanitization.
+- Safe `.env` parsing: `run.sh` reads only approved keys and never executes the file as shell code.
+- Graceful SIGINT/SIGTERM shutdown and absolute Telegram update cursor handling.
+
+## Quick start
+
+```bash
+cp .env.example .env
+chmod 600 .env
+# edit .env and set TELEGRAM_BOT_TOKEN from @BotFather
+./run.sh --check
+./run.sh --tests       # unit + bot-unit + live weather smoke tests
+./run.sh               # foreground bot; Ctrl-C stops cleanly
+```
+
+`TELEGRAM_ALLOWED_USERS` is recommended. Set it to a comma-separated list of Telegram numeric user IDs. If it is empty, the bot is public.
+
+## Usage
+
+```text
+Taipei
+/detail Tokyo
+/help
+```
+
+The weather module can also run independently:
+
+```bash
+python3 wttr_weather.py Taipei
+```
+

+# Implementation Review — Telegram Weather Bot
+
+## 1. Task and delivered scope
+
+The deliverable is a runnable Telegram bot that accepts text, treats the text as a city name, calls a weather API, and replies with the result. The implementation is isolated in this project directory and uses Python 3.12's standard library only.
+
+Implemented commands:
+
+- Plain text: current one-line weather report.
+- `/detail <city>`: multi-line report.
+- `/start` and `/help`: static usage help.
+
+## 2. Architecture decisions
+
+### 2.1 Standard library first
+
+The message-to-API-to-reply path only needs HTTP, JSON, URL encoding, signal handling, and typed result objects. Therefore:
+
+- `urllib.request` handles HTTP.
+- `json` parses Telegram and wttr.in responses.
+- `dataclasses` represent weather success/error results.
+- No third-party package or virtual environment is required.
+
+This follows the absorbed production pattern from `stdlib-production-tool-pattern.md` and avoids framework overhead for a small three-endpoint pipeline.
+
+### 2.2 Module separation
+
+`wttr_weather.py` has no Telegram dependency. It owns input normalization, wttr.in access, fail-loud response parsing, Unicode sanitization, and CLI formatting. `telegram_bot.py` owns Telegram HTTP calls, message routing, polling, rate limiting, and process shutdown. The dependency direction is one-way: Telegram glue imports the weather module; the weather module does not import the bot.
+
+### 2.3 Long polling
+
+The bot uses Telegram `getUpdates` with a 30-second long-poll timeout. This is appropriate for a headless machine without a public HTTPS endpoint. The update cursor is assigned as `update_id + 1`, not incremented by one from a local counter, so gaps in Telegram update IDs cannot cause duplicate processing.
+
+### 2.4 Three defensive layers
+
+1. Allowlist: `TELEGRAM_ALLOWED_USERS` can restrict access to known numeric user IDs.
+2. Rate limit: each user receives a three-second cooldown. A failed `sendMessage` rolls back exactly that request's reservation, so a transient failure does not consume the retry slot.
+3. Sanitization: response text is normalized to remove lone Unicode surrogates before sending to Telegram and capped below Telegram's 4096-character limit.
+
+### 2.5 Secret and transport handling
+
+`run.sh` deliberately does not `source .env`. It parses only three approved keys, rejects symlinks, and rejects group/world-readable env files. The Telegram token is required from the environment but is never printed. `_http_post` converts transport/API failures into sanitized exceptions that do not contain the token-bearing URL. Plain HTTP is rejected except for loopback test servers.
+
+## 3. Senior Architect feedback absorbed
+
+The discovered feedback files concern other projects, but their reusable guidance was applied:
+
+- Prefer the simplest sufficient architecture instead of adding a framework.
+- Fail loudly on malformed external data rather than silently inventing defaults.
+- Prove behavior with focused tests and live verification instead of relying on a code-only review.
+- Keep security properties explicit and testable, especially file permissions and secret handling.
+
+The existing weather-bot reference project was used as a known-good baseline, then improved in this project with safer env loading, sanitized Telegram transport errors, retry-safe rate limiting, and dedicated bot tests.
+
+## 4. Failure handling
+
+- Empty city input returns a typed `EMPTY_INPUT` error.
+- HTTP 404 becomes a user-facing not-found error.
+- Network and timeout failures become a bounded, readable weather error.
+- Malformed JSON or missing core fields becomes `BAD_JSON`; the parser does not silently fabricate weather values.
+- Telegram polling transport failures are retried after a short delay; expected long-poll timeouts are treated as normal.
+- A failed outgoing reply leaves the update cursor unchanged, allowing at-least-once retry. Unauthorized or malformed updates are acknowledged to avoid an endless queue.
+
+## 5. Verification plan
+
+The verification chain is intentionally layered:
+
+1. `python3 -m py_compile wttr_weather.py telegram_bot.py test_unit.py test_bot.py test_smoke.py`

+5. `./run.sh --check` using a temporary mode-600 env file — launcher parsing and configuration check.
+6. SHA256 fingerprints of delivered source and documentation files.
