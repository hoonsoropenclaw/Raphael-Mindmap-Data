+## 2. 設計決策(為什麼這樣做)
+
+### 2.1 多源監控(為什麼三個源不是一個)
+- **`/proc/stat`, `/proc/meminfo`, `/proc/loadavg`** — 資源指標的事實來源,0 依賴、永遠可讀
+- **`shutil.disk_usage`** — 磁碟使用率,直接走 statfs syscall
+- **`journalctl`** — 服務日誌首選(systemd 環境)
+- **`/var/log/syslog`** — 降級路徑,當 journalctl 沒裝或沒權限時自動 fallback
+
+選擇 journalctl + syslog 雙路徑的原因:很多生產環境 journald 沒啟用、或非 root 用戶讀不到 journal,這時還是要能監控。
+
+### 2.2 雙級閾值(warning / critical)
+實務上單級閾值會造成「告警疲勞」:使用者對所有 alert 麻木後,真正嚴重的也會被忽略。所以:
+- `warning`:值得注意、可能很快惡化
+- `critical`:立即處理
+
+CPU/Mem/Disk/Load 都用浮點百分比,Log 用計數(10 分鐘窗口內的紀錄數)。
+
+### 2.3 指紋去重 + 冷卻(為什麼必要)
+同一個問題在短時間內反覆告警 = 告警疲勞 = 監控失去意義。
+- `fingerprint` = `source|key|host`,例如 `cpu_percent|hoonsoropenclaw`
+- `cooldown_seconds` = 預設 300 秒,5 分鐘內同指紋只發一次
+- 從測試驗證:watch 跑 18 秒 + jsonl 只有 1 行 → 去重機制真的在擋
+
+### 2.4 多通道通知
+- **console** — 人讀,ANSI 顏色 icon(只在 tty 才上色)
+- **log file (JSONL)** — 機器讀 audit log,append-only
+- **webhook** — 對接 Slack/Discord/PagerDuty,urllib 內建不需 requests
+- **systemd-cat** — 走 systemd journal,跟其他系統日誌整合
+
+JSON 模式刻意**不**輸出 console(避免 ANSI 污染 machine-readable stream)。
+
+### 2.5 Fail-safe(監控腳本 crash 比沒監控更糟)
+- 頂層 `except Exception` 包整個 `main()`,確保腳本永遠 exit(失敗也是明確失敗,不是 silent crash)
+- journalctl 沒權限 → 自動降級 syslog(不回 error)
+- 磁碟路徑不存在 → 跳過該路徑(不 crash)
+- CPU/Mem 讀不到 → 發一條 warning alert 而不是 raise
+- 設定檔不存在/壞掉 → 用 DEFAULT_CONFIG 跑,stderr 警告
+
+### 2.6 模式設計
+- `--once` — cron 友善(預設)
