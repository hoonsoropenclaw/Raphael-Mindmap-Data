+# syswatch — Linux 系統日誌與資源監控腳本
+
+純 stdlib、零外部依賴的 Linux 系統監控工具。當系統資源（CPU / Memory / Disk /
+Load）或日誌錯誤率超過閾值時輸出 WARN / CRIT 警告，可選地送到 webhook。
+
+提供兩個實作：
+
+| 檔案 | 語言 | 適用情境 |
+|------|------|---------|
+| `syswatch.sh` | bash | shell + cron 環境、快速整合 |
+| `syswatch.py` | Python 3 | 複雜解析、需要 JSON 結構、需要長期維護 |
+
+兩者輸出格式對齊、exit code 一致，**可以任選一個使用**。
+
+## 功能
+
+1. **系統資源**
+   - CPU 使用率（兩次讀 `/proc/stat` 相減）
+   - Memory 使用率（`/proc/meminfo`）
+   - Disk 使用率（所有掛載點、排除 tmpfs / devtmpfs / overlay / squashfs / snap）
+   - Load Average（`/proc/loadavg`，對 CPU 數量取倍數）
+
+2. **日誌錯誤掃描**
+   - `/var/log/syslog`、`messages`、`auth.log`、`kern.log`（可自訂）
+   - `journalctl -b -1 -p err`
+   - `dmesg --level=err,crit,alert,emerg`
+   - 關鍵字：error / fail / panic / segfault / oops / out of memory / NFS 斷線
+     （可自訂 regex）
+
+3. **服務存活檢查**（可選）
+   - `systemctl is-active <unit>` 對一組 systemd unit 檢查
+
+4. **警告出口**
+   - 終端機人類可讀輸出（彩色）
+   - 純 JSON（`--json`，給監控系統吃）
+   - Webhook 送出（`--webhook https://...`，預設 dry-run）
+
+## 快速開始
+
+```bash
+# 給執行權限
+chmod +x syswatch.sh syswatch.py
+
+# 用預設閾值跑一次（dry-run）
+./syswatch.sh
+
+# 或 Python 版本
+./syswatch.py
+
+# 載自訂閾值
+./syswatch.sh --config syswatch.conf
+
+# 真的送出 webhook
+./syswatch.sh --webhook https://hooks.example.com/alerts --no-dry-run
+
+# JSON 輸出（給監控系統吃）
+./syswatch.sh --json | jq .
+
+# 加 systemd 服務監控
+./syswatch.sh --services "sshd cron nginx"
+```

+## 3. 涵蓋的監控維度
+
+### 資源監控（CRIT/WARN 兩級閾值）
+- **CPU**：兩次讀 `/proc/stat` 相減算使用率（採樣 0.5s）
+- **Memory**：`/proc/meminfo` 算 MemTotal - MemAvailable
+- **Disk**：掃所有掛載點、排除 tmpfs/devtmpfs/overlay/squashfs/snap
+- **Load**：對 CPU 數量取倍數（1x = warn、2x = crit）
+
+### 日誌錯誤掃描
+- **檔案掃描**：`/var/log/{syslog,messages,auth.log,kern.log}`（可自訂）
+  - 取檔尾 N 行（`LOG_LINES`，預設 200）
+  - regex 關鍵字（預設 `error|fail|panic|segfault|oops|oom|nfs: server.*not responding`）
+- **journalctl**：`journalctl -b -1 -p err`
+- **dmesg**：`dmesg --level=err,crit,alert,emerg`（需 root 或 `dmesg_restrict=0`）
+
+### 服務存活檢查
+- **systemd units**：`systemctl is-active <unit>`（使用者傳入空白分隔清單）
+
+### 警告出口
+- **人類可讀**：彩色終端機輸出（OK 綠 / WARN 黃 / CRIT 紅）
+- **JSON**：`--json` flag、stdout 純 JSON（給監控系統吃）
+- **Webhook**：`--webhook URL --no-dry-run`（預設 dry-run 避免誤發）

+## 4. 設計決策（L3 抽象層）
+
+### 為什麼同時提供 bash + Python 兩個版本？
+- **bash**：零依賴、內建 cron 友善、debug 簡單（`bash -x`）、serverless/容器冷啟動友好
+- **Python**：JSON 結構穩定、邏輯分層（Collector/Scanner/Watcher/Reporter）、易擴展、易測試
+- 兩者**介面對齊**（flag、exit code、輸出格式），使用者任選一個
+
+### 為什麼 exit code 用 0/1/2 而不是 0/non-0？
+- 0 = OK、1 = WARN、2 = CRIT
+- 配合 cron job 失敗偵測（mail / PagerDuty webhook 可分別處理）
+- 外部監控系統（Prometheus pushgateway、Datadog agent）可以直接 `||` 分流
+
+### 為什麼 daemon 化交給 cron？
+- 一個工具只做一件事：syswatch 跑一次完整檢查
+- 排程責任在外部（cron / systemd timer / k8s CronJob）
+- 易於整合到現有的監控生態
+- 避免雙重時序（cron 排程 + 程式內 sleep loop 容易 race condition）
+
+### 為什麼不用 psutil / 第三方套件？
+- 純 stdlib 確保部署在 minimal container / scratch image / 緊急救援 ISO 都能用
+- 系統監控工具**自己依賴過多東西 = 失去獨立性**
+- `/proc` 介面比 psutil API 更穩定（psutil 也是包 `/proc`）
+
+### 為什麼 dry-run 預設開啟？
+- 預設 dry-run 避免「第一次跑就誤發一堆 webhook」
+- 使用者必須明確 `--no-dry-run` 才會送出
+- 學習門檻低（先看到會發什麼、再決定是否打開）
