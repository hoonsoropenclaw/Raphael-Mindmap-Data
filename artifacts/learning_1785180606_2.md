+# Telegram Weather Bot
+
+A minimal Telegram bot that listens for text messages and replies with the current weather for the requested city. Built on `python-telegram-bot` 22.x + Open-Meteo (no API key required).
+
+## Quick start
+
+```bash
+# 1. Install dependencies (Python 3.10+)
+pip install -r requirements.txt
+
+# 2. Get a bot token from @BotFather on Telegram, then export it
+export TELEGRAM_BOT_TOKEN="123456789:AA..."
+
+# 3. Run
+python3 weather_bot.py
+```
+
+Now open Telegram, find your bot, and send it any city name (`台北`, `Tokyo`, `New York`, etc.).
+
+## Features
+
+- **Zero API key**: Open-Meteo is free for non-commercial use, no signup.
+- **Built-in city dictionary**: 30+ common cities (中文 + English) hit a local lookup so the first reply is instant.
+- **Geocoding fallback**: Unknown cities fall through to Open-Meteo's geocoding API.
+- **Markdown rendering**: Replies in `Markdown` with emoji weather codes.
+- **Graceful degradation**: 城市找不到 / API timeout / Markdown parse error all have user-facing messages and no crashes.
+- **Live typing indicator**: Sends `ChatAction.TYPING` while fetching, so the user knows the bot is working.
+
+## Commands
+
+| Command  | Behavior |
+| -------- | -------- |
+| `/start` | Welcome message with usage |
+| `/help`  | Same as /start |
+| `/ping`  | Returns `pong 🏓` (liveness check) |
+
+Any other text message is treated as a city query.
+
+## Architecture
+
+```
+Telegram  ──►  python-telegram-bot  ──►  handler.text
+                                          │
+                                          ├─►  CITY_PRESETS  (本地查表，0 latency)
+                                          │
+                                          └─►  Open-Meteo /v1/search (geocoding)
+                                                      │
+                                                      ▼
+                                          Open-Meteo /v1/forecast
+                                                      │
+                                                      ▼
+                                          Markdown formatted reply
+```
+
+Single-file design (`weather_bot.py`) — every dependency is stdlib + `python-telegram-bot` + `aiohttp`. The whole program is ~330 lines including the city dictionary and comment header.
+
+## Production hardening (deliberately omitted)
+
+These are intentionally out of scope for a minimal demo. If you want to deploy this for real:
+
+1. **Webhook mode** instead of polling. PTB has `app.run_webhook()`; works with any reverse proxy.
+2. **Rate limiting** per user. Telegram limit is 30 msg/sec globally, 1 msg/sec per chat for normal bots.
+3. **Persistent geocoding cache** — wrap `geocode_city` in a small SQLite/redis layer so repeat queries don't hit the API.
+4. **Structured logging** — `python-json-logger` instead of stdlib `logging`.
+5. **Graceful shutdown** — trap `SIGTERM` and call `app.shutdown()` so in-flight requests finish.
+6. **Health endpoint** — a tiny `aiohttp` server on `/health` for k8s/ALB probes.
+
+## Environment
+
+- Python 3.10+ (tested on 3.12.3)
+- python-telegram-bot 22.x
+- aiohttp 3.9+
+

+# Implementation Notes — Telegram Weather Bot
+
+> Drop-in for `feedback.md`. Read this before picking up the next iteration.
+
+## 1. Task received
+
+> 撰寫一個 Telegram 機器人腳本，能接收文字並呼叫天氣 API 查詢天氣回傳。
+
+Translation: a Telegram bot that listens for text input and replies with the weather for the queried city.
+
+## 2. Design choices
+
+### 2.1 Bot framework: `python-telegram-bot` 22.x (async PTB)
+
+Why PTB and not raw `aiohttp` + the Telegram Bot API?
+
+- **Community / docs**: PTB is the de-facto Python Telegram wrapper, with 22+ major releases; v22 dropped support for Python 3.7 and went fully async.
+- **Update dispatcher for free**: filter-based routing (`filters.TEXT & ~filters.COMMAND`) means we don't hand-roll dispatch logic.
+- **Built-in error handlers**: `application.add_error_handler()` lets us log PTB-internal exceptions without crashing the polling loop.
+- **Cost**: 0 LOC to wire up. Same package also pulls `aiohttp` through its dependency tree, so we get a single HTTP client to share.
+
+### 2.2 Weather API: Open-Meteo (forecast + geocoding)
+
+Why Open-Meteo and not OpenWeatherMap / AccuWeather?
+
+- **No API key**: zero signup, no key in env, no quota dashboard. Lower barrier to first run.
+- **Generous free tier**: 10k requests/day, non-commercial OK.
+- **Simple JSON**: flat current-observation schema — no auth header, no signed URL, no XML.
+- **WMO weather codes**: standardized numeric codes (0–99) we map to emoji descriptions once.
+- **Edge**: it's free but explicitly non-commercial. If this ever needs to monetize, swap to OpenWeatherMap (same call shape, just add `&appid=...`).
+
+We use **two** endpoints:
+- `https://geocoding-api.open-meteo.com/v1/search` — city name → lat/lon
+- `https://api.open-meteo.com/v1/forecast` — lat/lon → current weather
+
+### 2.3 City resolution: lookup table + geocoding fallback
+
+There's a 30-entry built-in dictionary for common Chinese and English cities (台北/東京/New York/...). Why bother?
+
+- **Latency**: preset hit = 0ms. Geocoding hit = 80–250ms.
+- **Robustness**: geocoding returns the *first* match with `count=1`, which for "Springfield" or "Paris" might pick the wrong one. Presets pin the exact city.
+- **CJK subtlety**: `normalize_city()` keeps Chinese case-intact but lowercases English ("Tokyo" → "tokyo", "台北" → "台北"). Index lookup is O(1).
+
+For unknown cities we fall through to the geocoding API. If *that* misses, we return a friendly "找不到這個城市" message rather than 500'ing.
+
+### 2.4 Single-file architecture
+
+`weather_bot.py` is ~330 lines including the city table and weather-code map. Intentionally not split into `bot.py` / `weather.py` / `cities.py`. Why?
+
+- **It's a demo.** Three modules for a Telegram bot that does one thing is over-engineering.
+- **Transitive cost**: every new file is a new import path, a new place to look. Single file = one read to understand the whole bot.
+- **Refactor trigger**: when the code exceeds ~500 lines, *or* if we add a second bot (e.g. a currency bot that shares the city table), then split. Premature splitting is its own kind of debt.
+
+### 2.5 Error handling strategy
+
+Three layers, each with a user-facing message:
+
+1. **Input validation** (`handle_text`): empty text is ignored (Telegram shouldn't send it, but defensive); raw text > 100 chars rejected with a friendly message.
+2. **City resolution** (`resolve_city`/`geocode_city`): unknown city → "找不到「<x>」這個城市" with a hint.
+3. **Weather fetch** (`fetch_weather`): HTTP timeout / non-200 / network error → "天氣服務目前不穩，請稍後再試", with the coordinates echoed so we can debug.
+4. **Markdown parse failure**: `parse_mode=ParseMode.MARKDOWN` can throw if the API returns weird characters. We catch and re-send as plain text.
+
+`on_error` is the final catch-all that logs any unhandled exception so we don't silently swallow PTB-internal bugs.
+
+### 2.6 UX touches
+
+- **ChatAction.TYPING** during the fetch — gives the bot a "human" feel, important when the API is slow.
+- **Markdown formatting** with emoji in the reply — weather is sensory data, emoji add more info density than text.
+- **/ping**, **/start**, **/help** commands standard — anyone who's used a Telegram bot knows what to do.
+- **drop_pending_updates=True** on `run_polling()` — if the bot restarts, don't replay every queued message (avoids spamming the user with stale "hi" replies).
