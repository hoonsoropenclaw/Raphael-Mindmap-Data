+## 實作思路
+
+### 1. 為什麼不用 GitHub API?
+GitHub **沒有**提供官方 trending API。雖然有 `gh-trending` 之類的第三方套件,
+但多一層依賴就是多一個未來會壞掉的點。所以我選擇:
+- 直接 `requests.get('https://github.com/trending?since=daily&language=python')`
+- 用 `BeautifulSoup` parse 回來的 HTML
+
+這樣**只依賴兩個套件**,而且對 GitHub 改 DOM 的應變方式很直接——
+只要把 CSS selector 改一下就好。
+
+### 2. 為什麼不用 git history scrape / RSS / 第三方 API?
+- **GitHub 沒有 RSS for trending**(只有頻道 / repo release 有)
+- 第三方套件(`gh-trending`)通常是 wrapper 套 API,自己寫反而更靈活
+- 直接抓 HTML 是「最貼近資料源」的做法,任何 wrapper 套件壞了都不影響我們
+
+### 3. 架構(3 層分離)
+
+```
+fetch_trending_html()   ←  I/O 層:打 HTTP 拿字串
+        ↓
+parse_trending()        ←  解析層:HTML → TrendingRepo list
+        ↓
+render_markdown()       ←  呈現層:TrendingRepo list → markdown 字串
+        ↓
+main()                  ←  CLI 入口 + argparse + 寫檔
+```
+
+每一層都可以獨立測試。`test_fetch_trending.py` 就是這樣設計的——
+不碰網路,給 fixture HTML 直接驗證 parse / render 邏輯。
+
+### 4. 資料模型
+
+用 `@dataclass TrendingRepo` 當載體:
+
+```python
+@dataclass
+class TrendingRepo:
+    rank: int
+    full_name: str          # owner/repo
+    url: str
+    description: str
+    language: str
+    total_stars: int
+    period_stars: int       # daily/weekly/monthly 內新增
+    forks: int
+    contributors: list[str] # 預留欄位,目前頁面沒抓
+```
+
+`to_markdown_row()` 是唯一碰字串格式的地方——
+如果未來要改成 CSV / HTML 表格,只加一個 method 就行,不會污染資料層。
+
+### 5. 解析策略(對 GitHub DOM 改動的容錯)
+
+我在 `parse_trending()` 用了「主選擇器 + 退化選擇器」兩層:
+
+```python
+articles = soup.select("article.Box-row")
+if not articles:
+    articles = soup.find_all("article")  # 退化:只要是 <article> 都算
+```
