+# GraphQL 微服務架構 — Federation 範例
+
+> 學習任務:基於 GraphQL 的微服務架構設計與實現
+> 工作目錄:`/home/hoonsoropenclaw/.hermes/projects/learning_1785313810_1/graphql-microservices/`
+
+## 架構圖
+
+```
+                ┌────────────────────────┐
+   Client ────▶ │  Gateway :4000         │
+   (HTML/JS)    │  (Apollo Gateway —     │
+                │   聚合 supergraph SDL, │
+                │   處理 entity resolve) │
+                └─────────┬──────────────┘
+                          │ RemoteGraphQLDataSource
+            ┌─────────────┴─────────────┐
+            ▼                           ▼
+   ┌──────────────────┐        ┌──────────────────┐
+   │ users    :4001   │        │ products :4002   │
+   │ subgraph(User)   │        │ subgraph(Product)│
+   │ type User @key   │        │ type Product @key│
+   └──────────────────┘        └──────────────────┘
+```
+
+每個 subgraph 都是**獨立 Apollo Server**(`@apollo/subgraph`),有自己擁有的資料。
+Gateway 是 **Apollo Gateway**(federation router),不存資料,只:
+1. 啟動時去兩個 subgraph 抓 SDL
+2. 合併成 **supergraph SDL**
+3. 收到 client query → **query planning** → 拆 sub-query 發到對應 subgraph
+4. entity 需要跨服務時(federation key)→ 透過 `RemoteGraphQLDataSource` 做 `__resolveReference`
+
+## 為什麼用 Federation 而不是 schema stitching
+
+| 比較         | Federation                                  | Schema Stitching           |
+|--------------|---------------------------------------------|----------------------------|
+| 標準化       | Apollo 官方規範,有 `@key` / `@link` 指令   | 各框架自訂                 |
+| query plan   | gateway 自己 plan,可跨服務 join            | 需要手寫 delegation        |
+| 維運         | subgraph 各自部署,gateway 只路由           | 通常 1 個 process          |
+| 反應速度     | 新版 Apollo Router 已 Rust 重寫(超快)      | 仍在 JS                    |

+## 2. 為什麼選 Apollo Federation v2 而不是 schema stitching
+- **Apollo Federation 是業界標準**(`@key` / `@link` / `@apollo/gateway`),有官方 router(Rust 版,效能好)
+- Schema stitching 各框架自訂、需手寫 delegation → 不符合「微服務架構設計」的工業強度
+- Apollo v2 federation 比 v1 更乾淨(`@link` 取代散落的 schema directive)
+
+## 3. 為什麼用 in-memory 假資料
+- 任務範圍是「架構設計與實現」,**不是**「真實資料庫整合」
+- in-memory 讓 E2E 5 個 case 都能在 7 秒內驗完
+- README 已說明「換 DB」的下一步方向(SQLAlchemy / Mongoose / Drizzle 皆可,各自加到 subgraph resolver)
+
+## 4. 實作過程踩過的 4 個真實雷
+(這些是 L2 試誤,**值得寫成 trial-and-error skill**,但 USER.md 規範要使用者明確說才存,先留在 IMPL_NOTES)
+
+### 雷 1:`@apollo/server/plugin/disabled` 是 ESM-only
+`require('@apollo/server/plugin/disabled')` 在 CJS 環境會炸。
+**If** 用 Apollo Server v4 + CommonJS **Then** 不要 import usage-reporting plugin,**直接不放就好**(本地開發不會打 Apollo Studio)。
+
+### 雷 2:Apollo Federation v2 的 `@link` 必須用 federation v2.x spec
+不要寫 `@link(url: ".../link/v1.0") @link(url: ".../key/v1.0")` — 兩個 link 衝突,composition 失敗。
+**正確寫法**:`@link(url: "https://specs.apollo.dev/federation/v2.5", import: ["@key"])`
+
+### 雷 3:跨服務 type reference 必須先 stub
+users-service 引用 `Product` type,但 Product 主定義在 products-service。
+**If** users SDL 有 `favoriteProducts: [Product!]!` 卻沒定義 `type Product` **Then** schema build 失敗。
+**正確**:在 users SDL 也寫 `type Product @key(fields: "id") { id: ID! }`(stub),只放 federation key,不放其他 field(那由 owner subgraph 提供)。
+
+### 雷 4:同 field 不能在多個 subgraph 定義(`Non-shareable field`)
+不能 users 和 products 兩個 subgraph 都解 `User.favoriteProducts` — federation 會抱怨資料來源不明。
+**正確做法**:entity field 只在「擁有資料」的那個 subgraph 定義,其他 subgraph 只放 key-only stub。
+也就是說 `User.favoriteProducts` 的 resolver 只能在 products-service 實作(users 端只放 `User { id }` stub)。
