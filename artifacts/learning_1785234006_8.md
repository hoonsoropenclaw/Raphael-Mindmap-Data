+**目標**：產出一個 production-grade 的 Linux 系統監控腳本，能跑在 N100 / 任何一般 Linux box、能在 cron / systemd timer 排程、能在告警時讓監控系統（或人類）收到訊號。
+
+**非目標**（明確排除）：
+- 不是 Prometheus exporter（那要做成 web server、可能要裝 prometheus_client，範圍會爆）
+- 不是 distributed agent（只跑單機、不需遠端協調）
+- 不是 ML-based 異常偵測（rule-based 即可，ML 的 false positive 風險在 on-call 場景很痛）
+
+**邊界**：腳本自己跑檢查、自己印結果，**不做通知**（不寄信、不打 webhook）。通知交給外部——cron 接到 exit≠0 自己寄 mail、或包一層 systemd service 把 stderr 轉到 Slack webhook。**理由**：通知策略每個 team 不同，塞進來就是無謂的 scope creep；退出碼是業界標準介面，留給上層組合比較乾淨。
+

+## 2. 關鍵設計決策
+
+### 2.1 純 stdlib，零外部依賴
+
+**決策**：不引入 psutil、requests、watchdog。
+
+**理由**：
+- 可離線部署（air-gapped 環境、container 沒有 pip）
+- 沒有版本衝突、沒有 supply chain 風險
+- Python 3 內建的 `os`、`shutil`、`subprocess`、`pathlib` 已足夠覆蓋所有採集需求
+
+**代價**：
+- CPU% 要自己讀 `/proc/stat` 算差值（psutil 會直接給）
+- 磁碟用量要自己用 `shutil.disk_usage`（psutil 一行）
+- 沒 OS-specific API（macOS `psutil.cpu_percent()` 用不同演算法），但本腳本只鎖 Linux 所以無差
+
+**驗證**：Python 3.12.3 上 `python3 -m py_compile` 通過、無 import 警告。
+
+### 2.2 三層嚴重度（OK / WARN / CRIT）而非二元（OK / 壞掉）
+
+**決策**：每個 metric 都回 OK / WARN / CRIT，整體 worst_status 取 max。
+
+**理由**：
+- on-call engineer 看到「CPU 80% 警報」跟「CPU 95% 警報」的反應時間不同
+- 「目前是 WARN 但接近 CRIT 邊界」是有用的早期訊號
+- 三層剛好對應退出碼 0/1（1 把 WARN/CRIT 都合在一起）、加上 2 = 腳本錯誤
+
+**10% buffer 規則**（實作在 `Metric.status()`）：
+- value < threshold → OK
+- threshold ≤ value < threshold × 1.10 → WARN（10% buffer 帶）
+- value ≥ threshold × 1.10 → CRIT
+
+**理由**：避免「87% 超過 85% 閾值 → 直接 CRIT」的假警報；給操作員時間回應。
+
+### 2.3 退出碼語義
+
+| 退出碼 | 意義 | 給 cron / 監控的暗示 |
+|--------|------|----------------------|
+| 0 | 全部 OK | 一切正常，不通知 |
+| 1 | 有 WARN 或 CRIT | 有事要處理（不管是 WARN 還是 CRIT 都回 1，因為 cron 只看得懂 0/非 0） |
+| 2 | 腳本本身錯誤 | config 壞掉、JSON 解析失敗、缺必要檔案 |
+
+**為什麼 0/1/2**：POSIX 標準（0 = 成功、1 = 一般錯誤、2 = misuse）。cron 預設只看「非 0 就寄信」，所以 1 跟 2 都會觸發 mail、但 2 通常代表腳本壞了、需要人工介入（mail 標題會帶 `[daemon] status=WARN exit=1` 之類 prefix 提示）。
+
+### 2.4 子命令分離（check / daemon / journal / syslog / test）
+
+**決策**：五個獨立子命令，不互相耦合。
+
+**理由**：
+- `--check` 適合 cron（每 5 分鐘一次、跑完就結束）
+- `--daemon` 適合長期跑的守護進程
+- `--journal` / `--syslog` 適合 debugging 階段單獨 inspect 某個來源
+- `--test` 讓 CI 能在沒有 root / 沒有真實高負載的環境驗證邏輯正確
+
+**沒有 --alert 子命令**：理由見 §1，通知策略不屬於本腳本範圍。
+
+### 2.5 self-test fixture（不需 root、不需真實高負載）
+
+**決策**：`--test` 子命令用 monkey-patch 把採集函式替換成 deterministic stub，跑全 pipeline。
