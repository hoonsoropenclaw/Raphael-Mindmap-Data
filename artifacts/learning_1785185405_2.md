+# GitHub Trending Markdown Exporter — Implementation Review
+
+## Objective
+
+Provide a repeatable, dependency-free script that fetches GitHub Trending repositories and emits a Markdown table containing repository links, descriptions, languages, stars, forks, and daily star counts.
+
+## Architecture decisions
+
+1. HTTP client: Python standard-library `urllib.request`.
+   - No third-party installation is required.
+   - Requests include a descriptive User-Agent and HTML Accept header.
+   - HTTP 429/5xx and transient network failures use bounded exponential retries; non-retryable HTTP errors fail explicitly.
+
+2. Parser: a record-oriented `html.parser.HTMLParser`.
+   - The parser treats `article.Box-row` as a repository boundary.
+   - It extracts semantic signals such as `itemprop="programmingLanguage"` and repository links ending in `/stargazers` or `/network/members`.
+   - Void HTML elements (`img`, `br`, `meta`, etc.) do not increase nesting depth. This prevents an image inside one card from absorbing later cards.
+   - `<br>` text is normalized to whitespace, and Markdown pipe characters are escaped only at rendering time.
+
+3. Output: Markdown rendered from a typed `Repository` dataclass.
+   - The output includes a UTC generation timestamp and source URL.
+   - Missing fields are represented as an em dash instead of producing malformed columns.
+   - Repository rows are renumbered after `--limit` is applied.
+
+4. File safety: concurrency-safe atomic replacement.
+   - Output is written to a uniquely named temporary file in the destination directory.
+   - The file is flushed and `fsync`-ed before `os.replace`.
+   - Exceptions remove the temporary file, preserving the previous successful output.
+
+5. Testability: offline HTML input path.
+   - `--input` allows deterministic parser tests without GitHub network access.
+   - `test_github_trending.py` covers void-tag handling, multiple cards, field extraction, limits/ranks, URL validation, Markdown rendering, and atomic output cleanup.
+
+## Review feedback absorbed
+
+The available Senior Architect feedback was for a previous FastAPI/Todo project. Its reusable L3 guidance was applied here:
+
+- Be sensitive to low-level behavior: explicit parser depth rules, typed normalized records, bounded retry behavior, and atomic file semantics.
+- Prefer infrastructure-level safety instead of relying on a happy-path invocation: unique temporary files, `fsync`, and cleanup on failure.
+- Validate with executable tests, not only a code inspection.
