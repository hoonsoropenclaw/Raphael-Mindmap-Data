+# Linux Monitor
+
+Dependency-free Linux resource and log monitor for cron or systemd timers.
+
+## Checks
+
+- CPU usage from `/proc/stat`
+- Memory usage from `/proc/meminfo` using `MemAvailable`
+- Disk usage using `shutil.disk_usage`
+- 1-minute load average
+- Recent journald errors via `journalctl`; fallback to `/var/log/syslog` or `/var/log/messages`
+- Threshold warnings written to stdout as JSON and to a local alert log
+- Optional JSON webhook delivery via `MONITOR_WEBHOOK_URL`
+- Single-instance lock using `fcntl.flock`
+- Atomic state file and cooldown suppression
+
+No third-party Python package is required.
+
+## Quick start
+
+```bash
+cd /home/hoonsoropenclaw/.hermes/projects/learning_1785182405_14/linux-monitor
+python3 monitor.py --dry-run --state-file ./state.json --alert-log ./alerts.log
+```
+
+Exit codes:
+
+- `0`: check completed; alerts may or may not exist
+- `1`: configuration or required-source error
+- `2`: alerts were found when `--fail-on-alert` was supplied
+
+The normal default exit code is `0`, which avoids turning a cron warning into a cron execution failure.
+
+## Configuration
+
+CLI options are suitable for non-secret thresholds. Secret webhook URLs are deliberately accepted only from the environment:
+
+```bash
+export MONITOR_CPU_THRESHOLD=90
+export MONITOR_MEMORY_THRESHOLD=90
+export MONITOR_DISK_THRESHOLD=90
+export MONITOR_LOAD_THRESHOLD=2.0
+export MONITOR_LOG_LOOKBACK_MINUTES=10
+export MONITOR_LOG_WARNING_COUNT=1
+export MONITOR_ALERT_COOLDOWN=300
+export MONITOR_STATE_FILE=/var/lib/linux-monitor/state.json
+export MONITOR_ALERT_LOG=/var/log/linux-monitor.log
+export MONITOR_WEBHOOK_URL='https://example.invalid/monitor-hook'
+python3 monitor.py
+```
+
+Do not place a webhook URL in a crontab command line. Use a root-readable environment file or a systemd credential mechanism with appropriate permissions.
+
+## Cron example
+
+Run every five minutes as a service account with write access to the state and alert-log paths:
+
+```cron
+*/5 * * * * MONITOR_STATE_FILE=/var/lib/linux-monitor/state.json MONITOR_ALERT_LOG=/var/log/linux-monitor.log /usr/local/bin/linux-monitor --fail-on-alert >>/var/log/linux-monitor.stdout 2>&1
+```
+
+Before installing under `/usr/local/bin`, copy `monitor.py` there and make it executable. The project defaults target `/var`, so a non-root test should override both paths into a writable directory.
+
+## Testing
+
+```bash
+python3 -m unittest -v test_monitor.py
+python3 -m py_compile monitor.py test_monitor.py
+python3 monitor.py --dry-run --state-file ./state.json --alert-log ./alerts.log
+```
+
+## Operational limitations
+
+- Metrics are sampled once per run; CPU is measured over a 100 ms interval.
+- The cooldown state is local to one host. For multiple hosts, aggregate alerts centrally.
+- Webhook delivery is best-effort and never hides a local warning.
+- `journalctl` output depends on the invoking user's journal permissions.
+- A multi-process lock prevents overlapping runs on one host; it is not a distributed lock.

+## Design
+
+- Python 3 standard library only, so the monitor can be copied to a minimal Linux host without package installation.
+- Resource readers are isolated as small functions and use Linux-native sources (`/proc/stat`, `/proc/meminfo`, `shutil.disk_usage`, and `os.getloadavg`).
+- Log collection prefers `journalctl` with a fixed argument list and a timeout. It falls back to common syslog files when journald is unavailable or inaccessible.
+- Alerts are emitted as JSON on stdout for machine parsing and also appended to a local alert log for durable local evidence.
+- A webhook is optional and is read only from `MONITOR_WEBHOOK_URL`; it is not accepted as a CLI argument, preventing accidental exposure through process listings or shell history.
+- `fcntl.flock` prevents overlapping runs on the same host. Cooldown keys are hashed and persisted in an atomically replaced mode-0600 state file.
+- `--dry-run` exercises collection and local logging without network delivery. `--fail-on-alert` is opt-in because ordinary cron should not report a healthy execution as a scheduler failure merely because it found a warning.
+
+## Verification plan
+
+1. Run the unit suite with `python3 -m unittest -v test_monitor.py`.
+2. Compile both modules with `python3 -m py_compile monitor.py test_monitor.py`.
+3. Run the real monitor in the project directory with writable state/log paths and `--dry-run`.
+4. Inspect the JSON output, alert log, state file permission, and lock behavior.
+
+## Known limitations
+
+- CPU and load thresholds are host-wide and intentionally simple.
+- Journal visibility depends on the executing account's permissions.
+- The in-memory metrics and local cooldown state are not a replacement for a fleet monitoring backend.
+- Webhook failure is reported locally but does not make the monitor crash; this preserves the local alert trail.
