+**交付物**：`monitor.py`（Python 3.12,純標準庫,575 行,可執行）

+
+## 一、為什麼寫成這樣（設計決策）
+
+### 1. 為什麼選 Python（不是 bash script）
+
+- **資料結構需求**：`@dataclass CheckResult` 讓 CPU/Mem/Disk/Journal 每個 check 都是結構化物件,可以序列化為 JSON,方便 cron → Loki / ELK / Prometheus node_exporter textfile collector 二次消費
+- **錯誤容忍**：try/except 比 bash 的 `||` + `set -e` 更精準——journalctl 失敗只 WARN、不整個腳本崩
+- **JSON 解析**：journalctl `--output=json` 每行是獨立 JSON,Python `json.loads` 逐行處理比 `jq` 串接更容錯
+- **不需要 bash 嗎？也寫了**：若改用 bash 會需要 `jq`/`awk`/`sed`,外部依賴更多,部署門檻更高
+
+### 2. 為什麼分四個獨立子函式（get_cpu_info / get_mem_info / get_disk_info / scan_journal）
+
+- 任何一個失敗不影響其他三個（**重要**：journalctl 在 chroot / minimal container 沒裝時不該讓整個監控腳本掛掉）
+- 每個函式可單獨 unit test
+- 加新 check（例如 network、process count）只需要新增一個函式 + 在 `run_checks` 加一筆,不改其他程式
+
+### 3. 為什麼用「雙指標」評估 CPU（usage% + load%）
+
+- CPU usage%（採樣 /proc/stat）是瞬時值,會抖動
+- load average / cores 是趨勢指標,更能反映「系統過載」
+- 兩者取最大值 → **單獨看 usage% 容易誤報（短暫 spike）,單獨看 load 對 idle 系統沒意義**
+
+### 4. 為什麼 journal 預設 `since=15min ago`
+
+- 監控頻率通常 1 分鐘、5 分鐘、15 分鐘一次
+- 15 分鐘是「上一次監控到現在」的合理回顧窗口
+- 想拉長（例如 daily report）→ `--since 24h ago`
+- 不預設 `today` 是因為 journal 會灌爆,效能 + 雜訊都差
+
+### 5. 為什麼「磁碟每個掛載點各一筆」不是「只看 /」
+
+- `/` 看起來 47% 沒事,但 `/var` 或 `/tmp` 滿了照樣炸服務
+- 用 `df -PBG` 自動跳過 `/proc /sys /dev /run /snap /boot/efi` 等虛擬 FS,只關心真實掛載點
+- 每個掛載點獨立判斷 warn/crit → `--disk-warn` 一個閾值就夠,不必為了 `/boot`（2G）跟 `/`（231G）各設一個
+
+### 6. 為什麼三層 log fallback（journalctl → syslog → messages）
+
+- Ubuntu/Debian → `/var/log/syslog`
+- RHEL/CentOS/Alma → `/var/log/messages`
+- Alpine / minimal container → 可能兩個都沒有 → 直接 INFO 跳過（不該假裝有 log）
+
+### 7. 為什麼寫 JSONL 而不只是純文字 log
+
+- 文字 log 給人看、JSONL 給程式消化
+- 同一個檔案 append 兩種格式,grep/sed 處理文字行,`jq`/Python 處理 JSON 行
+- 想接 Loki？`promtail` 直接吃 JSONL；想接 ELK？`filebeat` 解析 JSON 沒問題
+- 想接 Prometheus？`--json` 模式輸出 → 再寫個 `textfile_collector.py` 轉成 `node_exporter` 格式
+
+### 8. 為什麼 exit code 用 0/1/2 而不是 0/non-zero
+
+- **0 = 全綠,1 = 有 WARN,2 = 有 CRIT**
+- cron / systemd 可以分別處理：`OnFailure=` 只在 CRIT 時觸發通知、WARNING 只寫 log
+- Nagios/Icinga 風格的 service check 預期三段 exit code,直接相容
