+# Reflection — Telegram 天氣機器人
+
+## 1. 任務理解
+
+需求很簡潔：「**撰寫一個 Telegram 機器人腳本，能接收文字並呼叫天氣 API 查詢天氣回傳**」。
+
+從「能用」到「production-ready」之間有一大段距離，所以我把任務拆成三個層次：
+
+1. **最小可執行 (MVP)**: bot 起來、收訊息、回訊息
+2. **可靠 (reliable)**: 錯誤處理、API 額度、安全性
+3. **可維護 (maintainable)**: 模組分離、測試、文件
+
+最終交付的版本走完了這三層。
+
+---
+
+## 2. 技術選型
+
+### 為什麼是 `python-telegram-bot` v22（async）而不是 `python-telegram-bot` v13 或 polling 自幹？
+
+- **系統已經裝了 v22**（確認過 `pip3 list`）→ 不要裝舊版
+- v22 是純 asyncio 設計，跟 `aiohttp` / `httpx` 生態一致
+- 自幹 `requests.get(BOT_API_URL/longPoll)` 也可以，但 PTB 處理了：
+  - backpressure（網路斷線重連）
+  - conflict（多實體搶同一個 token）
+  - signal handling（SIGTERM / SIGINT）
+  - update queue 的 thread-safety
+
+結論：**站在巨人肩膀上**，只寫商業邏輯。
+
+### 為什麼是 OpenWeatherMap？
+
+- 免費 tier 60 calls/min、1M calls/month → 對個人 / 小群組綽綽有餘
+- `lang=zh_tw` 參數直接回傳中文天氣描述（測過 `多雲`、`小雨` 等）
+- 不需要註冊信用卡
+- API 文件清楚、endpoint 穩定
+
+替代選項：wttr.in（不需要 API key、純 GET）、WeatherAPI（有免費 tier 但 1M calls/月要申請）。
+取捨：wttr.in 太玩具化、WeatherAPI 額度審查慢。OWM 是社群主流 → **選主流**。
+
+---
+
+## 3. 架構決策
+
+### 3.1 三檔案分離（config / api / bot）
+
+```
+config.py     → 環境變數載入（無業務邏輯）
+weather_api.py → HTTP 客戶端 + 錯誤階層（無 Telegram 依賴）
+bot.py        → Telegram handlers（用 weather_api）
+```
+
+**為什麼這樣切？**
+- `weather_api.py` **完全不知道 Telegram 的存在** → 可以獨立 unit test、可以給 CLI / web 重用
+- `bot.py` **不知道 HTTP 細節** → 如果改用 aiohttp，只要改 `weather_api.py`
+- `config.py` **不知道任何業務** → 換框架只要 import 它
+
+這是經典的「分層 + 單一職責」原則。檔案數量 3 個、每個 < 300 行，沒有過度設計。
+
+### 3.2 錯誤階層
+
+```python
+WeatherAPIError (root)
+├── CityNotFoundError    → 404
+├── AuthError            → 401
+├── RateLimitError       → 429
+└── TransientError       → 5xx / 網路問題
+```
+
+為什麼不用單一 `WeatherAPIError(message)` 就好？

+| AuthError | `⚙️ 機器人設定有問題`（不洩漏 key） | **ERROR** |
+| RateLimitError | `⏳ 稍後再試` | WARNING |
