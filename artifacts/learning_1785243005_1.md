+## 1. 需求拆解（先想清楚再寫 code）
+
+「GitHub Trending Repositories」這個詞至少有兩種詮釋：
+
+| 詮釋 | 來源 | 優點 | 缺點 |
+|---|---|---|---|
+| **A. 官方 trending 頁面** | `https://github.com/trending?since=daily` | 官方定義的「trending」,帶「stars today/week/month」權威欄位 | HTML scraping,結構可能改 |
+| **B. Search API** | `GET /search/repositories?q=created:>=7d&sort=stars` | 結構化 JSON、不被反爬、可自訂條件 | 「trending」≠「新建+高星」,會漏老但爆紅的專案 |
+
+**結論：兩個都實作**,預設優先 A,失敗 fallback 到 B,並提供 `--also-api` 把 B 的結果作為附錄。
+
+---
+
+## 2. 架構決策（為何這樣拆）
+
+### 2.1 單檔、純 stdlib + bs4
+
+- 環境已驗證 `requests + bs4 ok`（用 `python3 -c "import requests,bs4"` 確認）
+- 不引入新第三方依賴 = 零安裝風險 = 符合「第一次就做對」
+- 單檔易於 `cron` 整合、易於 git review
+
+### 2.2 三段式：fetch → render → main
+
+```
+main() ──► fetch_trending_html()      # 主來源
+       └► fetch_search_api()          # fallback / 附錄
+       └► render_markdown()           # 純函式,易測
+       └► write_file()                # 副作用只在邊界
+```
+
+**好處**：`render_markdown` 是純函式,可單元測試、不需要 mock。
+**原則**：副作用（網路 I/O、檔案寫入）集中在函式邊界,業務邏輯保持純淨。
+
+### 2.3 自動 fallback 而非 panic
+
+不直接 raise 給使用者,而是 `errors: list[str]` 收集,最後：
+- 兩來源都失敗 → exit 1 + 把 errors 全列在 stderr
+- HTML 失敗但 API 成功 → exit 0 + stderr 一行 warn,stdout 主流程照常
+
+理由：trending 頁面偶爾 502、Search API 偶爾 rate limit,使用者不該為「來源暫時抖動」付費。
+

+## 3. 細節陷阱（debug 中實際遇到的）
+
+### 3.1 markdown table 的 `|` 會破壞表格
+
+repo 的 description 經常含 `|`（例：`TypeScript-to-Native Compiler | ...`）。
+**修法**：寫入 cell 前 `.replace("|", "\\|")`。
+
+### 3.2 「stars today」的位置在 HTML 不同角落
+
+GitHub trending HTML 的「N stars today」存在於兩種 selector：
+- 舊版：`span.d-inline-block.float-sm-right`
+- 新版（2024 後）：`span.color-fg-muted`
+
+**修法**：兩個都試,只要含 "star" 字就採用。並加 try 容忍結構變化。
+
+### 3.3 `--limit 0` 會讓 requests 送 `per_page=0`
+
+GitHub API 不接受 `per_page=0`。
+**修法**：CLI 入口先驗 `1 <= limit <= 100`,提早 exit code 2。
+
+### 3.4 附錄模式會撞到重複 H1
