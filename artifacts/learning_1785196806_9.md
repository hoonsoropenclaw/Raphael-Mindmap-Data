+### B.1 單檔 Bash 而非 Python — 為什麼？
+
+| 選項 | 優點 | 缺點 | 結論 |
+|------|------|------|------|
+| **Bash 單檔** | 零安裝、可直接 cron / systemd 跑、log 監控路徑原生 | 浮點數依賴 awk | ✅ **選這個** |
+| Python 多檔 | 模組化、易測試 | 需 venv、有 PE 668 障礙、cron 環境 hooks 缺失 | ✗ |
+| Go 單檔 binary | 效能高、單檔可執行 | 需編譯鏈、維運要重 build | ✗ |
+
+**理由**：本任務是「維運腳本」，Bash 是 POSIX 標準、所有 Linux 系統內建、排程（cron / systemd timer）直接掛。Python 對此 over-engineered。
+
+### B.2 三大檢查維度
+
+1. **資源檢查**（即時資料）
+   - CPU load (15-min) per core — 比總核心數更能反映瓶頸
+   - 記憶體使用率
+   - 磁碟使用率（**全部** filesystems，排除 tmpfs/overlay/squashfs）
+   - inode 使用率（**常被忽略** — 沒有空 inode = 寫不進新檔）
+   - Swap 使用率
+
+2. **日誌檢查**（24h 滑動視窗）
+   - 認證失敗次數（sshd Failed password / Invalid user / max auth attempts）
+   - OOM kills（kernel OOM killer 觸發記錄）
+   - Critical/emergency 等級日誌（kernel panic / BUG / segfault / Call Trace）
+
+3. **分級輸出**
+   - `OK` / `WARN` / `CRIT` 三級
+   - 退出代碼：`0` (OK) / `1` (warning) / `2` (critical) / `3` (config error)
+
+### B.3 為什麼 OOM/Critical 預設 = 1 / 5？
+
+- **OOM kill**：任何 OOM 都是 production 環境的嚴重事件 → 預設 ≥ 1 就是 critical
+- **Critical log**：kernel panic / 硬體錯誤很罕見，預設 5 條/24h 給一點 buffer 容忍 normal noise
+- **Disk 95%**：腳本內硬編碼 `crit if > 95%`（即使 env 閾值是 80），因為「磁碟滿」= 寫不進去 = 服務一定死
