+# Telegram Weather Bot
+
+A small Telegram bot that receives a location as text, queries wttr.in, and replies with current weather. It uses only Python's standard library, so there is no `pip install` step.
+
+## Features
+
+- Telegram Bot API long polling (`getUpdates`)
+- Text location lookup through wttr.in JSON API
+- `/start` and `/help` commands
+- Optional Telegram user allowlist
+- Per-user cooldown to reduce API abuse
+- Private atomic offset state file
+- Single-instance `fcntl.flock` lock
+- Graceful SIGINT/SIGTERM shutdown
+- Secrets read from environment variables, never CLI arguments or source code
+
+## Requirements
+
+- Python 3.10+
+- A Telegram bot token from BotFather
+- Network access to `api.telegram.org` and `wttr.in`
+
+## Setup
+
+```bash
+cd /home/hoonsoropenclaw/.hermes/projects/learning_1785168006_2
+cp .env.example .env
+# Edit .env and set TELEGRAM_BOT_TOKEN. Do not commit .env.
+chmod 600 .env
+./run.sh
+```
+
+`run.sh` loads `.env` without printing it, then starts the bot. You can also export variables in the shell and run `python3 telegram_bot.py` directly.
+
+## Configuration
+
+| Variable | Default | Purpose |
+|---|---:|---|
+| `TELEGRAM_BOT_TOKEN` | required | BotFather token |
+| `TELEGRAM_ALLOWED_USERS` | empty | Comma-separated numeric Telegram user IDs; empty means allow all users |
+| `WEATHER_TIMEOUT_SECONDS` | `15` | wttr.in request timeout |

+| `USER_COOLDOWN_SECONDS` | `3` | Minimum seconds between weather lookups per user |
+| `BOT_STATE_FILE` | `./bot_state.json` | Offset state file; written with mode `0600` |

+# Implementation Notes
+
+## Goal
+
+Build a Telegram bot that accepts a text location, calls a weather API, and sends a concise weather reply.
+
+## Architecture decisions
+
+1. Standard Library only: `urllib.request` handles HTTPS, `json` handles payloads, `signal` handles shutdown, `dataclasses` models weather data, and `fcntl.flock` prevents duplicate instances. The request is a small message-to-API-to-reply flow, so a framework would add dependency and operational overhead without improving the core behavior.
+2. Long polling instead of webhooks: this works on a headless machine without a public HTTPS endpoint or certificate. Telegram's `getUpdates` timeout is bounded and retried after transient network errors.
+3. Separate weather and Telegram modules: `weather_api.py` is independently testable and CLI-capable; `telegram_bot.py` owns Telegram routing, polling, authorization, rate limiting, persistence, and shutdown.
+4. wttr.in JSON endpoint: it is free and requires no weather API key. The bot requests JSON and translates common condition strings locally because the API's `lang` parameter does not reliably translate JSON fields.
+
+## Security and reliability controls absorbed from Senior Architect feedback
+
+- Secrets are read only from `TELEGRAM_BOT_TOKEN` in the environment; no token CLI argument exists and no token is written to source files.
+- `TELEGRAM_ALLOWED_USERS` provides an optional numeric allowlist. Empty means intentionally public; production operators should set it for a private bot.
+- Weather locations are trimmed, limited to 100 characters, and rejected if empty. Telegram text is not treated as HTML or shell input.
+- Per-user cooldown limits repeated weather calls and reduces API abuse.
+- Telegram update offset is persisted atomically to a private `0600` JSON file. The next process resumes after the last successfully processed update.
+- `fcntl.flock` provides a single-instance lock, preventing two polling loops from racing over updates and state.
+- SIGINT/SIGTERM set a shutdown flag; the bounded polling request exits naturally and the process releases the lock.
+- External errors are logged server-side without exposing the bot token or raw upstream response to Telegram users.
+
+## Verification plan
+
+- Unit tests mock Telegram and weather HTTP calls, covering URL encoding, JSON parsing, translation, input validation, authorization, cooldown, state persistence, and API error handling.
+- `py_compile` checks syntax for all Python files.
+- No live token or external network is required for the automated tests.
+
+## Deliberate non-goals
+
+- No webhook server, database, job queue, or third-party Telegram framework.
+- No location geocoding database; wttr.in accepts the text location directly.
+- No forecast conversation flow; the first version answers current conditions only.
+
+## Operational limitation
+
+The offset is saved after each update handler returns. If the process is terminated during a handler, Telegram may redeliver that update after restart; the handler should therefore remain safe to repeat. The weather query is read-only, so duplicate delivery is harmless.
