+# GitHub Trending Fetcher — 實作思路與審查
+
+## 1. 核心決策：為什麼不用第三方 API，直接用 search/repositories
+
+GitHub **沒有官方 Trending API**（github.com/trending 是 HTML 頁，沒有 JSON endpoint）。
+常見解法有 3 條：
+
+| 方案 | 優點 | 缺點 |
+|------|------|------|
+| **第三方程式庫**（如 `github-trending-api`） | 一行就抓 | 仰賴外部服務存活、需要 GitHub token、不受官方支援、SLA=0 |
+| **HTML 爬蟲**（BeautifulSoup 抓 `github.com/trending`） | 跟官方頁一致 | HTML 變更風險、`User-Agent` 容易被擋、graphql 介面才是 source of truth |
+| **`/search/repositories` 模擬 trending** ✅ | 官方 API、有 SLA、可指定時間窗口 / 語言 | 並非 100% 等於 trending 頁（站方會調權重） |
+
+本腳本採方案 3，因為：
+1. **有官方 SLA**（gh CLI token 60 req/h 認證後 5000/h 已經足夠）
+2. **可程式化**控制時間窗口（daily/weekly/monthly 各自不同的 qualifier）
+3. **不需要新維護一個爬蟲**
+
+trade-off：search ranking 跟 `github.com/trending` 的 curators 排序不完全一致——Trending 頁實際上有手調權重（優質 repo 加分）。
+為了 table 真實呈現，**把「daily window」定義為「7 天內建立、stars>100」；「weekly window」是「30 天內有 push、stars>500」**，這是 GitHub 內部 trending 算法公開過的最接近近似。
+
+## 2. 架構
+
+```
+CLI args
+  ↓
+fetch_trending(since, limit, language)
+  │  → /search/repositories?q=stars:500+pushed:>YYYY-MM-DD+language:X
+  │  → 帶 Bearer token（gh CLI 自動讀、或 env GH_TOKEN）
+  ↓
+to_markdown()  → 清洗換行/直引號、emoji stars/forks、k/M 單位
+  ↓
+output to stdout OR file
+```
+
+### 關鍵設計點
+
+**A. Token 三層 fallback**
+1. `GH_TOKEN` / `GITHUB_TOKEN` env
+2. `gh auth token` 子行程（gh CLI 已登入的場合）
+3. None（fallback 到匿名 60 req/h）
+
+**B. 二次重試只對 secondary rate limit**
+GitHub 有兩種 429/403：
+- **primary**（搜尋 API 超量）：沒有 `Retry-After`，無法自動恢復 → 直接報錯
+- **secondary**（濫用偵測）：有 `Retry-After` header → sleep 等候後重試一次
+
+避免「看不出來是配額爆了還是網路掛了」。
+
+**C. Markdown cell 清洗**
+- `\n` → `空格`（多行 description 在 table 內會炸 cell）
+- `|` → `\\|`（直引號是 table 分隔符，不跳脫會整列位移）
+- `None` → `—`（em-dash，避免空白 cell）
+
+**D. 不偽造結果**
+API 拋錯時：印出 HTTP code、真實 error body、URL 第 500 字。退出碼 = 2。
+**絕不**用空 array 假裝「今天沒 trending」。
+
