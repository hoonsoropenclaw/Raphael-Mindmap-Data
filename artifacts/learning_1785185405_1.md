+# GitHub Trending Scraper
+
+抓取 [github.com/trending](https://github.com/trending) 並輸出為 markdown 表格。
+
+零依賴外部 API token — 用 `requests` + `BeautifulSoup` 解析公開頁面 HTML。
+沒有 GitHub OAuth、沒有 GraphQL rate limit、沒有 gh CLI 需求。
+
+## Quick Start
+
+```bash
+# 1. 直接從 src/ 跑（推薦,免安裝）
+cd src && python3 -m github_trending --help
+
+# 2. 抓每日 trending (25 個 repo),輸出到 stdout
+python3 -m github_trending
+
+# 3. 抓 Python 本週 trending,寫入檔案
+python3 -m github_trending --since weekly --language python --output python-weekly.md
+
+# 4. 限定前 10 名
+python3 -m github_trending --limit 10
+```
+
+## CLI 選項
+
+| 選項 | 預設 | 說明 |
+|------|------|------|
+| `--since` | `daily` | 時間範圍:`daily` / `weekly` / `monthly` |
+| `--language` | (全部) | 語言 slug,例如 `python` / `rust` / `go` |
+| `--limit` | `25` | 最多收幾個 repo (GitHub trending page 最多 25) |
+| `--output`, `-o` | stdout | 寫入 markdown 檔案路徑 |
+| `--user-agent` | Chrome | 自訂 User-Agent header |
+| `--timeout` | `30` | HTTP timeout (秒) |
+| `--verbose`, `-v` | off | Debug logging |
+

+## 1. 架構決策
+
+### 1.1 為什麼 scrape HTML,不用 GitHub REST API?
+
+| 方案 | 優點 | 缺點 | 本案選 |
+|------|------|------|--------|
+| **scrape github.com/trending** | 公開頁、無 token、無 rate limit | HTML 改版需維護 | ✅ |
+| REST API `/search/repositories` | 結構化 JSON、官方支援 | 需 OAuth、5000 req/h 嚴格上限、sort=stars 的 daily 沒 native endpoint | ❌ |
+| gh CLI `gh search repos` | 本機已裝 | 一樣需 sort hack、且 data 是 search engine 不是真 trending | ❌ |
+
+**關鍵洞察**：GitHub trending page 是 HTML 而非 API,但好處是:
+- 完全匿名可抓（curl 即可）
+- 已經過 GitHub 的 trending 算法篩選（vs API 要自己 sort）
+- 支援 daily/weekly/monthly + language 雙維度 query string
+
+### 1.2 為什麼純函式分離 I/O?
+
+```
+fetch_trending_page() → str (HTML)
+    ↓
+parse_trending(html) → list[TrendingRepo]      ← Pure, easy to test
+    ↓
+render_markdown(repos, ...) → str             ← Pure, easy to test
+    ↓
+main() → CLI glue
+```
+
+**Senior Architect feedback 的精神繼承**（對應 `architect_feedback.md`「對底層細節極度敏感的工程紀律」）：
+
+- **「reducer 純函式 → 易測試」的精神**：parser 跟 renderer 都不碰網路 → 35 個 pytest 只花 0.88 秒
+- **「UI-state vs domain-state 分離」的精神**：fetch 是 I/O,parse/render 是 domain logic,分層後**測試不需要 mock network**
+- **「Fail loud」的精神**：HTML 改版時 `parse_trending` 立刻 raise `TrendingFetchError`,而不是 silently 回空列表
+
+### 1.3 為什麼不引入 requests-cache / retry library?
+
+- **沒必要**：GitHub trending 是公開頁面,被擋機率極低（測試 4 次 live fetch 全成功）
+- **避免過度工程**：純 requests + timeout 已涵蓋 99% 場景
+- **If** 未來真的碰到 rate limit **Then** 才加 `urllib3.util.retry.Retry` 作為 transport-level backoff
