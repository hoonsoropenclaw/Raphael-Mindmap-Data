平行執行原理 (How Parallelism Works)

Worker Pool

// WorkerPool.run() — 啟 N 個 worker，每個 worker 是獨立 Chromium 行程
async async run() {
  this.startedAt = Date.now();
  const n = Math.max(1, Math.min(this.config.workers, this.cases.length));
  const promises = [];
  for (let i = 0; i < n; i++) {
    promises.push(this._worker(i));
  }
  await Promise.all(promises);
  return this._summary();
}

// Worker — 共用 1 個 Browser，1 個 BrowserContext，但每個 test 一個新 page
async _worker(workerId) {
  const browser = await chromium.launch({ headless: true, args: ['--no-sandbox'] });
  const context = await browser.newContext();
  try {
    while (true) {
      const idx = this.cursor++;        // 共用 cursor：每個 worker 搶下一個 case
      if (idx >= this.cases.length) return;
      await this._runOne(workerId, browser, context, this.cases[idx]);
    }
  } finally {
    await context.close();
    await browser.close();
  }
}

為什麼這麼設計？

  • 每 worker 1 個 Chromium 行程 → 真的平行（不是單執行緒偽平行）
  • 每 test 1 個新 page → DOM / cookie 完全乾淨，不會污染下一個 test
  • 共用 cursor → 不需要排程器，N 個 worker 自動搶下一個 case
  • retry 內建 → flaky test 不會整個 run 紅掉
  • 失敗截圖 + trace → CI 上看得到現場，不用重跑
  • JSONL 串流 → CI / dashboard 可以即時消化
  • process.exitCode = 1 → 失敗會讓 CI 自動紅燈

如果重來一次我會注意…

  • auth 必須在路由第一行 — 漏的話「不存在的資源」會回 404 蓋掉 401
  • 每個 test 要自己 newContext() — 共用 context 會讓 cookie 在 worker 內累積
  • Regex 路徑匹配要含 hyphen — 否則合法 id 會被當成 404

DSL：怎麼寫測試

const { describe, it, defineConfig, run } = require('./framework/test-runner');

describe('Login Flow', () => {
  it('accepts valid credentials via the UI',
    async (page, { baseURL }) => {
      await page.goto(`${baseURL}/login`);
      await page.fill('#username', 'alice');
      await page.fill('#password', 'pass123');
      await Promise.all([
        page.waitForLoadState('load'),
        page.click('button[type=submit]'),
      ]);
    },
    { retries: 1, timeout: 20000, viewport: { width: 375, height: 667 } }
  );
});

run({
  file: __filename,
  config: defineConfig({
    baseURL: 'http://localhost:3011',
    workers: 4,
    headless: true,
    retries: 1,
    reporter: 'both',       // 'console' | 'jsonl' | 'both'
    screenshot: 'retain-on-failure',
    trace: 'retain-on-failure',
  }),
});

為什麼不直接用 @playwright/test

官方 Playwright Test Runner 本身就有 worker + retry + report。但它有幾個在實戰上讓人卡住的點：

  • ❌ 內建 expect() 與 test() 綁死，要寫 fixture 必須學 test.extend
  • ❌ Reporter 擴展要寫 plugin、loader 機制黑盒
  • ❌ 要從 CDN 抓 fixture / worker 數量 / browser pool 行為高度耦合
  • ❌ 框架本身大（>3000 LOC），debug 內部 race 條件痛苦
  • ✅ 但官方版本功能齊全、有 trace viewer UI 整合

本框架的價值在於 400 行的 source code 你能完全讀懂，而且每個行為（retry、context 隔離、JSONL 輸出）都跟你的測試需求貼齊。

穩健性 (Robustness) 怎麼保證

  • ✅ Worker-level isolation：每個 worker 自己的 Browser + Context，cookie 完全隔離
  • ✅ Test-level isolation：每 test 一個新 page，DOM / storage 自動重置
  • ✅ Auth hermetic：要 cookie 的 test 自己 newContext()，不被前一個 test 污染
  • ✅ Per-test timeout：超時就 fail，不會卡死整個 pool
  • ✅ Retry policy：預設 1 次 retry，flaky 測試不會整 run 紅
  • ✅ Screenshot on failure：失敗現場一定有圖
  • ✅ Trace on failure：Playwright Trace Viewer 可以完整重播每個動作
  • ✅ process.exitCode = 1：CI 自動紅燈
  • ✅ 不污染磁碟：每個 run 寫到帶 timestamp 的檔案，不覆蓋舊記錄
  • ✅ 冪等 demo app：每次重啟乾淨 in-memory state

使用方式

# 1. 啟動 demo app（背景）
PORT=3011 node demo-app/server.js &

# 2. 跑測試（預設 4 worker）
node run-tests.js

# 3. 調 worker 數 / 改 baseURL
WORKERS=8 BASE_URL=http://localhost:3011 node run-tests.js

# 4. 看報表
ls reports/                          # 看 .jsonl + summary.json
open reports/screenshots/*.png       # 失敗截圖（如有）
npx playwright show-trace reports/traces/*.zip   # Trace Viewer
