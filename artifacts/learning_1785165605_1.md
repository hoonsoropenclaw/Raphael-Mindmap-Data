+## 0. 任務原句
+
+> 撰寫一個自動化檢查 Linux 系統日誌與資源的維運腳本，並在超過閾值時發出警告。

+## 1. 為什麼不寫 Nagios / Zabbix plugin？
+
+因為這個需求被問的人**還沒有 monitoring 基建**。先給「能在 5 分鐘內看到東西」的工具比「架完整 monitoring stack」優先。

+
+```
+┌─────────────────────────────────────┐
+│ Alert Channel (cron MAILTO /       │  ← 未來擴充：Slack / PagerDuty
+│ systemd OnFailure)                  │
+└──────────────┬──────────────────────┘

+┌──────────────▼──────────────────────┐

+┌──────────────▼──────────────────────┐

+## 2. 為什麼 stdlib only？
+
+| 解方 | 取捨 |
+|------|------|
+| `psutil` | 多平台、但需要 pip install；不同 distro 上版本不一 |
+| 自己讀 `/proc` | 0 安裝；本來 Linux 上 `/proc` 就是公共契約 |
+| 子行程叫 `df` / `free` | 有 command injection 風險、輸出 parsing 脆弱 |
+
+**結論**：直接讀 `/proc/loadavg`、`/proc/meminfo`、`/proc/self/mountinfo`、`/proc/net/dev`、statvfs。Python stdlib 全 cover。
+
+## 3. 為什麼三層 fallback 寫 baseline？
+
+network errors Δ 是個「絕對值讀沒意義、需要看變化量」的指標。但 baseline 寫到 `/var/lib/linux-monitor/`：
+
+- 跑在 cron 環境：多半 root、有 `/var/lib` 權限 → 第一順位寫
+- 跑在開發環境：non-root、無 `/var/lib` 權限 → fallback 到 `~/.cache/linux-monitor/`
+- 全軍覆沒：fallback 到 cwd 旁的 hidden file
+
+而且**讀和寫走同一順序**——否則 baseline 永遠寫到 A、讀從 B 開始（每次跑都當首次）。
+
+## 4. 為什麼 exit code = 0/1/2（不是 0/1）？
+
+這是我踩過的坑：很多 monitoring 系統只認 0 = OK、non-0 = bad。但「non-0」是一個集合——**「alert」跟「checker 壞掉」是兩件事**。如果腳本因為 bug 死在 runtime exception，rc 也是 1，會跟真實告警混在一起。
+
+```
+0  - all OK
+1  - 有 WARN/CRIT（你看到 mail 就知道要查 host）
+2  - checker 自身 fail（你看到 mail 就知道要查 monitor 自己）
+```
+
+cron MAILTO 兩種都收信但主體內容不同；PagerDuty 可以用 `severity` mapping。
+
+## 5. 為什麼每個 checker 獨立 try/except？
+
+**失敗不傳染**。典型場景：
+
+- `/var/log/btmp` 不存在 → lastb check fail；但其他 7 個 checker 繼續跑
+- `/sys/fs/cgroup` 不可讀（容器環境常見）→ memory 走 MemAvailable；不整支掛
+- 某個 mount 的 statvfs 失敗（被 umount race）→ 跳過、其他 mount 還在
+
+實作：`run_checks()` 用 `for name, fn in CHECKERS`，每個 `try/except`，錯誤寫到 `Report.errors`。即便所有 resource checks 壞了，log scan 跟 failed_login 還是給結果。
+
