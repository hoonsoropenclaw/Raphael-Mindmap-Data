+"""Rate limiter — 滑動視窗 (sliding window) 算法。
+
+設計選擇：
+- 用記憶體內的 dict {client_key: deque[timestamp]}，每 client 一個 FIFO 隊列
+- 視窗大小 RATE_LIMIT_WINDOW_SECONDS、限制 RATE_LIMIT_MAX_REQUESTS 次
+- 純函式化 check_rate_limit(client_key, now=None) → (allowed, retry_after)

+    with _lock:
+        _buckets.clear()

+    client_key: str,

+    now: float | None = None,

+
+    回傳：

+        - allowed=False 表示已超過上限；retry_after 是「再過幾秒」最舊的時間戳會過期
+    """

+        # 沒有 client key 就視為同一人（共用 bucket），不擋

+        return True, 0.0

+## 2. 設計決策（每個都有 why）
+
+### 2.1 為什麼用 sync SQLAlchemy 而非 async
+- FastAPI 的 sync handler 跑在 threadpool，天然處理 concurrency
+- 換 async 要 aiosqlite + 全 async 化，殺雞用牛刀
+- 測試用 `TestClient` 更簡單（httpx ASGI client）
+
+### 2.2 為什麼用「工廠函式」`create_app()` 而非模組頂端 `app = FastAPI()`
+- 測試每個 test function 都想要全新的 app 實例（隔離 lifespan / middleware 狀態）
+- 也可以用 `pytest.fixture(autouse=True)` 重置，但工廠模式更直觀
+- 模組底層仍 `app = create_app()` 讓 uvicorn 直接跑
+
+### 2.3 為什麼 Rate Limit 用「滑動視窗」而非 token bucket
+- 語意直觀：「N 秒內最多 M 次」剛好符合 HTTP 429 的直覺
+- 實作簡單：每 client 一個 `deque[timestamp]`，pop 掉出窗的、append 新的
+- Token bucket 適合「允許突發」的場景；這裡要的是「嚴格上限」
+
+### 2.4 為什麼把 `MAX_REQUESTS` 改成 `DEFAULT_*` 並用 sentinel None
+- Python 函式 default arg 在 `def` 時 evaluate 一次就凍結
+- 測試想用 `monkeypatch.setattr(rate_limit, "MAX_REQUESTS", 3)` 調小上限 → 沒用，因為 middleware 用的是 import 時的值
+- 解法：default `None`，函式內 `globals()["DEFAULT_MAX_REQUESTS"]` 動態讀 → monkeypatch 立刻生效
+- 第一次實作踩到這個坑（2 個 test 失敗），debug 後改掉
+
+### 2.5 為什麼用 `from_attributes=True` 而非手動 `.from_orm()`
+- Pydantic v2 新寫法：SQLAlchemy ORM 物件可以直接 `.model_dump()` / `TodoRead.model_validate(orm_obj)`
+- 比 v1 的 `from_orm` 更明確，且對未來加欄位更友善
+
+### 2.6 為什麼把 `delete_todo` return type 改成 `Response`
+- FastAPI 強制：HTTP 204 不能有 response body
+- 原本 `-> None` 會 assert fail → 改用 `Response(status_code=204)` + `response_class=Response`
+
+### 2.7 為什麼 rate_limit middleware 用 thread.Lock 而非 asyncio.Lock
+- `check_rate_limit()` 是純函式，middleware 在 `async def` 中呼叫
+- FastAPI threadpool 跨 thread 共用 `_buckets` dict → 必須有 lock
+- asyncio.Lock 在 thread 之間沒保護，這裡用 threading.Lock 才對
+
+### 2.8 為什麼 In-memory SQLite 用 StaticPool
+- 預設 QueuePool 對 `:memory:` 會每 thread 建一個獨立 connection → 看不到其他 thread 的資料
+- StaticPool 強制所有 thread 共用同一個 connection → in-memory DB 才能正常運作
+- 這是 SQLite + threaded test 的標準踩坑點
