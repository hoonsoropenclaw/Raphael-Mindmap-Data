+## 2. 設計決策（為什麼這樣寫）
+
+### 2.1 為什麼選 `aiohttp` 而不是 `httpx`
+- `httpx` 雖然支援 async,但內部仍有 sync fallback 路徑,對純 asyncio 場景是多餘的
+- `aiohttp` 是專為 asyncio 設計的 HTTP client,server 端也能用同一套（測試就用它架 mock）
+- 兩者都有,用 `aiohttp` 比較純
+
+### 2.2 為什麼不用 `tenacity` / `backoff` library
+- 核心 retry 邏輯不到 50 行,引入第三方依賴反而模糊了「指數退避 + jitter」的細節
+- SOUL.md「第一次就做對」精神: 自己寫才能確保 jitter 真的是 decorrelated（AWS 推薦算法）
+
+### 2.3 為什麼錯誤要分類成 Transient / Permanent / RateLimit
+- 4xx (除 408/429) **不該**重試 — server 明確告訴你「不要來」
+- 5xx + timeout + connection reset → 值得重試
+- 429 → 重試但要尊重 `Retry-After` header,不能用 random delay
+- 全 catch `Exception` 會把 KeyboardInterrupt 吃掉、把 bug 當 transient 重試 → 反 pattern
+
+### 2.4 為什麼要 Circuit Breaker
+- 對死掉的 server 持續重試只會浪費 quota + 拖慢整體
+- threshold=5 + reset_timeout=30s 是 Cloudflare/AWS 公開建議值
+- HALF_OPEN 狀態只放 1 個請求試探,避免一恢復就被打爆
+
+### 2.5 為什麼 AsyncCrawler 是 context manager
+- `aiohttp.ClientSession` 一定要 close,否則會有 unclosed connection warning（甚至 memory leak）
+- `async with` 確保即使例外也會正確清理
