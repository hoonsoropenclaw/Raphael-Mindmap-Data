+# Todo API v2
+
+A minimal Todo REST API, intentionally small but production-shaped:
+
+- **FastAPI** HTTP layer (sync endpoints, run in threadpool)
+- **SQLAlchemy 2.x + SQLite** persistence (file by default, `:memory:` in tests)
+- **slowapi** rate limiting (per-IP, per-route, with global fallback)
+- **pytest** test suite (CRUD + HTTP + rate-limit + filter coverage)
+
+## Why this exists (and why it looks the way it does)
+
+See `IMPLEMENTATION_NOTES.md`. The short version:
+
+- Sync, not async — see [trial-and-error lesson 37][L37] about mixing
+  sync sessions with async endpoints. We pick sync to avoid it.
+- `headers_enabled=False` on the limiter — slowapi's default injection
+  crashes on endpoints that return Pydantic models instead of `Response`
+  objects (lesson 38).
+- Test fixtures build their own `Limiter` instance — never share the
+  module-level singleton with the production app (lesson 39).
+
+[L37]: https://docs.sqlalchemy.org/en/20/orm/session_basics.html
+
+## Quickstart
+
+```bash
+python3 -m venv .venv
+source .venv/bin/activate
+pip install -e ".[test]"
+
+# Run tests (should show 24+ passed, coverage >= 90%)
+pytest -v --cov=app
+
+# Run the API
+uvicorn app.main:app --port 8765
+# Open http://127.0.0.1:8765/docs for Swagger UI
+```

+"""Database engine, session, and Base declaration.
+
+**Why sync (not async)?**
+
+Mixing ``async def`` endpoints with a regular ``sessionmaker`` is a
+deadlock waiting to happen: an event-loop-blocking call holds the
+session open while the loop tries to schedule other coroutines, and
+under concurrent traffic the requests stall instead of returning.
+
+Two clean options exist:
+
+* **Fully async** — ``aiosqlite`` + ``AsyncSession`` + ``await db.execute()``.
+* **Fully sync** — plain ``sqlite3`` + sync ``sessionmaker`` + sync def.
+
+We pick sync. Todo data is single-user / single-machine; the throughput
+benefit of async is not the bottleneck. The downside of async (more
+ceremony, more async client plumbing in tests) outweighs it here.
+
+FastAPI runs sync endpoints in a threadpool, so this never blocks the
+event loop.
+
+**Why ``check_same_thread=False`` + ``StaticPool`` for in-memory?**
+
+An in-memory SQLite (``sqlite:///:memory:``) gives every connection
+its own private database. The FastAPI TestClient uses a threadpool,
+which means consecutive requests land on different connections that
+can't see each other's tables. ``StaticPool`` makes every "session"
+share the single underlying connection so the whole process sees the
+same DB. ``check_same_thread=False`` lets SQLAlchemy hand that one
+connection across thread boundaries.
+
+**Why ``expire_on_commit=False``?**
+
+Pydantic's ``model_validate(obj)`` reads attributes off the ORM
+object. After commit, SQLAlchemy normally expires those attributes
+(they'll be re-fetched on next access); but if validation happens
+after the session is closed (typical in our endpoints — the session
+closes before the response is serialised), the access raises
+``DetachedInstanceError``. Keeping attributes after commit side-steps
+that whole class of bugs.
