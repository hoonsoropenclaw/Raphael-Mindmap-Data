+# IMPLEMENTATION_NOTES.md — Linux System Monitor 設計與實作說明
+
+## 一、為什麼做這個
+
+任務交付需求：「自動化檢查 Linux 系統日誌與資源的維運腳本，超過閾值時發出警告」。
+
+產出包含 5 個檔案、純 Python stdlib、零外部依賴（建議但非必需裝 PyYAML 取得完整 list-of-strings 支援）：

+monitor.config.yaml     # 閾值與告警設定
+sysmonitor.service      # systemd unit（oneshot）
+sysmonitor.timer        # systemd timer（每 5 分鐘）
+sysmonitor.crontab      # 無 systemd 環境的替代方案
+```

+## 二、架構決策
+
+### 2.1 為什麼 Python stdlib 不用 psutil / Prometheus client
+- **單檔可移植**：丟到任何 Linux + Python 3.10+ 就能跑，沒有 pip install 風險
+- **攻擊面小**：不引入第三方依賴、減少 supply chain 風險
+- **讀 `/proc` 直接**：這是 Linux 的事實來源，比 psutil 包出來的更接近底層
+
+唯一外部工具是 `journalctl`（systemd 生態的事實來源），腳本會偵測是否存在、不存在就靜默跳過。
+
+### 2.2 為什麼「資源探測」和「日誌掃描」分開兩個區塊
+兩個子系統的失敗模式完全不同：
+- 資源探測：CPU/Mem/Disk → 數值型、拿當下快照、比閾值
+- 日誌掃描：journalctl → 事件流、要 lookback window、要 regex 計數
+
+混在一起會讓 alert 的 category 分不清是「資源吃緊」還是「日誌噴錯」。分開後 ops 在 oncall 時一看 `category` 欄就知道往哪查。
+
+### 2.3 為什麼用 Cooldown 而不是 Rate-limit
+**Cooldown = 同一個 alert key 在 N 秒內只發一次**。
+- 避免「CPU 高」這種慢性條件每 5 分鐘重複 spam
+- rate-limit（每分鐘最多 N 條）會在多條件同時爆發時丟失重要 alert
+- 同一個 key（`{category}:{message}`）做 dedupe、清除 cooldown（例如服務重啟後）也直觀
+
+### 2.4 為什麼用 dataclass + Findings 物件
+- `Alert` 是資料載體，`dataclass` 比 dict 安全（IDE 能跳轉、type check 能抓錯）
+- `Findings` 同時裝 alerts 和 metrics → 後續要做 Prometheus exporter / OpenTelemetry / JSON 上報，只需 `findings.to_dict()` 一行
+- 目前先用 text / JSON 印、保留擴展點
+
+### 2.5 為什麼 CPU 採樣要 sleep 1 秒
+Linux `/proc/stat` 是累計值，要兩次 sample 算 delta。`top` 預設也是這樣做。1 秒是準確度 vs. latency 的合理平衡；如果以後要塞進 Prometheus pull mode 可改 `psutil.cpu_percent(interval=None)` 模式但需重算 delta。
+
+### 2.6 為什麼 disk 用 `/proc/mounts` + `shutil.disk_usage` 不用 `df -P`
+- `df -P` 會列出所有掛載含重複 bind-mount、且需要 parse 不同 locale 的欄位
+- `/proc/mounts` 是結構化的、`shutil.disk_usage(path)` 直接拿到 used/total/free 數值
+- 過濾策略明確：跳過 `tmpfs/devtmpfs/squashfs/overlay/proc/sysfs`、再比對 `mounts_exclude` 子字串
+
+### 2.7 為什麼 journal 用 `--since` 不是 `--lines`
+- `--lines N` 取最近 N 行可能跨過 window 邊界、把舊事件算進來
+- `--since` 是時間精確的、跟 `lookback_minutes` 設定一致
+
+### 2.8 為什麼 Fallback YAML Parser
+PyYAML 在某些 minimal container / embedded device 上不一定有。fallback parser 至少能解析 2-level 巢狀的 `key: value`，足夠跑基礎 CPU/Mem/Disk 監控。遇到 list（如 `mounts_exclude`）會降級 → README 註明建議裝 PyYAML。
+

+## 三、Alert 嚴重度分級
+
+| Level | 觸發條件 | 行為 |
+|---|---|---|
+| **info**  | 目前未使用，預留 | log only |
+| **warn**  | CPU/Mem/Disk/Load 高於閾值、journal 大量 err、自訂 pattern 命中 | log + webhook（如有）+ alert log file |
+| **crit**  | Mem 超過 critical 閾值、journal 出現 emerg/alert/crit 級別 | 同 warn、並標記為緊急 |
+
+可在 `alert_levels` 設定哪些 level 要 webhook / 寫 log。實務上建議 `info` 永不發 webhook、只留 ops 內部 log。
