+# sysmon.py — Linux 系統監控腳本
+
+零依賴的 Linux 系統資源與日誌監控工具，閾值超標時輸出告警。

+## 監控項目
+
+| 類別 | 檢查 | 來源 |
+|------|------|------|
+| 資源 | CPU 使用率 | `/proc/stat` 兩次取樣 |
+| 資源 | Load Average (per-CPU) | `/proc/loadavg` |
+| 資源 | 記憶體使用率 | `/proc/meminfo` |
+| 資源 | Swap 使用率 | `/proc/meminfo` |
+| 資源 | 磁碟使用率 | `/proc/mounts` + `os.statvfs` |
+| 日誌 | journalctl ERR 條數 | `journalctl --priority err` |
+| 日誌 | dmesg OOM / panic | `dmesg --level err,crit,alert,emerg` |
+| 日誌 | auth.log / secure 失敗登入 | `/var/log/auth.log` 或 `/var/log/secure` |

+

+
+# 每 60 秒循環
+./sysmon.py --watch 60
+
+# 告警 JSONL 落盤
+./sysmon.py --alert-log /var/log/sysmon.log
+
+# 推 webhook（Slack / Discord / 通用）
+./sysmon.py --webhook https://hooks.slack.com/xxx
+./sysmon.py --webhook https://discord.com/api/webhooks/xxx --crit-only
+```

+# sysmon.py — 實作思路
+
+## 設計定位
+
+寫一個**純監控、不寫資料庫**的腳本：一次掃描 → 輸出人類可讀 + JSON → 閾值爆掉時額外觸發 webhook。不預設要 Prometheus / Grafana，可單獨跑。
+
+## 為什麼選 Python（vs Bash）
+
+| 考量 | Python | Bash |
+|------|--------|------|
+| 跨語言解析 syslog 時間 | `datetime` 內建 | 要 call `date -d` 來回搞 |
+| JSON 組裝 | `json.dumps` | `jq` 外部依賴 |
+| 結構化輸出 | `dataclass` + `asdict` | 拼字串 |
+| cpu_percent 兩次取樣 | `time.sleep()` + 數值算 | 一樣 OK |
+| 部署難度 | `python3` 標準 | 0 |
+
+Bash 的優勢是**不需要 Python 直譯器**，但實測這台 N100 一定有 python3、容器也幾乎都有，沒差。Python 給的型別 / 結構保護值得。
+
+## 為什麼 stdlib only（不用 psutil）
+
+- `psutil` 要 `pip install`，部署多一個步驟
+- 我們只需要：`/proc/stat` (CPU)、`/proc/loadavg` (load)、`/proc/meminfo` (mem)、`/proc/mounts` + `os.statvfs` (disk) — 全是 stdlib 範圍
+- log 部分本來就要叫 `journalctl` / `dmesg`，省不了外部依賴
+
+## 為什麼每個 check 獨立容錯
+
+cron 跑的監控腳本最怕「單一檢查 raise → 整個 process 死」。設計成：
+- 每個 check 用 try/except 包住
+- 失敗回傳 `level=SKIP(-1)` 而不是 throw
+- main 永遠能輸出完整報告
+
+容器環境特別需要這個：`dmesg` 在沒 `--privileged` 時會失敗、`auth.log` 在 Alpine 沒有、journalctl 要 root — 這些都不能讓整個腳本掛掉。
+
+## 為什麼用 dataclass + 統一 CheckResult
+
+兩種選擇：
+- **A) 每個 check 回 tuple** `(name, level, msg)` — 簡單，但 JSON 序列化很醜
+- **B) dataclass 統一格式** — 多寫 10 行，但每個 check 都有 value / threshold / message / details，輸出/JSON/webhook 完全一致
+
+選 B。代價是程式碼冗長、好處是新加 check 只要照 pattern 寫，告警接線不用改。
+
+## 為什麼 exit code 0/1/2
+
+- 0 = 全綠 / 1 = WARN / 2 = CRIT
+- cron / systemd 不用解析 stdout，只看 exit code 就能決定要不要觸發通知
+- 是 Unix 慣例（grep 沒找到 = 1、segment fault = 139 等）
+
+## 設計難點 debug 紀錄
+
+寫的過程踩了 3 個非顯而易見的雷：
+
+1. **`_level_by_value` 簽名跟呼叫端對不上**
+    - 寫第一版時直接把 `threshold` 整個 dict 傳進函數，但函數預期兩個 float
+    - 9 處呼叫要批次改 — 改成 `warn_key` / `crit_key` 參數更靈活
+    
+2. **每個 check 應該只看到自己的子 threshold**
+    - `DEFAULT_THRESHOLDS` 是個大 dict，裡面有 `cpu_percent` / `load_per_cpu` 等多個 key
+    - 一開始我直接把整個 dict 傳給每個函數，導致 `threshold["warn"]` 報 KeyError
+    - 解法：加 `_threshold_for(check_name, thresholds)` 抽 dispatch，每個 check 拿到剛好的子 dict
+    
+3. **threshold 字典塞進 CheckResult 太冗**
+    - 第一版每個 check 把「整個 DEFAULT_THRESHOLDS」塞進 Report → JSON 膨脹 12 倍
+    - 解法：每個 check 各自精煉自己的 `{warn, crit, ...extras}` 子集
+
+## 加 webhook 時的考量
