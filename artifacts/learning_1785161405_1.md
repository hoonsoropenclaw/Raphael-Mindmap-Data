+

+## Usage
+
+```bash
+python3 github_trending.py
+python3 github_trending.py --since weekly --language python
+python3 github_trending.py --since daily --output trending.md
+```
+
+The supported periods are `daily`, `weekly`, and `monthly`. The script uses GitHub's public Trending HTML endpoint, a descriptive `User-Agent`, a configurable timeout, and no API token or third-party dependency.
+
+## Architecture / implementation notes
+
+1. `build_trending_url()` validates the time period and URL-encodes the optional language filter.
+2. `fetch_trending()` isolates network I/O and reports HTTP, URL, and timeout errors through the CLI exit status.
+3. `parse_trending_html()` parses each `Box-row` repository card and normalizes repository name, URL, description, language, star count, and trending text. It tolerates missing language and trending fields.
+4. `render_markdown()` owns presentation and escapes pipe characters so descriptions cannot break the table layout.
+5. The CLI writes atomically from the application perspective (complete string generated before output) and creates the output parent directory when needed.
+6. Tests use a deterministic HTML fixture, so parser tests never depend on GitHub availability or changing live data.
+
+## Senior Architect feedback absorbed
+
+- Kept a standard-library-first implementation, matching the prior feedback's deployment simplicity and low supply-chain surface.
+- Maintained separation between network fetching, parsing, rendering, and CLI orchestration, following the recommended modular boundary.
+- Added robust input validation, timeout handling, and a deterministic test seam around the external HTTP boundary.
+- This is a batch CLI rather than a long-running service, so long-polling/webhook guidance is not applicable. If this is later deployed as a serverless scheduled job, the fetch/render command should run as a short-lived request and write to durable storage rather than use a persistent loop.
+- The same feedback suggested upstream protection against excessive requests. For repeated scheduled runs, add a scheduler interval and/or cache the generated Markdown for a short period rather than calling GitHub on every invocation.
