## 關鍵技術決策

### 1. 為什麼 PDF 處理用「pdfplumber + pdf2image/pytesseract fallback」雙軌？
- pdfplumber 抓文字層 + 表格（快、零 OCR、保留表格結構）
- 文字層空白或亂碼時（常見於掃描 PDF）自動降級到 OCR 流程
- 觸發條件：頁文字 < 20 chars 或含 □/▯/??? 等無法識別字元
- 這是 `ocr-and-documents` skill 的最佳實踐（見 `pdf` skill 對照表）

### 2. 為什麼 OCR 語言用 `chi_tra+chi_sim+eng` 組合而不是單一語言？
- 實務文件常混中英（公司名、英文 email、數字、英制金額）
- Tesseract 對「混合腳本」用單一 lang pack 會大幅降低準確率
- 系統偵測到 `chi_tra`（繁中）已裝、`chi_sim`（簡中）已裝、`eng`（英文）已裝
- 介面預設 `auto=combined`，必要時前端可選單語

### 3. 為什麼 Whisper API 沒 key 時還要寫完整呼叫碼？
- 介面契約正確：傳 `OPENAI_API_KEY` 後立即可用，不需改 code
- 用 `unittest.mock` patch `app.OpenAI` 確認呼叫的 model=`whisper-1`、語言對應正確
- graceful fallback：沒 key / 401 / 網路錯誤，都保留 audio metadata（ffprobe 抓 codec/duration），明確告訴使用者下一步動作
- 這是「真實可執行 + 介面正確 + UX 透明」的三層保障

### 4. 為什麼結構化欄位用 regex 而不是 NER？
- 觸發 8 個常見高價值欄位（email/phone/url/money/date/ip/id/hashtag）
- regex 速度 < 1ms、可解釋、易除錯
- 對 NER 類的「人名/組織名」不強求（pdfplumber 文字層已經能保留原字串，使用者肉眼可讀）
- 實務上 PDF 報表 90% 高價值資料是這 8 類，NER 主要服務非結構化文本

### 5. 為什麼前端用單檔 HTML 而不是 React/Vue？
- 任務交付是 `web_output.html`（單檔）
- 整個 UI 30KB（壓縮前），無框架依賴、無 build step
- vanilla JS 模組化（IIFE）已經足夠表達這個互動密度
- 部署：`python3 app.py`，瀏覽器開 `http://127.0.0.1:8789/`，零配置

## 踩坑紀錄

### 坑 1：其他 learning 任務佔用 8765 端口
- 同時跑 learning_1、learning_2、learning_3（OCRS）時，全搶 8765
- 解法：程式預設 port 改參數化（`--port 8789`），啟動時先檢查
- 教訓：cron 平行任務要讓每個任務綁死自己的 port 範圍

### 坑 2：`datetime.utcnow()` 在 Python 3.12 觸發 DeprecationWarning
- 修為 `datetime.now(timezone.utc).isoformat().replace("+00:00", "Z")`
- 教訓：cron 跑得久才會看到 deprecation，提前升級避免下次 warning 變 error

### 坑 3：langdetect 對繁中 PDF 顯示 `en: 1.0`
- 原因：測試文件大量英文數字/網址/金額，繁中只佔少部分
- 這是 langdetect 已知特性（短文本預設傾向英文）
- 教訓：中文文件處理要看 CJK char 比例再判斷，不能只看 langdetect

### 坑 4：Flask 第一個測試 timeout 120s（OCR PDF 4.5s / 請求）
- 原本以為 `threaded=True` 沒生效；實際是 4 個並行每個都跑 OCR（4.5s × 4 = 18s）
- 改為 3 個並行純文字 PDF（0.35s × 3 = 0.52s）確認 threaded 真的有效
- 教訓：threaded 驗證不要用最重的任務當測試
