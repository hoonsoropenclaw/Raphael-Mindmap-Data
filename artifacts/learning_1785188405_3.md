+# Linux Health Monitor
+
+`linux_health_monitor.py` is a read-only, dependency-free monitor for cron or a systemd timer. It checks:
+
+- normalized 1-minute load average
+- sampled CPU utilization
+- memory utilization using `MemAvailable`
+- disk and inode utilization for a selected mount
+- warning-or-higher journal entries in a recent window
+- OOM-related kernel events
+- failed systemd units
+
+It prints a human-readable report by default, can emit JSON, and optionally appends WARN/UNKNOWN reports to a JSONL alert file. Exit status is `0` for OK, `1` for WARN, and `0` for UNKNOWN unless `--unknown-is-warning` is supplied.
+
+The monitor never runs a shell and does not mutate the system. `journalctl` and `systemctl` are optional: if unavailable or inaccessible, those checks are explicitly marked `UNKNOWN`.
+
+## Quick start
+
+```bash
+chmod +x run_linux_health_monitor.sh
+./run_linux_health_monitor.sh
+./run_linux_health_monitor.sh --output json --alert-file /var/log/linux-health-monitor.jsonl
+```
+
+For a non-root cron install, use a writable alert path, for example:
+
+```cron
+*/5 * * * * /absolute/path/to/run_linux_health_monitor.sh --alert-file "$HOME/.local/state/linux-health-monitor/alerts.jsonl" >>"$HOME/.local/state/linux-health-monitor/monitor.log" 2>&1
+```
+
+For system-wide operation, a systemd timer can invoke the wrapper every five minutes. Treat exit status 1 as an alert in the surrounding scheduler; this script intentionally does not send email, chat messages, or make network requests.
+
+## Thresholds
+
+Defaults are conservative starting points and should be tuned for the host:
+
+- `--load-per-cpu 1.50`
+- `--memory-used-percent 90`
+- `--disk-used-percent 85`
+- `--inode-used-percent 90`
+- `--log-warning-count 20`
+- `--oom-event-count 1`
+- `--failed-units 1`
+
+Example:
+
+```bash
+./run_linux_health_monitor.sh --filesystem /var --window-minutes 30 \
+  --memory-used-percent 85 --disk-used-percent 80 --unknown-is-warning
+```
+
+## Security and operational notes
+
+- The script is read-only with respect to system state; the only write is the optional append-only alert file.
+- Commands are passed as argument arrays to `subprocess.run`; no shell interpolation is used.
+- Alert JSONL contains recent journal samples. Protect the alert file because system logs may contain hostnames, paths, usernames, or service details.
+- Run with the minimum privileges needed. Root is not required for `/proc`, filesystem statistics, or many journal configurations.
+- A WARN is not automatically a failure: journal volume and load thresholds are host-dependent. Review the report before automated remediation.

+# Implementation notes
+
+## Architecture
+
+- `linux_health_monitor.py` contains the monitor and keeps checks as small, deterministic functions.
+- `/proc/loadavg`, `/proc/meminfo`, and `/proc/stat` are read directly so the core resource checks need no external package.
+- `journalctl` and `systemctl` are invoked through `subprocess.run` with argument arrays, fixed timeouts, captured output, and no shell.
+- Each check returns `OK`, `WARN`, or `UNKNOWN`. Missing permissions, missing commands, malformed data, and command timeouts do not silently become healthy results.
+- The overall result is `WARN` if any threshold is exceeded; otherwise it is `UNKNOWN` if a check could not be evaluated; otherwise `OK`.
+
+## Threshold semantics
+
+- Load is normalized by logical CPU count, avoiding a fixed load threshold that behaves differently on small and large machines.
+- Memory uses `MemAvailable` rather than only `MemFree`, which better reflects reclaimable Linux memory.
+- Disk and inode checks are independent because a filesystem can exhaust inodes before bytes.
+- Journal warnings and OOM events use a bounded recent window and bounded sample count.
+
+## Safety decisions
+
+- The script is read-only except for the optional JSONL alert append.
+- No automatic restart, package installation, log deletion, network request, or remediation is performed.
+- Alert records may include journal text, so the operator must protect the chosen alert path.
+- The wrapper resolves its own directory and uses `exec`, so cron can invoke it from any working directory.
+
