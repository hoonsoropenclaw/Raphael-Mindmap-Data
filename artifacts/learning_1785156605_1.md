    2. 設計選擇與理由
    
    a. 純標準庫 SQLite（不引 SQLAlchemy）
    理由：題目是 light-weight demo，SQLAlchemy 會拖 30+ 個依賴；標準庫夠用、sqlite3.Row 直接轉 dict。
    
    b. 工廠函式 create_app(db_path, rate_limit)
    理由：測試必須能注入隔離 DB 跟自訂 rate limit；production 才用預設值。FastAPI 的 app.state 機制剛好對應。
    
    c. :memory: 陷阱 → 改用 temp file
    踩坑記錄：SQLite 的 :memory: 是 per-connection / per-thread 隔離。lifespan 跟 request 兩端會拿到不同份 DB。最終設計：測試用 tempfile.mkstemp() 給固定檔案路徑 → lifespan 跟 request 共用，行為與 production 一致。
    
    d. 不用 SlowAPIMiddleware
    slowapi 0.1.10 的 middleware 內建寫死 {"error": ...} 響應，會繞過 FastAPI exception handler。我改用 @app.exception_handler(RateLimitExceeded) 統一 429 響應為 {"detail": ...}，跟其他 4xx 對外契約一致。
    
    e. Pydantic Field(min_length=1, max_length=200)
    標題長度上界是明確的產品決定（不要讓使用者塞 1MB 字串爆 DB）。
    
    f. 部分更新（PATCH 風格 PUT）
    PUT /todos/{id} 接受 title / completed 兩個可選欄位，比 RFC 純 PUT 語意更寬鬆、但對前端更實用。沒給欄位 → 維持現況。
    
    g. completed 從 int 轉 bool
    SQLite 存 INTEGER 0/1、對外契約是 bool。在 db._row_to_dict() 統一轉換，FastAPI response_model 驗證就不會炸。
    
    h. 觸發器自動更新 updated_at
    DB 層用 TRIGGER AFTER UPDATE 維護 updated_at，API 程式碼不用記得手動更新。Known limitation：SQLite datetime('now') 在同一個 transaction 內 timestamp 會相同，所以 created_at 跟 updated_at 在同一 transaction 內會相等（這是 SQLite 文件示範的特性，不是 bug）。
