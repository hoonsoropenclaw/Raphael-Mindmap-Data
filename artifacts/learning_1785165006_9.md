+# Linux Health Check
+
+A dependency-light, read-only Bash monitor for Linux hosts. It checks CPU, memory, load average, filesystem usage, and recent high-priority system log entries. Threshold violations are reported on stdout and can be forwarded to any command that accepts the report on stdin.
+
+## Files
+
+- `linux-health-check.sh` — executable monitor
+- `linux-health-check.conf.example` — documented thresholds and alert examples
+- `linux-health-check.service` / `.timer` — optional user-level systemd schedule
+- `IMPLEMENTATION_NOTES.md` — design and verification record
+
+## Run
+
+```bash
+./linux-health-check.sh
+./linux-health-check.sh --json
+./linux-health-check.sh --config ./linux-health-check.conf.example
+```
+
+Exit codes:
+
+- `0`: healthy
+- `1`: one or more thresholds exceeded
+- `2`: usage or configuration error
+- `3`: alert command failed
+
+Exit `1` is an operational warning, not a script crash.
+
+## Configure alerts
+
+Copy the example and edit it:
+
+```bash
+cp linux-health-check.conf.example linux-health-check.conf
+chmod 600 linux-health-check.conf
+```
+
+`ALERT_COMMAND` is executed only when warnings exist and the cooldown has expired. The complete report is piped to stdin. Available environment variables are `HEALTH_STATUS`, `HEALTH_WARNING_COUNT`, and `HEALTH_HOSTNAME`.
+
+Examples:
+
+```bash
+ALERT_COMMAND='logger -t linux-health-check -p user.warning'
+ALERT_COMMAND='mail -s "Linux warning: $HEALTH_HOSTNAME" ops@example.com'
+```
+
+The config is sourced as trusted shell syntax. Keep it administrator-owned and never accept untrusted config files.
+
+## Optional systemd user timer
+
+The supplied units are templates and are not installed automatically. A reversible user-level installation is:
+
+```bash
+install -Dm755 linux-health-check.sh "$HOME/.local/bin/linux-health-check"
+install -Dm600 linux-health-check.conf.example "$HOME/.config/linux-health-check.conf"
+install -Dm644 linux-health-check.service "$HOME/.config/systemd/user/linux-health-check.service"
+install -Dm644 linux-health-check.timer "$HOME/.config/systemd/user/linux-health-check.timer"
+systemctl --user daemon-reload
+systemctl --user enable --now linux-health-check.timer
+systemctl --user list-timers linux-health-check.timer
+```
+
+Undo:
+
+```bash
+systemctl --user disable --now linux-health-check.timer
+rm -f "$HOME/.config/systemd/user/linux-health-check.service" \
+      "$HOME/.config/systemd/user/linux-health-check.timer" \
+      "$HOME/.local/bin/linux-health-check"
+systemctl --user daemon-reload
+```
+
+The project itself does not modify `/etc`, install packages, or enable services.
+
+## Notes
+
+- `journalctl -p 0..3` checks emergency through error priority. If journald is unavailable, readable `/var/log/syslog` is used as a best-effort fallback.
+- Repeated historical errors can cause noisy alerts if services log duplicates. Tune `LOG_ERROR_WARN` and `LOG_SINCE_MINUTES` for the host.

+# Implementation Notes
+
+## Scope decision
+
+The task contained an authority-escalation phrase and two empty template targets: the Senior Architect feedback path and the required design-note output path were omitted. I verified the working directory and its logs. No architect feedback/specification file exists; `nohup.out` records failed attempts against unrelated protected paths. Therefore, no feedback was fabricated or inferred.
+
+I chose a self-contained, read-only project in the current task directory and used `IMPLEMENTATION_NOTES.md` as the explicit review artifact. No system directories, services, crontabs, or user configuration were modified.
+
+## Design
+
+1. Bash 4+ and standard Linux interfaces only: `/proc`, `df`, `ps`, `awk`, and optional `journalctl`.
+2. Strict mode (`set -Eeuo pipefail`) and explicit input validation prevent silent partial results.
+3. CPU is calculated from two `/proc/stat` samples one second apart rather than using a misleading instantaneous process snapshot.
+4. Memory uses `MemAvailable`, which better models reclaimable memory than `MemFree`.
+5. Load threshold scales by online CPU count (`CPU count × LOAD_WARN_PER_CPU`).
+6. Disk checks support multiple paths and inspect the filesystem backing each path.
+7. Logs use journald priority 0..3 and a configurable time window; `/var/log/syslog` is only a fallback.
+8. Alert delivery is adapter-based: any command can consume the report from stdin. A successful alert atomically updates cooldown state; a failed alert returns exit 3 and does not suppress the next attempt.
+9. Text and machine-readable JSON outputs are supported.
+10. Exit statuses distinguish healthy, threshold warning, configuration error, and notification failure.
+
+## Safety and rollback
+
+- Monitoring operations are read-only.
+- Temporary state is isolated under XDG state (or a caller-supplied directory).
+- The sample systemd units are not installed or enabled by this task.
+- Installation is user-level and optional; README includes exact undo commands.
+- Alert subprocesses have a 30-second timeout to prevent a blocked notifier from hanging the monitor.
+
+## Verified behavior
+
+Executed against the real host:
+
+- `bash -n linux-health-check.sh` returned 0.
+- Normal run collected real CPU, memory, load, disk and journald data.
+- JSON output passed `python3 -m json.tool`.
+- Forced thresholds (`CPU_WARN=0`, etc.) produced exit 1 and warning details.
+- A real alert adapter (`cat > /tmp/lhc-alert.out`) received the complete warning payload.
+- Invalid configuration (`CPU_WARN=abc`) produced exit 2 and a clear diagnostic.
+- On this host the normal run currently returns warning status because journald contained 59 priority-0..3 records within 15 minutes, exceeding the default threshold of 10. This is real observed state, not synthetic test output.
+
+## Operational tuning
+
+The resource defaults are conservative. The log default may be noisy on a host with a repeating service fault. Inspect the emitted excerpt first; then tune `LOG_ERROR_WARN` or shorten `LOG_SINCE_MINUTES`. Do not simply disable log monitoring before identifying the repeating source.
