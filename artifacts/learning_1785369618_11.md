+## 2. 架構決策紀錄（why 這個、不是那個）
+
+### 2.1 模式：**polling**，不是 pub/sub webhook
+
+Google Calendar 的「realtime」通知其實有兩種官方方式：
+
+| 方案 | 需要 | 適用 |
+|------|------|------|
+| **events.watch + Pub/Sub push** | Google Cloud Pub/Sub topic、Pub/Sub 訂閱 → 一個公開 HTTPS endpoint | 有對外 HTTPS server 的環境（雲端 / ngrok / Cloudflare Tunnel） |
+| **`events.list` + `syncToken` polling** | 任何能跑 long-running script 的環境 | N100 headless、純本機 |
+
+**選 polling 的原因**：N100 是住宅 IP（MEMORY 已知 `118.231.136.116` 是 Far EastTone 住宅線），直接對外 443 不一定有 port forward，且 OAuth 設定一次性後 polling 可以完全本機跑、零外部依賴。Pub/Sub + webhook 路徑我留了擴充介面（`Notifier` interface），使用者若想升級可換。
+
+### 2.2 dedupe 用 SQLite，不是 Redis
+
+- 重複推送 = 通知 spam，是最常見 bug
+- SQLite 零安裝、和 polling 同一台 machine → file lock = 天然 dedupe gate
+- Redis 多了 daemon / port / config 三層依賴 — 對「最小可執行」是反模式
+
+### 2.3 多 chat_id 支援
+
+Telegram bot 推送可以同時打到多個 chat（多人共用行事曆）。`NOTIFY_CHAT_IDS` 用逗號分隔環境變數。
