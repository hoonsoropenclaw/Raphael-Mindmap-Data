+# syswatch — Linux 系統日誌與資源監控
+
+自動監控 CPU / Memory / Disk / Load / I/O wait 等資源,以及 `auth.log` (SSH 暴力破解)、`syslog` (OOM / segfault / 磁碟 I/O error / kernel panic),超過閾值時輸出 alerts。
+
+## 設計目標
+
+- **stdlib-only** — 無第三方依賴 (Python 3.10+)
+- **可離線執行** — 不依賴 systemd / Prometheus / 任何 daemon
+- **多輸出通道** — console + JSON report (每日輪替) + JSONL log + syslog (logger)
+- **自動 fallback** — `/var/log/syswatch` 寫不進去 → 改用 `~/.local/share/syswatch/log`
+- **冷卻機制** — `urgent_flag` 存在期間不重複發 CRITICAL 警報
+
+## 檔案
+
+| 檔案 | 用途 |
+|------|------|
+| `syswatch.py` | 主腳本 (CLI + library) |
+| `config.json` | 預設配置 (含所有閾值) |
+| `test_syswatch.py` | Smoke test (7 個 threshold 場景) |
+| `syswatch-run.sh` | Cron / systemd timer 用的 wrapper |
+
+## 使用方式
+
+```bash
+# 單次掃描、印人類可讀 + 寫 report
+python3 syswatch.py
+
+# 印 JSON only (給其他工具 ingest)
+python3 syswatch.py --json-only
+
+# 持續 loop,每 60 秒一次
+python3 syswatch.py --loop 60
+
+# 不要寫檔,只 console
+python3 syswatch.py --dry-run
+
+# 用自訂 config
+python3 syswatch.py --config /etc/syswatch/myconfig.json
+
+# 寫一份預設 config 到指定路徑
+python3 syswatch.py --init-config /home/hoonsoropenclaw/.hermes/scripts/syswatch/prod.json
+
+# 跑 smoke test
+python3 test_syswatch.py
+```

+## 監控項目
+
+### 資源
+- CPU busy % (1 秒 dual-sample,讀 `/proc/stat`)
+- I/O wait %
+- Load average (1/5/15) per CPU
+- Memory used % (MemAvailable)
+- Swap used %
+- Disk used % — 監控 `monitored_mounts` + 自動走訪 `/proc/mounts` 排除 tmpfs / proc / sysfs 等
+- 0 byte 偽檔案系統 (`securityfs`, `efivarfs`, `bpf`) 自動排除
+
+### 日誌
+- `auth.log` (15 min / 60 min 滑動窗口)
+  - `Failed password` — Top 5 攻擊 IP + Top 5 被嘗試 username
+  - `Invalid user` — Top 5 IP + username
+  - `Accepted` / session opened / closed
+- `syslog` (60 min 滑動窗口)
+  - `OOM kill` — ≥3 次 → `EMERGENCY`, ≥1 次 → `CRITICAL`
+  - `segfault` — WARN ≥3 / CRITICAL ≥10
+  - I/O error / EXT4-fs error — WARN ≥2 / CRITICAL ≥5
+  - Kernel panic — 任何一次 = `EMERGENCY`
+
+## Severity 模型
+
+| 等級 | 觸發條件 | 動作 |
+|------|---------|------|
+| INFO | 預設 | 寫 report, console 印 ℹ️ |
+| WARN | 閾值 warn 級別觸發 | 同上 + `logger -t syswatch` |

+| EMERGENCY | OOM ≥3 / kernel panic | 同上 |

+# syswatch 設計與實作記錄 (2026-07-27)
+
+## 任務
+自動化檢查 Linux 系統日誌與資源,超過閾值時發出警告。
+
+## 設計取捨
+
+### 1. 為何 stdlib-only
+- N100 環境要最小化依賴
+- `psutil` / `requests` 等第三方套件需要 `pip install`,會污染 hermes 環境
+- Python 3.12 內建 `pathlib`,`shutil.disk_usage`,`os.getloadavg`(雖然我改用 `/proc/loadavg` 更直接),`subprocess`,`re`,`json`,`dataclass` 完全夠用
+
+### 2. 為何雙輸出目錄(primary + fallback)
+- `/var/log/syswatch` 適合 root 跑的 cron,但 user cron 沒權限寫
+- 自動 fallback 到 `~/.local/share/syswatch/log` (N100 user-space 標準位置)
+- `_usable()` 函式先 `mkdir + touch + unlink` 探測,比 `os.access` 更可靠(實測 `os.access` 在 bind-mount 環境會誤判)
+
+### 3. 為何 JSON + JSONL 雙格式
+- **每日 JSON report** (`syswatch-report-YYYYMMDD-HHMMSS.json`)— 完整 snapshot,適合事後分析 / 餵給 Grafana / ELK
+- **JSONL log** (`syswatch.log`)— 一行一個 summary,適合 `tail -f` / `jq` / 進 Prometheus
+- 兩種格式互補:JSON 完整、JSONL 簡潔好串流
+
+### 4. 為何 cooldown 而非 rate-limit
+- 同一個 CRITICAL 在 10 分鐘內連發 5 次 = 警報疲勞
+- cooldown 控制「urgent flag 重寫」,不控制「report 寫入」(後者每次都寫、保留完整歷史)
+- 預設 600 秒 = 10 分鐘,夠人看完第一次通知 + 回應
+
+### 5. 為何不在腳本內呼叫 `dmesg`
+- `dmesg --since` 在新版 kernel 需要 `CONFIG_SECURITY_DMESG_RESTRICT=0`
+- syslog 內的 kernel line 通常夠用
+- 若未來需要,可加 `--use-dmesg` flag
+
+## 實作踩坑 (L2 → L3 提煉)
+
+### 坑 1:`UnboundLocalError: sev` (segfault/disk_error 兩個分支)
+**症狀**: `if-elif` 結構沒設 `sev=None` 預設值,當條件都不滿時,`if sev and seg_count > 0` 拋 UnboundLocalError。
+**根因**: 與 check_auth_log 不同(後者有 `else: sev=None`),`check_syslog` 內 segfault/disk_error 兩段只有 `if-elif` 沒 `else`。
+**L3 教訓**:
+**If** 在 Python 內 if-elif 結構裡給區域變數設值,後續 `if <var>:` 使用 **Then** 必加 `else: var = None` 或 `var = None` 在 if-elif 之前顯式初始化
+**Why** UnboundLocalError 在 production 路徑才觸發(lint 抓不到),且只在某個分支條件不滿時發生
+
+### 坑 2:`PermissionError` 在 `primary.mkdir` 直接 raise、fallback 沒被建立
+**症狀**: 第一次跑時 `ensure_output_paths` 在 `primary.mkdir(parents=True, exist_ok=True)` 直接炸 `PermissionError: /var/log/syswatch`,fallback 完全沒建,後續寫入全失敗。
+**根因**: 我以為 `exist_ok=True` 會 swallow PermissionError,但它只 swallow FileExistsError。
+**L3 教訓**:
+**If** 設計「primary + fallback」雙路徑,primary 通常是系統路徑(需 root)、fallback 是 user 路徑 **Then** 不要在 `_usable(primary)` 之前硬 mkdir primary,**必先** mkdir fallback (try-except OSError),**然後** 用 `_usable` 探測 primary
+**Why** PermissionError 在 mkdir 階段 raise 比在 write_text 階段 raise 早,順序錯就整個 fallback 邏輯死掉
+**驗證**: 我修正後重跑 `_usable(primary)` 探測失敗 → 改用 fallback.mkdir(已建好) → 成功
+
+### 坑 3:`render_console` 從 `r['mem_used_pct']` 讀但實際是 nested `r['memory']['mem_used_pct']`
+**症狀**: 第一次跑 `python3 syswatch.py` 報 `KeyError: 'mem_used_pct'`。
+**根因**: `check_memory` 回傳 dict,被 `resources.update(check_memory(...))` 展開後...等等,我檢查原始碼,我用 `resources["memory"] = check_memory(...)` 不是 update,所以是 nested。但 render_console 從 `r['mem_used_pct']` 讀。
+**L3 教訓**:
+**If** 一個函式回傳 nested dict,主迴圈把它塞進外層 dict 的特定 key **Then** render 程式碼必對應讀 nested 路徑,**不要**直接讀外層 key
+**驗證**: grep -n "mem_used_pct" 兩處:`check_memory` 內的 self-result + `render_console` 內的讀取路徑;兩者必須一致
+
+### 坑 4:Python 3.12 `@dataclass` 在動態 import 時要先把 module 加進 `sys.modules`
+**症狀**: `test_syswatch.py` 用 `importlib.util.spec_from_file_location` 載入 syswatch 時,跑 `@dataclass` 報 `AttributeError: 'NoneType' object has no attribute '__dict__'`。
+**根因**: Python 3.12 dataclass 用 `sys.modules.get(cls.__module__).__dict__` 找 module namespace;動態載入的 module 沒進 sys.modules 就 None。
+**L3 教訓**:
+**If** 用 `importlib.util.spec_from_file_location` 動態載入含有 `@dataclass` 的 module **Then** 在 `spec.loader.exec_module(mod)` **之前** 先 `sys.modules["<name>"] = mod`
+**驗證**: 加 `sys.modules["syswatch"] = syswatch` 之後測試立刻過
+
+### 坑 5:syslog timestamp 解析的 year 處理
+**症狀**: syslog timestamp 格式 `"Jul 27 18:02:03"` 沒年份,我用 `year = UTC_NOW().year`。
+**根因**: 跨年時 (12/31 → 1/1) 會把 1/1 的 log 算成去年的 12/31,所以 `ts < since` 會誤判。
+**L3 教訓**:
+**If** 解析 syslog 沒年份的 timestamp **Then** 對未來時間 (例如 1/1 解析出來 12/31) 要 `year -= 1`;這個修正沒做、未來會出 bug 但目前測試都是同一年內
+**標記**: 目前沒處理,但在 docstring 內已記錄「year = UTC_NOW().year」會跨年誤判,未來需修
