+### 為什麼 `dry_run` 接受 rc=2？
+
+`linux_ops_monitor.py` 對 `--dry-run` 仍走 exit code 邏輯（critical → rc=2）。這是**設計上要保留的**：
+- 讓 dry-run 真的能驗證 exit code 通路（如果 dry-run 永遠 rc=0，就驗不出「critical 沒傳到 exit code」這類 bug）
+- rc=2 ≙ 系統在跑、journal 在流、採樣到真實 alert — 這才是「健康」的證據
+- rc=0 反而是「系統完全靜默」的可疑信號
+
+### 為什麼 `lock` 用 `flock -n` 測試？
+
+不要再 `rm -f` lock file — 那會跟正在跑的 process 搶資源。`flock -n` 測試能不能搶到、不能搶就是「有人在用」（健康）、搶得到就是「stale」（也可以、但寫入 PROCESS 會自然吃掉）。
+
+### 為什麼 `recent_alert` 用 24h 閾值？
+
+警告頻率取決於 cron 週期：若 cron 是 5 分鐘跑一次，6 條檢查 24h 內一定有 alert 寫入（即便 all OK、不寫 alert、state 也不會更新 — 所以這條只檢查「如果曾經 alert 過、最後一筆時間不該太舊」）。若 cron 沒在跑，這條會 WARN 但不會 FAIL（提示用）。
