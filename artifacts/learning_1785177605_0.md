+## 2. Inputs and constraints actually verified
+
+The original message contained two unfilled template targets: the Senior Architect input path and the delivery-review output path. Rather than invent paths, the work directory was searched. `nohup.out` pointed to these real files:

+This document is the explicit project-local target for the requested implementation rationale.
+
+## 3. Architecture
+
+| Module | Responsibility |
+|---|---|
+| `weather_api.py` | Validate location, call wttr.in `format=j1`, parse JSON, translate common conditions, format output; also usable as a CLI. |
+| `telegram_bot.py` | Telegram Bot API transport, command routing, allowlist, per-user rate limit, update cursor state, process lock, retries, shutdown. |
+| `test_weather_bot.py` | Offline unit and integration-style tests with mocked HTTP, synthetic SIGTERM, lock collision, private atomic state verification. |
+| `run.sh` | Load local `.env`, require the token, replace the shell with the Python process. |
+
+The implementation deliberately uses only the Python standard library. The flow needs only Telegram `getMe`, `getUpdates`, `sendMessage`, and one wttr.in request; a Telegram framework would add dependencies without improving this simple routing problem.
+
+## 4. Senior Architect feedback mapping
+
+| Architect concern | This project’s response | Verification |
+|---|---|---|
+| CWE-214: secret in CLI arguments leaks through the process list | `TELEGRAM_BOT_TOKEN` is read only from `os.environ`. There is no token CLI flag. `run.sh` uses `exec`. | Source inspection; no-token startup test. |
+| CWE-276: state file permissions | State is written through a private temporary file and final `chmod 0600`; lock file is also `0600`. | `test_state_store_private_atomic_and_resume`; final `stat`. |
+| Cursor tracking instead of re-reading/replaying | Telegram `offset = update_id + 1` is saved after every successfully handled update and loaded on restart. | Synthetic main-loop test asserts persisted offset `101`. |
+| Single-instance race prevention | Non-blocking exclusive `fcntl.flock`; second process receives exit code 2. | Lock-collision test. |
+| Atomic state update | `tempfile.mkstemp` in the destination directory, `flush`, `fsync`, `os.replace`, cleanup on failure. | Test asserts no orphan temporary files. |
+| Graceful shutdown | SIGINT/SIGTERM set a `threading.Event`; the polling loop exits after the active request and releases the lock. | Synthetic SIGTERM test. |
+
+## 5. Data flow
+
+1. Telegram long polling returns one or more updates.
+2. Non-text or malformed messages are ignored.
+3. Optional numeric user allowlist is enforced.
+4. Per-user cooldown blocks bursts before calling the weather API.
+5. `/start` and `/help` are handled locally; `/weather CITY` or plain text becomes the location.
+6. Location validation removes lone Unicode surrogates, bounds length to 100, and rejects symbol-only input.
+7. `weather_api.py` URL-encodes the location and calls `https://wttr.in/<location>?format=j1` with an explicit timeout and User-Agent.
+8. The response is parsed into an immutable `Weather` dataclass and formatted with direct Unicode emoji literals.
+9. After a successful handler/send sequence, `update_id + 1` is atomically persisted.
+
+## 6. Security and failure behavior
+
+- No credential is embedded in source, examples, tests, logs, or command-line flags.
+- `.env` and runtime state are excluded by `.gitignore`.
+- Raw weather-service errors are logged server-side; users receive a generic retry message.
+- Telegram and weather calls have finite timeouts.
+- Telegram polling failures use exponential backoff capped at 30 seconds.
+- Unknown weather descriptions are preserved instead of being falsely translated.
+- A missing/malformed token causes a controlled startup failure with exit code 2 and no network access.
+
+## 7. Why long polling
+
+The host is headless and no public HTTPS endpoint was requested. Long polling therefore avoids DNS, reverse proxy, TLS certificate renewal, firewall opening, and webhook signature concerns. Webhook mode would be justified only when a public HTTPS service already exists or message volume requires it.

+

+## Outcome
+
+The input review belongs to a Linux monitoring project, but four architecture-level principles transfer directly to this bot and are implemented rather than merely acknowledged:
+
+1. CWE-214: bot credentials are environment-only; no `--token` argument exists.
+2. CWE-276: offset state and process lock are mode `0600`.
+3. Cursor semantics: Telegram `update_id + 1` is persisted and resumed.
+4. Single-instance safety: `fcntl.flock(LOCK_EX | LOCK_NB)` prevents overlapping polling loops.
+
+Additional production controls retained in this implementation:
+
+- Standard library only.
+- Destination-directory atomic state writes with unique temp files.
+- `fsync` before `os.replace`.
+- Per-user allowlist and rate limiting.
+- Input sanitization including removal of lone Unicode surrogates.
+- Explicit HTTP timeouts and bounded exponential retry.
+- SIGINT/SIGTERM graceful stop.
+- Generic user-facing upstream errors, with details restricted to local logs.
+
+## Review checklist
+
+- [x] No hard-coded Telegram or weather credential.
+- [x] `.env` excluded from version control.
+- [x] No secret-bearing CLI flag.
+- [x] State/lock permissions enforced.
+- [x] Offset advances absolutely (`update_id + 1`), never with a blind increment.
+- [x] Offset persists only after the update handler completes.
+- [x] Second instance fails predictably instead of racing.
+- [x] Network calls are bounded by timeout.
+- [x] Telegram polling recovers through bounded backoff.
+- [x] Tests exercise main-loop state persistence and synthetic shutdown.
+- [x] Real weather API is checked separately from mocked tests.
+- [x] Real Telegram E2E is not falsely claimed without a BotFather token.
+
+## Known operational limit
+
+The handler is at-least-once, not exactly-once. If the process dies after sending the Telegram reply but before saving the new offset, Telegram can redeliver the update after restart. The weather lookup is read-only, so replay is safe but may produce a duplicate reply. Exactly-once delivery would require an idempotency/outbox store and is disproportionate for this small bot.
+
+Detailed implementation rationale and verification commands are in `IMPL_NOTES.md`.
