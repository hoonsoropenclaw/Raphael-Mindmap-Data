+# Linux Health Monitor
+
+`linux_health_monitor.py` is a dependency-free, one-shot Linux operations monitor. It checks resource saturation and recent system failures, prints a warning when a threshold is exceeded, and can persist alerts or POST a compact JSON payload to a webhook.
+
+## What it checks
+
+- Aggregate CPU utilization from `/proc/stat` over a short bounded sample.
+- Memory and swap utilization from `/proc/meminfo`.
+- One-minute load average normalized against the number of CPUs.
+- Filesystem blocks and inodes for each configured path.
+- Recent warning/error/critical events from `journalctl`; configured text logs are used as a fallback.
+- Failed systemd units through `systemctl --failed`.
+
+The collector is best-effort by default: a missing optional source is reported as `DEGRADED` instead of hiding measurements from other sources. `--strict` changes a degraded collection result to exit status `2`.
+
+## Files
+
+| File | Purpose |
+|---|---|
+| `linux_health_monitor.py` | Main CLI and importable implementation |
+| `config.example.json` | Safe starting configuration |
+| `run-monitor.sh` | Local/cron launcher |
+| `linux-health-monitor.service` | systemd oneshot unit |
+| `linux-health-monitor.timer` | Five-minute systemd schedule |
+| `test_linux_health_monitor.py` | Unit, fallback, persistence, and concurrency tests |
+| `IMPLEMENTATION_THOUGHTS.md` | Architecture decisions and review notes |
+| `review_queue.md` | Delivery acceptance checklist |
+
+## Quick start
+
+```bash
+cd /home/hoonsoropenclaw/.hermes/projects/learning_1785184206_2
+chmod 700 run-monitor.sh linux_health_monitor.py
+./run-monitor.sh --dry-run
+./run-monitor.sh --dry-run --json
+```
+
+Exit codes:
+
+- `0`: no threshold alert (or a concurrent invocation was skipped)
+- `1`: one or more thresholds exceeded
+- `2`: strict collection/notification failure
+- `3`: invalid command line or configuration
+
+A threshold alert intentionally returns `1`, which lets cron/systemd monitoring detect it without parsing human text. The report itself is still printed to stdout.
+
+## Configuration
+
+Copy `config.example.json`, edit thresholds and paths, then pass it with `--config`:
+
+```bash
+cp config.example.json "$HOME/.config/linux-health-monitor.json"
+chmod 600 "$HOME/.config/linux-health-monitor.json"
+./run-monitor.sh --config "$HOME/.config/linux-health-monitor.json"
+```
+
+Important fields:
+
+- `cpu_percent`, `memory_percent`, `swap_percent`, `disk_percent`, `inode_percent`: percentage limits.
+- `load_per_cpu`: one-minute load limit per logical CPU.
+- `max_log_events`: number of matching warning/error events allowed in the configured window.
+- `max_failed_units`: failed systemd units allowed.
+- `alert_cooldown_seconds`: suppresses duplicate notifications for the same check while retaining the active state.
+- `state_file`: owner-only JSON state used for cooldown and recovery detection.
+- `alert_file`: append-only JSON Lines alert history; set to `null` to disable local history.
+- `webhook_url`: optional HTTP(S) endpoint. The URL is never printed in error output.
+- `strict_collection`: make missing data an exit-2 condition.
+
+The log scanner first invokes `journalctl` with `--no-pager` and a bounded time window. If journald is unavailable or denied, it reads only the tail of configured files, capped by `max_log_bytes`; it never shells out through `sh -c`.
+

+# Implementation Thoughts and Review Notes
+
+## 1. Goal
+
+Build a one-shot Linux operations monitor that can run from a minimal host without a Python package installation. It must inspect both resource pressure and system failures, emit an actionable warning when a configured limit is crossed, and remain safe when a timer fires twice or an optional subsystem is unavailable.
+
+## 2. Senior Architect feedback absorbed
+
+The available feedback file was `/home/hoonsoropenclaw/.hermes/architect_feedback.md`. Its reusable principles were applied as follows:
+
+| Feedback principle | This implementation |
+|---|---|
+| Validate concurrent behavior, not only sequential behavior | `SingleRunLock` uses non-blocking `flock`; tests prove a second process is rejected. A 100-job thread pressure test also exercises pure report evaluation. |
+| Treat generated files as security boundaries | `os.umask(0o077)`, `fchmod(0600)`, atomic `mkstemp` + `fsync` + `os.replace`, and no secret values in reports. |
+| Prefer infrastructure-as-code safeguards | The systemd unit includes `UMask=0077`, `NoNewPrivileges`, `ProtectSystem`, `ProtectHome`, and explicit read/write boundaries. |
+| Make failures observable rather than silently fatal | Each collector records a warning and the report becomes `DEGRADED`; `--strict` lets operators turn that into an exit-2 failure. |
+
+The SQLite WAL/SHM-specific part of the feedback is not directly applicable because this monitor has no SQLite database. Its underlying file-permission lesson is still applied to JSON state, lock, and alert files.
+
+## 3. Architecture
+
+```text
+CLI / systemd timer
+        |
+        v
+  load_config()  -> validated immutable Config
+        |
+        v
+  SingleRunLock  -> skip overlapping invocation
+        |
+        v
+  collect_snapshot()
+    |      |       |       |
+   /proc  disks  journald  systemd
+        |
+        v
+  build_report() -> independent Check records
+        |
+        v
+  dispatch_alerts()
+    |       |        |
+ state   JSONL    webhook
+```
+
+### Why one-shot instead of a resident daemon
+
+A timer gives a bounded process lifetime, simple restart semantics, and no background event loop to supervise. The monitor can therefore be used from systemd, cron, a CI host check, or a manual shell. The non-blocking lock prevents duplicate invocations from producing duplicate side effects.
+
+### Why stdlib-first
+
+The task is a small pipeline: read local kernel interfaces, invoke two standard utilities, compare values, and optionally POST JSON. `urllib`, `subprocess`, `fcntl`, and `dataclasses` avoid a package supply-chain/install dependency on a monitoring host. All subprocess calls use argument arrays and `shell=False` implicitly.
+
+## 4. Collection decisions
+
+- CPU is sampled using deltas from `/proc/stat`, not a single instantaneous value.
+- Memory uses `MemAvailable` where available, which is a more useful pressure signal than `MemFree` alone.
+- Load is compared with `load_per_cpu * os.cpu_count()` so the same policy scales between small and large hosts.
+- Disk block and inode usage are separate checks; a filesystem can exhaust inodes while still having free bytes.
+- Journald is preferred because it supports a time-bounded query. Text logs are a fallback and are read from the tail under a byte cap.
+- `systemctl --failed --no-legend` is parsed conservatively; unavailable commands create a collection warning rather than a fabricated healthy result.
+
+## 5. Alert state design
+
+The state file stores:
+
+- currently active alert names;
+- the last emission timestamp for each alert name;
+- the last update timestamp.
+
+Cooldown is per check, not global: a noisy disk alert should not suppress a new CPU alert. Recovery records are emitted when an alert disappears. State updates are atomic and owner-readable only, so a killed process cannot leave a partially-written JSON document at the target path.
+
+## 6. Failure and security boundaries
+
+- Missing optional commands: `DEGRADED`, with the exact source warning.
+- Invalid configuration: exit `3`, before collection starts.
+- Alert state/notification write failure: recorded as a notification error; `--strict` can make it exit `2`.
+- Webhook errors intentionally report only the exception class, never the URL or response body.
+- No shell interpolation is used for system commands.
