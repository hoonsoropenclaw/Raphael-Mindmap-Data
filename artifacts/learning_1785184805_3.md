+# 實作思路 — Telegram 天氣機器人
+
+## 為什麼選 Open-Meteo
+- **無 API key**：省掉 onboarding 摩擦，整個 bot 只需要 Telegram token 一個 secret
+- **兩個 endpoint 剛好對應需求**：Geocoding（城市名 → 經緯度）+ Forecast（經緯度 → 當前 + 24h）
+- **回傳格式乾淨**：JSON、不需解 XML/HTML
+- **可商用**：Creative Commons BY 4.0，但有引用義務，我已設 User-Agent 標註
+
+## 為什麼選 python-telegram-bot 22.x
+- **官方維護**：Telegram 官方推薦的 Python 庫
+- **async 架構**：跟 httpx 一起用不打架（asyncio.gather 時）
+- **post_init / post_shutdown hooks**：httpx client 的生命週期剛好可以 hook 進去
+- **Application.builder().run_polling()**：一條龍，跳過 webhook 設定（自架 server 才需要）
+
+## 為什麼用 httpx 不用 aiohttp / requests
+- httpx 原生 async、API 跟 requests 幾乎一樣（library 切換成本低）
+- aiohttp 太底層，要自己處理 session 細節
+
+## 為什麼要 fail-fast 驗 token
+- 不驗就會卡在底層的 `python-telegram-bot` 報錯，stack trace 落落長
+- 多一道「形狀檢查」（>= 30 字 + 包含 `:`）可以在還沒發任何網路請求時就抓出空字串 / 短字串
+- 開機時順便 `get_me()` 驗證 token 真的有效，比 user 打了訊息才 401 友善
+
+## 城市 fallback 機制
+- Open-Meteo Geocoding 對中文支援時好時壞（看 `Seoul` 回「首尔特别市」這種簡中）
+- 解法：先送原字串，失敗時看 `CITY_FALLBACK` 字典（30+ 條中英對照），換成英文 re-try
+- 缺點：字典是寫死的，沒涵蓋的城市會失敗
+- 改進方向：未來可加資料庫當 cache、或用 LLMs 翻譯
+
+## 錯誤處理策略
+- **httpx.HTTPError** → 直接回 user「API 暫時連不上」、log 印 stack
+- **geocode 找不到** → 回「請用英文再試一次」+ 提示 /help
+- **未知 exception** → 統一攔截、印 stack、給 user 友善訊息
+- **Telegram 訊息 4096 字元截斷**：用 chunk send 避免底層 raise（雖然目前 24h 預報不會超過）
+
+## 沒做什麼（清楚標記）
+- ❌ **Inline mode**：要的是「丟訊息給 bot」不是「在對話框 @bot 查」
+- ❌ **Rate limit**：單人惡意洗會打爆 geocoding（Open-Meteo 公開 API 沒強制限流，但用量大會被 deprioritize）
+- ❌ **Webhook 模式**：polling 對輕量 bot 夠用；要上 production 還是要 webhook
+- ❌ **持久化**：沒對話 state、沒歷史查詢，所以不需要 DB
+- ❌ **多語系**：WMO code 我寫死中文標籤；要 i18n 的話要做 lookup table
+
