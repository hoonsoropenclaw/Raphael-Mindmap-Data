+# GitHub Trending 自動化腳本 — 實作思路
+
+> 任務:寫一個自動化腳本,抓 GitHub 上的 trending repositories,輸出 markdown 表格。

+
+## 1. 設計決策
+
+### 1.1 為什麼走 HTML scraping 而非 GitHub API
+
+**選**: HTML scraping(`https://github.com/trending`)
+**不選**: GitHub REST API `/search/repositories?sort=stars&order=desc` 模擬 trending
+
+理由:
+- trending 排序是「特定時間窗內 stars 增加量」,不是「總 stars」
+- REST API 沒原生 trending endpoint
+- 用 query `created:>YYYY-MM-DD` 模擬 daily trending 會誤抓「當天建立的所有熱門 repo」,跟真正的「老 repo 突然暴紅」概念不同
+- 官方 trending 頁面的資料口徑是「使用者最想看的」,這是任務語義
+
+### 1.2 為什麼用 stdlib 而非 scrapling / playwright
+
+走 `urllib.request` + `re`(標準庫),不引 scrapling/playwright/requests:
+- 該頁面是純 server-rendered HTML(沒有 JS 渲染必要),用 stdlib 30 行就能抓
+- PEP 668 環境下,用 stdlib 就不需要建 venv(從 trial-and-error L3 教訓:PEP 668 友善是優先選項)
+- 啟動時間 < 1s,記憶體 < 30MB,比 browser-based scraping 快 10-50x
+- 失敗模式少:不需要等 headless browser 啟動、不需要處理 cookies/anti-bot
+
+### 1.3 為什麼 dataclass + asdict()
+
+`TrendingRepo` 用 `@dataclass`:
+- 結構化儲存 parse 結果(type-safe)
+- 產出 JSON 時用 `dataclasses.asdict()` 一行搞定,不用手刻 dict
+- 欄位命名清楚、未來擴充(例如加 `created_at`、`topics`)只改 dataclass
+
+## 2. HTML 結構 + Selector 設計(2026-07-28 驗證)
