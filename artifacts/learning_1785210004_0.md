+# sysmon_watch
+
+Linux 系統日誌與資源監控腳本 — 純 Python 標準庫,超過閾值時發出警告。
+
+## 功能
+
+- **資源監控** — CPU (透過 `/proc/stat` 兩次快照差分) / 記憶體 (`/proc/meminfo`) / 磁碟 (`shutil.disk_usage`) / load average (per-CPU 比率)
+- **日誌掃描** — `/var/log/syslog` / `/var/log/messages` 過去 N 行正則匹配,內建 default regex 鎖定「真正嚴重事件」(`kernel panic` / `out of memory` / `segfault` / `I/O error`),不抓 systemd 雜訊
+- **程序存活** — `systemctl is-active` 檢查必活服務清單(可在 YAML 設定)
+- **兩種執行模式** — `--once` 跑一次 / `--daemon` 連續監控(SIGINT/SIGTERM 優雅退出)
+- **三層警告通道** — stdout (always) / log file (always if --log-file) / webhook (optional, `SYSMON_WEBHOOK_URL` 環境變數)
+- **結構化輸出** — `Alert` dataclass,JSON Lines 相容;可用 `json.loads(alert.to_json())` 串接
+- **Exit code** — 0=正常 / 2=有 critical 告警(可串接 cron 或監控系統的 on-fail alerting)
+
+## 系統需求
+
+- Linux (用 `/proc` 與 `/var/log`,非 portable)
+- Python 3.8+ (用 `f-string` 與 `dataclasses`;本機實測 3.12)
+- 不需任何第三方套件 (`pip install` 不需要)
+- 選用:`systemctl` (若要監控 systemd 服務)

+
+### 3.1 為什麼 stdlib-first (不引入 psutil / requests / yaml / 任何第三方)

+依 trial-and-error 教訓 36(2026-07-26 cycle 538):

+
+### 3.2 為什麼 default regex 不抓「error / fail」
+
+第一次跑實機(`/var/log/syslog` 3.5 小時的資料)噴出 30+ 條「匹配」。
+原因:`systemd: Failed with result 'exit-code'` 這種**正常訊息**也含「Fail」字。
+把 default regex 改嚴到:
+- `\b(emerg|panic)\b`
+- `\b(fatal|out of memory|kernel panic|kernel:[^\n]*BUG)\b`
+- `\bsegfault\b`
+- `\b(I/O error|media error|disk failure)\b`
+
+這些是「真的出事了」的信號,雜訊低很多。
+**經驗**:監控工具的「誤報率」>「漏報率」時,人會開始忽略全部警告。
+所以 default 要寧可漏,不要濫。
+
+### 3.3 為什麼 patterns 從 `list[tuple]` 改 `list[dict]`
+
+YAML 不能直接寫 tuple。
+如果 default 是 `[(r"...", "critical")]`,那 YAML config 就只能寫成怪格式
+(像範例裡的 `"\b(emerg|panic)\b": critical` — 把 regex 當 key,severity 當 value,
+但這會被當成 string-dict,YAML parser 完全解錯)。
+
+解法:default 用 `list[dict]`,YAML 跟 Python 兩邊都自然;
+`_normalize_patterns()` 統一轉成 `list[tuple[str, str]]` 給內部用。
+**這是讓「config 檔可讀」的關鍵設計。**
+
+### 3.4 為什麼 CPU 用兩次 snapshot 而非 `psutil.cpu_percent()`
