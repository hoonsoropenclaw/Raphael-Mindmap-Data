+# hermes-monitor
+
+Linux 系統日誌與資源維運腳本。每分鐘 / 每 5 分鐘 / 排程跑,
+超過閾值時同時輸出 JSON、`logger -p user.warning`、並把狀態寫入
+`status.json` 與 `reports/<時間戳>.json` 兩處。
+
+## 檔案
+
+  hermes_monitor.py    主腳本 (~270 行, stdlib only)
+  config.json          預設閾值 (環境變數 HC_* 可覆寫)
+  test_hermes_monitor.py 自驗證腳本 (6 case)
+  status.json          atomic write 的當前狀態 (每次覆寫)
+  reports/             歷史報告 (每次跑出一份, 可配置 logrotate)
+  ARCHITECTURE.md      設計思路與決策紀錄
+  .hermes-monitor.lock fcntl lock, 防止 cron 撞 deadline 重疊執行
+
+## 用法
+
+    ./hermes_monitor.py                          # 用預設 config
+    ./hermes_monitor.py --quiet                  # 正常不打 JSON
+    HC_CPU_PCT=95 ./hermes_monitor.py            # 環境變數覆寫單項閾值
+    ./hermes_monitor.py --config /etc/my.json    # 自定義 config
+
+## 退出碼
+
+  0  一切正常 (無警告、無 fail)
+  2  有警告 (syslog convention: rc>=2 = 需要關注)
+  3  執行失敗 (如 config 壞掉、journalctl timeout)
+
+## 可監控指標
+
+  - cpu:        busy% (含 iowait) + load1/nproc
+  - memory:     MemAvailable / MemTotal
+  - disk:       任意 filesystems 列表
+  - journal:    --priority=<=<N> 過去 N 秒錯誤數
+
+## 監控指標解釋
+
+  cpu_pct      busy/total*100 包含 iowait。短時間 90% 不算嚴重,但
+               持續 1 分鐘 100% 表示有 IO bottleneck。
+  load_per_cpu 1.5 是舒服/開始慢的邊界。>2 表示 saturated queue。
+  mem_pct      走 MemAvailable 不是 MemFree,避免被 kernel cache
+               誤導為「記憶體不夠」。
+  disk_pct     各獨立告警;任何一個超就 warn。
+  journal      priority=3 表示 err/crit/alert/emerg。我們只看實際
+               error 而不是 informational noise (10 分鐘 5 條起跳)。
+
+## 環境變數覆寫規則
+
+任何 config.json 內的 key 都可以被 `HC_<KEY_UPPER>` 環境變數覆寫。
+例如 `cpu_pct_warn` → `HC_CPU_PCT`。
+
+數字 / 布林 / null / 陣列 / 物件用 `json.loads` 解,
+其他當字串 fallback。

+## 1. 設計目標
+
+1. **零外部依賴** — 任何 Ubuntu/Debian 機器可直跑 (只 import stdlib)
+2. **明確退出碼** — 0=OK / 2=WARN / 3=FAIL (BSD syslog 慣例, nagios/zabbix 也讀這組)
+3. **三通道告警** — stdout JSON (人類讀)、syslog (其他工具訂閱)、reports/ + status.json (歷史/長查詢)
+4. **不重疊執行** — fcntl flock, cron 跑太久也不會堆積
+5. **可調閾值** — config.json + 環境變數兩層覆寫, 不用改程式碼
+
+---

+## 2. 為什麼選這些指標
+
+- **CPU**: `busy_pct = (sum_of_busy_jiffies delta) / (sum_of_total_jiffies delta)`
+  - 用 `/proc/stat` 兩次取樣 (間隔 1s), 是最乾淨的方法,比讀 top 穩
+  - 同時回報 `load1 / nproc`, 因為 load 對 IO-bound 敏感, busy% 對 compute-bound 敏感 — 兩個訊號並存就涵蓋大多數情境
+  - 預設 85% 是給 N100 mini PC (CPU 少 core, threshold 不需要 95%)
+- **Memory**: `MemTotal - MemAvailable` (Linux 的「可用記憶體」含可回收 cache,比 `MemFree` 真實)
+  - 90% 預設 — 因為現代 Linux 會用 free memory 當 page cache,達 90% 是真的有問題
+- **Disk**: `shutil.disk_usage` — 跨檔案系統一致, 不用 parse df 輸出
+- **Journal**: `priority=3 (=<err)` 看 err/crit/alert/emerg, 過去 600 秒 5 條起跳才 warn
+  - 不用 info/debug (太吵)
+  - 用 priority 不用 pattern 是因為 5 分鐘內的 syslog err**通常**真的要關注
+
+> **不在 v1**: 沒做 per-process Top-N、沒做 inode / network listening port 監控。
+> 這些之後加 —— 腳本結構 (`checks[name] = check(cfg)`) 允許 plug-in 一個新函式。
+

+## 3. 為什麼是這套輸出設計
+
+### 三檔案輸出 + atomic write
+
+- `status.json` — 給 portal / 查詢 / 儀表板讀; atomic rename 不會被讀半套
+- `reports/<UTC-timestamp>.json` — 歷史快照, 一份一次跑, 給 diff / 走查 / 趨勢分析
+- syslog — 給其他工具訂閱 (Promtail、Vector、其他 cron 寫的 watcher)
+
+設計權衡:
+- 不寫 Prometheus textfile (`*.prom`) —— 這是個 4 指標的輕量監控, 不是 metrics 平台
+- 不寫 CSV —— JSON 能承載所有 heterogeneous 欄位, CSV 對 nested 不友善
+- 不發 webhook / Slack —— 外部網路 + 需要 token, 跨出頭髮的依賴會把簡單東西複雜化
+- `logger` 走 user.facility 是有意義的:讓它在 rsyslog / journald 的 `user.warning` 出現,不是 `daemon.notice`。這是 BSD syslog convention。
+
+### exit code 為何是 0/2/3
+
+- 1 留給 "catch-all error" (shell 慣例)
+- 2 = "already used by bash for syntax error", 我們**故意**沿用 BSD 內核的 syslog convention: rc=2 表示 syslog facility `LOG_WARNING`; nagios/zabbix/icinga 都認識這個數字
+- 3 = 我自己定義的「執行失敗」(配置壞、journalctl timeout、磁碟路徑消失),沒有標準, 這個值夠遠離 0/1/2/130/143/255 不會撞 alias
+
+> **已故意不做**: 沒有 `-v/--verbose`、沒有 `--dry-run`、沒有 `--once/--daemon` mode。
+> 第一版 cron + syslog 已經蓋住 95% 的 use case, 剩下等有人來要。
