+### 2.1 為什麼 `useReducer` 而非多個 `useState`
+- 「Mark all done」是單一原子操作：一次 dispatch 翻轉所有 task；如果用多個 `useState`，要嘛分開呼叫 `setDone` N 次（race condition）、要嘛自造 batch 邏輯（重複 reducer 工作）
+- Reducer 是純函數 → 可獨立 unit test（見 `test/test_reducer.mjs` 38/38 通過）
+- 每一個 mutation 走 named action（`ADD_TASK` / `TOGGLE_TASK` / `CLEAR_DONE`）→ debugger 時一眼看出意圖
+
+### 2.2 為什麼 Context（不直接 prop drilling 也不用 Redux）
+- 元件樹 3 層深：App → Toolbar/Form/List → Item — 確實需要 Context
+- 狀態完全在 UI tree 內、不需要 devtools / middleware → Redux 太重
+- 與 Redux 比：省 `~12 KB`（redux + react-redux + redux-thunk 最小組合）、少一層 abstraction
+
+### 2.3 為什麼 state shape 是 `{ byId, allIds, ... }`
+扁平 + 索引化結構：
+- 單一 task 更新 O(1)（`byId[id] = newTask`），不用 array.find
+- 插入順序保留在 `allIds`，sort 時不會破壞原始順序
+- 整體操作仍是 immutable（`{...byId, [id]: new}`）
+
+代價：selectors 多一點 boilerplate，但 `selectVisibleTasks` / `selectStats` / `selectAllTags` 已經用 `useMemo` 包起來，rendering 開銷可控。
+
+### 2.4 為什麼 debounce localStorage 而非每次 dispatch 都寫
+- 預設 250ms debounce：搜尋輸入「abc」只觸發一次寫入，而非三次
+- 即使每秒 60 次 dispatch 也只會寫一次（節省 IO、避免 localStorage quota warning）
+- useEffect cleanup 會清掉 pending timer，不會 leak
+
+### 2.5 為什麼 reducer 用 Set 解析 tags 但 state 用 Array
+- `parseTags(input)` 內部用 `Set` 去重（`split → trim → lowercase → filter → dedupe`）
+- 但存進 state 的是 `Array`（JSON-serializable、可在 JSX map）
+- 從 localStorage 還原時直接拿 `Array`，不需重建 Set
+
+### 2.6 為什麼用 `useDebouncedValue` + `useDebouncedEffect` 兩段
+- 輸入框綁**本地** state（每次 keystroke 流暢）
+- 150ms 後才 dispatch 到 reducer（state 不會被每個 keystroke 污染）
