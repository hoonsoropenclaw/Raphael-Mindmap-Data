+### Why a normalized state shape?
+

+3. **Drag-and-drop reordering** is a single `moveItem` on a small array — no deep tree walks.
+
+### Why `useReducer` + history snapshot?
+
+The reducer is a pure function of `(state, action) → state`. +# Architecture write-up — Kanban board
+
+## 1. Goal
+
+Demonstrate a **complete, runnable React 18 + TypeScript** component that exercises every layer of state management worth talking about:
+
+| Layer | Mechanism |
+|---|---|
+| Local UI state | `useState` (modals, drafts) |
+| Domain state | `useReducer` + normalized `Record<ID, T>` |
+| Side effects | `useEffect` (persistence, cross-tab sync) |
+| Reusability | Custom hooks (`useBoardState`, `useDragAndDrop`, `useUndoRedo`) |
+| Memoization | `React.memo`, `useMemo`, `useCallback` |
+| Cross-cutting | History stack inside the reducer (not a middleware) |
+
+I picked a Kanban board because it forces *all* of these to coexist: domain shape, undo/redo, dirty UI state, drag-and-drop, persistence, multi-board isolation.
+
+## 2. State shape
+
+```text
+BoardState
+├── cards:       Record<CardId, Card>
+├── lists:       Record<ListId, List>      (List.cardIds: CardId[])
+├── tags:        Record<TagId, Tag>
+├── boards:      Record<BoardId, Board>    (Board.listIds: ListId[], filterTag: TagId|null)
+├── boardOrder:  BoardId[]
+├── selectedBoardId: BoardId
+├── past:        BoardState[]   // undo history
+└── future:      BoardState[]   // redo history
+```
+
+Why two-level (id-by-id + ordered id arrays) instead of a single nested tree?
+
+- Updates touch exactly one key — React's `Object.is` short-circuits re-renders for unaffected subtrees.
+- Cards can be moved between lists without touching any `Card` object.
+- Tags can be referenced by many cards without copy.
+
+## 3. Reducer & history
+
+Every non-history action goes through `pushHistory(state)` at the top of the case branch:
+
+```text
+state.past.push(structuredClone(state))
+state.past = state.past.slice(-(HISTORY_LIMIT - 1))
+state.future = []
+```
+
+Undo / Redo:
+
+```text
+Undo:  previous = past.pop();  future.push(clone(current)); return previous
+Redo:  next     = future.shift(); past.push(clone(current));  return next
+```
+
+Putting history *inside* the reducer (rather than wrapping dispatch) keeps the reducer pure and the entire undo machine reproducible from state alone. The cost is one `structuredClone` per action — acceptable for a model of this size; we could swap to Immer later if profiling demanded it.

+# 交付審查 — Kanban Board
+
+## 一、實作思路（為什麼這樣做）
+
+### 1. 選擇 Kanban 作為載體
+題目要求「複雜的狀態管理 + CSS 樣式展示」。Kanban 剛好是一個「麻雀雖小、五臟俱全」的場景：
+
+- **多層樹狀資料**：Board → List → Card，每層都需要 CRUD
+- **一對多關聯**：Card 跟 Tag、Card 跟 Priority、List 跟 WIP
+- **使用者互動**：拖放、Modal、即時編輯
+- **持久化 + 跨 session**：這是任何「複雜狀態管理」必須處理的副作用
+- **歷史記錄**：Undo/Redo 是驗證 reducer 設計的天然試金石
+
+如果選 Todo 或 Counter，那展示不出層次。
+
+### 2. 狀態管理的「分層」
+我用 **3 層分離**：
+
+| 層 | 機制 | 為什麼 |
+|---|---|---|
+| 本地 UI 狀態 | `useState` (modal 開啟、草稿輸入) | 短暫、不關心 history |
+| 領域狀態 | `useReducer` + normalizr 風格 `Record<ID, T>` | reducer 純函式、可序列、可 undo |
+| 副作用 | `useEffect` (localStorage、`storage` 事件) | 不要把副作用混進 reducer |
+
+最關鍵的決定：**history 放在 reducer 內部、不透過 middleware**。理由：
+- Reducer 保持純函式 `(state, action) → state` — 易測試
+- 整個 history 機制可從 state 還原 → 易 debug
+- 不用引入 Redux/Zustand 的時間旅行依賴
+
+### 3. 為什麼 `useReducer` 而不是 Redux/Zustand
+- App 範圍只有 1 個 root component，沒有「跨多個深層子樹共用 state」的需求
+- 引入 Redux 等於引入 200KB+ 與 5 個新概念（store / action / reducer / dispatch / middleware）來換一個 30 行的 `useReducer`。**over-engineering**
+- 等真的需要「跨子樹 + time-travel DevTools」的需求再升級也來得及
+
+### 4. 拖放（DnD）的取捨
+- **用 HTML5 DnD**：零依賴
+- **不用 dnd-kit / react-beautiful-dnd**：300KB+ 對這種規模太重
+- 缺點：手機不好用（但 Trello 桌面版也只在桌面好用，這是可接受的 scope）
+- **優化點**：`overRef` 是 ref 不是 state，避免 dragover 事件高頻觸發 re-render
+
+### 5. 持久化的兩個關鍵細節
+- **debounce 200ms**：拖一張卡片時不會寫 20 次 localStorage
+- **cross-tab 同步**：用 `storage` event，A 頁 add board、B 頁即時看到
+- **history 不持久化**：避免「重整後殘留舊 undo」這種 UX bug
+
+### 6. CSS 的設計
+- **CSS Custom Properties**：深淺色主題用 `prefers-color-scheme` 切換變數，不寫兩份樣式
+- **響應式**：< 720px 時 list 寬度改為 84vw
+- **動畫**：modal 進入、優先級 pill 切換、drop indicator 脈衝 — 都是 CSS-only
+- **無障礙**：focus-visible、ARIA label、ESC 關 modal
