+
+Pure functions where possible so they can be unit-tested without a live bot.
+Each handler takes a TelegramMessage and returns a reply string (or None to
+silently ignore the message).
+
+The conversation log is kept in-process for simplicity.  A real production

+(`ConversationLog`) is small enough to swap without touching handlers.
+"""
+from __future__ import annotations

+from dataclasses import dataclass, field

+# ---------------------------------------------------------------------------
+# Conversation state
+# ---------------------------------------------------------------------------
+
+
+@dataclass
+class ChatMemory:
+    """Per-chat short-term memory.  Bounded to last N exchanges."""
+    chat_id: int
+    history: deque[tuple[str, str, str]] = field(default_factory=lambda: deque(maxlen=20))
+    # entries are (timestamp_iso, direction, text); direction is "in" or "out"
+
+    def record(self, direction: str, text: str) -> None:
+        ts = datetime.now(timezone.utc).isoformat(timespec="seconds")
+        self.history.append((ts, direction, text))
+
+    def tail(self, n: int = 5) -> list[tuple[str, str, str]]:
+        return list(self.history)[-n:]
+
+
+class ConversationLog:
+    """In-process conversation log keyed by chat_id."""
+
+    def __init__(self) -> None:
+        self._chats: dict[int, ChatMemory] = {}
+
+    def get(self, chat_id: int) -> ChatMemory:
+        if chat_id not in self._chats:
+            self._chats[chat_id] = ChatMemory(chat_id=chat_id)
+        return self._chats[chat_id]
+
+    def known_chats(self) -> list[int]:
+        return sorted(self._chats.keys())

+# FastAPI Telegram Bot
+
+A minimal but production-shaped FastAPI service that talks to the Telegram Bot
+API.  Designed to be deployed behind a webhook (Cloudflare, ngrok, Vercel
+serverless with adapter, or a plain VPS with nginx).
+
+## Features
+
+- **Webhook endpoint** at `POST /webhook/telegram` (validates shared secret)
+- **Command handlers**: `/start /help /id /ping /echo /history /status`
+- **Plain-text fallback** that echoes anything not starting with `/`
+- **Dry-run mode** when `TELEGRAM_BOT_TOKEN` is unset — captures every
+  `sendMessage` in memory and returns it via `GET /debug/dry-run-log`
+- **Programmatic command channel** at `GET /chat/{user_id}?text=...` so cron
+  jobs / scripts can trigger replies without going through Telegram
+- **Per-chat conversation log** (last 20 exchanges, in-process, swappable)
+- **Health check** at `GET /health`
+- **OpenAPI docs** at `GET /docs`
+

+```bash
+# 1. Install (in a venv)

+
+> 為什麼這樣做、規格缺失時妥協了什麼、怎麼延伸。
+
+## 任務原文 vs 實際交付
+
+**原文**：「開發基於 FastAPI 的 Telegram Bot 以實現自動化工作流程」
+
+**實際交付**：`telegram_bot/` package — 11 個 Python 檔 + 1 個 README + 1 個 requirements.txt + 1 個 pytest.ini。一個最小但 production-shaped 的 FastAPI 服務，包含 webhook + 命令分派 + 對話記憶 + dry-run 模式 + 程式化命令通道。
+
+## 為什麼這樣選擇
+
+### 1. 直接用 httpx，不裝 `python-telegram-bot`
+
+裝了會多 20+ 個 transitive deps，且 `python-telegram-bot` 預設是 polling 架構，binding 到 webhook 還要自己 wrap。Telegram Bot API 其實就是個 HTTPS endpoint，我用 `httpx.AsyncClient` 寫一個 100 行的 `TelegramClient` 就夠了——更可控、依賴更少、除錯更容易。
+
+### 2. Dry-run 模式是 default
+
+當 `TELEGRAM_BOT_TOKEN` 環境變數沒有設定時，bot 自動進入 dry-run 模式：
+- 還接受 webhook、跑 dispatch、產生 reply
+- 但**不** POST 到 `api.telegram.org`
+- 把所有 sendMessage call capture 在記憶體，可以從 `/debug/dry-run-log` 撈出來
+
+這是唯一能在沒有真實 bot token 的情況下完整驗證服務的方式。N100 開發機上不可能有 production token，dry-run 讓測試跟 demo 都能跑。
+
+### 3. 命令分派用純函式 + dispatch table，不引入 ConversationHandler
+
+`python-telegram-bot` 的 `ConversationHandler` 把 state machine 藏在框架裡，很難 unit test。我把 handlers 寫成 `Callable[[TelegramMessage, ChatMemory], str | None]`，純函式、沒有隱藏狀態、可以直接餵假 message 測試（看 `tests/test_handlers.py` 24 個測試）。需要 stateful conversation 再加新 handler，不必動 framework。
+
+### 4. Pydantic 2 + `populate_by_name`
+
+Telegram 的 JSON 欄位名是 `from`（Python 保留字）。我用 `Field(alias="from")` 配上 `populate_by_name=True`：
+- 從 webhook 收到的 JSON 用 `from` → 自動 mapping 到 field `from_`
+- 從 Python 端建構可以用 `from_=...`（避免 keyword 衝突）
+- 兩種都通，測試寫起來自然
+
+### 5. 程式化命令通道 `/chat/{user_id}?text=...`
+
+任務說「自動化工作流程」——代表 bot 不只被人用，也會被 cron / script 觸發。`/chat/{user_id}` 讓任何 HTTP client 不用走 webhook 也能「對某個 chat 說一句話」，自動走完整個 dispatch pipeline、寫進 history、capture 進 dry-run log。production 可以接 cron：「每天 9 點 push 當日待辦」。
+
+### 6. In-process conversation log，但介面是 `ConversationLog` 類別
+
+短期記憶用 `dict[int, ChatMemory]`，每個 chat 保留 20 條 exchange。production 要上 Redis 的話，只要 swap 掉 `ConversationLog` class，handler signature 完全不用改。deque maxlen=20 避免記憶體膨脹。
+
+### 7. Webhook shared-secret 驗證
+
+`X-Telegram-Bot-Api-Secret-Token` header — Telegram 官方推薦的方式，擋掉偽造 webhook 的攻擊（任何人都可以 POST 到你的 endpoint）。沒設 secret 時不驗證（方便 dev），設了之後錯的 header 直接 401。
