+# Linux Ops Monitor
+
+零第三方相依的 Linux 系統資源與日誌監控工具。讀取 `/proc`、`statvfs`、systemd journal 或傳統文字日誌，超過閾值時輸出警告並寫入可串流處理的 NDJSON。
+
+## 功能
+
+- CPU 使用率：讀 `/proc/stat` 兩次取 delta，不使用瞬間值。
+- 記憶體：以 `/proc/meminfo` 的 `MemAvailable` 計算；舊 kernel 自動 fallback。
+- 負載：`load1 / logical CPU count`，避免 4 核與 64 核主機用同一絕對值。
+- 磁碟：可設定多個 mount path，以 `statvfs` 取得精確 byte 數。
+- 日誌：`auto` 優先 journal；失敗時 fallback 到文字檔。文字檔支援 inode rotation、copytruncate 與增量 offset。

+### 日誌 backend
+

+
+## 1. 任務摘要
+
+交付一個零第三方相依的 Linux 系統資源與日誌監控工具，能在閾值超過時輸出警告並可選送 HTTPS webhook。產出位置：`./linux-ops-monitor/`，共 11 個原始檔、約 45 KB。
+
+## 2. 範圍與非目標
+
+- 範圍：CPU／記憶體／負載／磁碟資源檢查、文字或 journal 日誌增量掃描、warning/critical 兩級告警、stderr + NDJSON + 選配 webhook 輸出。
+- 非目標：未安裝 systemd unit、未排程 cron、未安裝到 `/usr/local`、未對外送任何訊息；這些都留給部署者依環境決定。
+- 安全邊界：未動 `/etc`、`/var`、`/usr`、`/boot`、cron 與 systemd；未讀取 `~/.hermes/architect_feedback.md` / `~/.hermes/review_queue.md` 之外的使用者檔案。
+
+## 3. 設計決策（為什麼這樣做）
+
+### 3.1 為什麼純 stdlib
+- N100 環境常無 `pip install` 權限，stdlib 反而最可靠。Archetype 來自 `devops/stdlib-production-tool-pattern` skill 的兩輪驗證（sysmon-tool 49 tests + asyncio variant 13 tests, 2026-07-26/28）。
+- `/proc`、`statvfs`、journalctl 已經給齊 4 種資源 + 日誌所需訊號；`psutil` / `requests` 都只是包裝。
+
+### 3.2 為什麼 strict config（fail-loud）
+- Architect feedback #1（rate limiter lazy `defaultdict`）的直接啟示：把「預設」與「用戶覆寫」混在一起會讓首次請求走錯設定。本工具對「config validator 寫法」完全套用同一精神：
+  - 未知 key 直接拒絕（`Unknown threshold key` 等四種 message），不默默接受拼字錯誤。
+  - `critical <= warning` 拒絕；`percentage > 100` 拒絕；`alert_max_bytes` / `alert_backup_count` 必須是整數。
+  - `disk_paths` 必須是非空字串 list；`logs.files` 同樣拒絕空字串。
+- 測試 `test_unknown_key_fails_loud`、`test_invalid_threshold_order_rejected`、`test_non_integer_rotation_rejected` 直接驗證以上三條。
+
+### 3.3 為什麼 CPU 採兩次 `/proc/stat` delta 而不是 `top`
+- `top` / `ps` 是命令列、解析成本高；`/proc/stat` 是核心真實值，量測 CPU 總和 idle/busy 在 0.25s 區間內的差即可得 0–100 百分比。
+- 兩次讀取都用 4 個欄位（user/nice/system/idle）；新核心 iowait 屬於 idle 一部分，所以 4 欄位 + 5 欄位兩種都接受。
+
+### 3.4 為什麼 memory 用 `MemAvailable`（不是 `MemFree`）
+- Linux 3.14+ 提供 `MemAvailable`，代表「在不觸發 swap 的情況下還能給應用程式用的記憶體」；這是監控記憶體壓力的正確指標。
+- 舊 kernel 自動 fallback 到 `MemFree + Buffers + Cached`。`test_meminfo_legacy_fallback` 鎖定這個行為。
+
+### 3.5 為什麼 load 用 `load1 / cpu_count`
+- 不同機器（4 核 vs 64 核）用同一絕對 `load1` 會誤判。比例化後 threshold 直覺可調。
+
+### 3.6 為什麼 log backend 預設 `auto` 並有 fallback
+- systemd 主機：`journalctl --show-cursor` 是低風險、cursor 持久化、跨 log rotation 乾淨。
+- 無 systemd 主機（容器、distroless）：`auto` 立刻 fallback 到 `files`，不會讓整次檢查報錯。
+- 真實測試的 `test_partial_line_completed_next_tick` 證明：writer 中途 flush 但沒換行的部分會被保留到下次 tick 完整讀入。
+
+### 3.7 為什麼 `scan_file` 同時處理 rotation、truncation 與 partial line
+- `inode` 改變 → 視為 rotated，從 0 開始。
+- `offset > current_size` → 視為 truncated，從 0 開始。
+- 結尾不是 `\n` → 倒回到 partial 開頭，下次 tick 補完。
+- 這三條規則都各自有 unit test，避免「第一次 fail 不報、第二次重複報」這類經典 bug。
+
+### 3.8 為什麼 NDJSON + rotation 而不是 SQLite
+- NDJSON 可 `tail -f | jq`、pipe 給 vector / fluentd / logstash、單行崩潰只丟一筆。
+- 內建 `alert_max_bytes` + `alert_backup_count` 讓檔案不無限增長。
+- 獨立 `.<name>.lock` 檔提供 `fcntl.flock` 跨程序保護，多個 agent 並行安全。
+- 測試 `test_ndjson_rotation` 證實備份檔被建立。
+
+### 3.9 為什麼 webhook 只接受 HTTPS（loopback 測試例外）
+- Alert payload 會含主機名與部分日誌樣本，HTTP 會在 proxy / 路由節點被看到。
+- `_validate_webhook` 拒絕非 loopback 的 http；loopback 例外讓本機 webhook 仍可測。
+- `test_insecure_remote_webhook_rejected` 鎖定這個限制。
+
+### 3.10 為什麼 collector 互不耦合
+- `run_check` 用 try/except 包每個 collector；CPU 失敗不影響磁碟／日誌。
+- errors 列表會被回填進 JSON report，但**不會**讓整次 run 直接 fail；只有「全部 collector 失敗」或「sink 全壞」才升級成 `exit 3`。
+- 真實主機第一次跑（預設 config）即為 `status=ok metrics=4 alerts=0 errors=0`，證明整個 pipeline 順暢。
+
+### 3.11 為什麼 CLI 同時有 `--watch` 與 `--json`
+- 預設人讀輸出對應 monospace 終端、可 grep 範例。
+- `--json` 提供完整結構給 SIEM 或下一棒 pipeline。
+- `--watch` + SIGTERM handler：每 tick 最多等 1 秒就響應信號，不會卡在 `time.sleep(60)` 內。
+
+### 3.12 為什麼 19 → 20 個測試（多了 partial line）
+- 第一輪測試暴露 `scan_file` 的「readline 吞行」bug：partial-line 重新讀時，readline 從行首讀到 \n 並丟進 carry 變數，後續 for-loop 沒看到這行。

+- 這是 **TDD 紅綠循環的真實示範**：測試先抓 bug、production 邏輯再修。
