# 學習任務：撰寫一個自動化檢查 Linux 系統日誌與資源的維運腳本，並在超過閾值時發出警告。
## 執行歷程與原始碼
```text
# SysMon 實作思路與審查紀錄 (2026-07-28)

## 交付清單
- `sysmon.py`          (Python 3.10+, 18,728 bytes)
- `sysmon.sh`          (Bash defensive wrapper, 2,315 bytes)
- `sysmon.toml`        (閾值設定說明, 605 bytes)
- `tests/test_sysmon.py` (18 unit tests, 全部通過)
- `README.md`          (用法 + 設計重點)

## 問題定義
撰寫一個 Linux 維運腳本：
1. 定期採樣系統資源 (CPU / Mem / Disk / Load / Swap)
2. 掃描系統日誌 (systemd journal + 傳統 syslog)
3. 閾值超標時發出結構化警告
4. 兩種使用情境:cron (`--once --exit-code`) 與 long-running (`--loop N`)

## 架構決策

### 1. 為什麼 Python 主程式 + Bash wrapper?
- **Python** 適合資料模型 (`dataclass`)、threshold 評估、JSON 輸出、unit testing。
- **Bash** 適合環境檢查 (python3 是否存在)、`logger` 串 systemd journal、state dir 自動降級、cron 路徑包裝。
- 沒有把所有東西塞進 shell,避免 `awk` 算閾值地獄,也避免 `python -c` 一大坨。

### 2. 為什麼 `dataclass` + injectable collectors?
- `Threshold` / `MetricReading` / `LogFinding` / `Report` 全部 `dataclass`,讓 `json.dumps` 跟 unit test 都不用自訂 serializer。
- `SysMon.__init__` 接受 `collectors` 跟 `log_collectors` callable dict — 測試時傳 `lambda: 99.0` 就能驗證 crit 路徑,不依賴實際系統狀態。
- `collect_journal_errors(journalctl=(...))` 連 `journalctl` 指令 tuple 都可注入 — 測試「journalctl 不存在」場景不用 monkey-patch subprocess。

### 3. 為什麼五個 fallback 而非純 psutil?
- psutil 不在精簡 container 也有 (`python:3.12-slim` 沒預裝)。
- `/proc/stat` + `/proc/meminfo` + `shutil.disk_usage` + `os.getloadavg()` 已經涵蓋所有需求。
- 寫 fallback 不是 over-engineering:這是「第一次就做對」的習慣 — 主路徑壞掉時腳本不該直接 crash。

### 4. 為什麼 dual-track 日誌 (journalctl + syslog)?
- systemd journal 是現代 Linux 預設,但 `kernels`、`cloud-init`、`syslog-ng` 有些環境不寫 journal。
- 同時讀 `/var/log/syslog` + `auth.log` + `kern.log` 作為保險,regex 抓 `err|crit|emerg|alert|failed` 關鍵字。
- 「讀取錯誤」本身用 `LogFinding(severity=warn)` 記錄,**不當 silent failure**。

### 5. 為什麼 SEVERITY_ORDER 多一個 "err"?
- 第一版用 `{ok:0, info:1, warn:2, crit:3}`,結果 `LogFinding.severity="err"` 直接 `KeyError`。
- 改成 `{ok:0, info:1, warn:2, err:3, crit:4}` — 一個 failed-service 應該 outrank metrics warning 但輸給 OOM/disk-full。
- Exit code mapping 也補上:err → 1 (跟 warn 同級,讓 cron 能區分「有問題」跟「完全壞掉」)。

## 試誤紀錄 (真實發生過的 4 個 bug)

### Bug 1: `psutil.cpu_percent(interval=None)` 第一次回 0.0
- **現象**:主機明明有負載,CPU 卻永遠 0.0%,threshold 永遠不觸發。
- **根因**:psutil 的 `interval=None` 是「相對於上次呼叫的 delta」,程序啟動後沒有「上次」,所以回 0.0。
- **修法**:模組層級 `_CPU_LAST` cache,第一次呼叫做 priming pass (`interval=sample_interval/2`),後續 `interval=None` 才有 baseline。
- **測試**:`CPUCollectorTests.test_priming_keeps_subsequent_call_nonzero` 用 FakePsutil 驗證。

### Bug 2: `SEVERITY_ORDER` KeyError on "err"
- **現象**:`test_worst_severity_is_crit` 跟 `test_report_serializable` 直接 crash。
- **根因**:見 §架構決策 #5。
- **修法**:補上 "err" rank + 補上 exit-code 對應。

### Bug 3: `tmp_path` 是 pytest fixture 不是 unittest 的
- **現象**:`test_reads_file_with_errors` 報 `missing 1 required positional argument`。
- **根因**:我寫 `unittest.TestCase` 但抄了 pytest 的 fixture 語法。
- **修法**:改用 `tempfile.TemporaryDirectory()` context manager,純 stdlib,不依賴 pytest。

### Bug 4: journalctl 解析 "CRITICAL: ..." 沒被升級成 crit
- **現象**:第一版檢查 `" crit "` (含前後空白),"CRITICAL:" (接冒號) 沒匹配。
- **修法**:改成 `any(tok in low for tok in (" crit ", " critical", ...))`,把 `critical` 當獨立 token 處理。
- **測試**:`test_parses_journalctl_output` 用 `CRITICAL: database cluster is down` 當 fixture,驗證 crit 升級。

## 設計亮點

1. **Cron / daemon 兩用**:同一支程式,`--once` 給 cron,`--loop N` 給 systemd,UX 一致。
2. **State 持久化**:每次跑都寫 `/var/lib/sysmon/state.json` (不可寫就降級到 `~/.local/share/sysmon/`),外部監控可直接 `cat` 最新狀態。
3. **Defensive bash**:`set -Eeuo pipefail`、`logger -t sysmon` 串 journal、`require_file` 早失敗。
4. **No silent failures**:每個 collector / log reader 都用 `try/except`,失敗時產生 `severity=warn` 的 finding 而不是吞掉。
5. **Unit test 離線可跑**:不需要 psutil、不需要 root、不需要 journalctl — 全部用 lambda + tempfile 注入。

## 可改進 / 未做 (留給下個 iteration)

1. `sysmon.toml` 目前只是說明檔,沒被 loader 讀。可以加 `tomllib` (Python 3.11+) 或 `tomli` 把 warn/crit 變成可調。
2. 沒有 `prometheus_client` exporter,如果要塞進 Prometheus,加個 `/metrics` HTTP endpoint。
3. Alert deduplication:目前每次都全量吐,可以加「last alert state hash」短期內不重複同樣的 alert。
4. Journald 路徑在不同 distro 不一樣 (`/var/log/journal` vs `/run/log/journal`),目前只依賴 `journalctl`,沒問題。
5. 沒有做 threshold 自適應 (例如週末白天跟平日晚上不同基線),留給 ML。

## 心得 (L3 抽象)
- **Injectable dependency 在 Python dataclass 時代幾乎零成本** — 直接傳 callable dict,不用 protocol 不用 abstract class,unit test 立刻可行。
- **「雙層 fallback」(psutil → /proc, journalctl → syslog) 才是生產級腳本的標準**,任何「我裝了 X 所以不用擔心」的心態都會在 6 個月後的某個 container 翻車。
- **第一次就做對 vs. 修 bug 的成本**:這支腳本總共踩 4 個 bug,全部都在 unit test 跟第一次 smoke run 階段被抓到,沒流到任何 production。這正是 SOUL.md 強調「深度理解優先於廣泛收集」想要的效果。```
